UltiMusic por dentro

Cómo está construido el reproductor: cada script explicado uno a uno, su estructura, el flujo de datos que los conecta y los conceptos de Android, Kotlin y Room que necesitas para entenderlos.

Qué es UltiMusic

UltiMusic es «el reproductor de música definitivo, libre de las restricciones de MediaStore». Esa frase resume su decisión de diseño más importante.

Concepto · MediaStore

MediaStore es el índice de medios del sistema Android: una base de datos que el propio Android mantiene con todas las canciones, fotos y vídeos del móvil. La mayoría de reproductores se limitan a preguntarle «dame las canciones». El problema: si MediaStore tiene una etiqueta mal, un artista mal escrito, etc., tú no lo puedes corregir de verdad.

UltiMusic da la vuelta a eso con dos reglas:

  • Descubrir canciones recorriendo las carpetas que el usuario concede (UltiMusic y las que añada), leyendo las etiquetas de cada archivo, no preguntando a MediaStore. Desde la migración a Storage Access Framework, ese acceso es por carpeta concedida, no al almacenamiento entero.
  • Lo que el usuario edita dentro de la app manda. Las ediciones se guardan en una base de datos propia (Room) y sobrescriben lo que dijera el archivo; el escaneo nunca las pisa. Los campos og* de una canción guardan la canción original de un remix, pero al ser secundarios no crean perfil de artista ni de álbum.

Sobre esa base, la app tiene hoy: seis pestañas (Canciones, Álbumes, Artistas, Géneros, Etiquetas y Listas), con orden configurable, selección múltiple y deslizar para encolar; fichas de álbum y artista con su discografía oficial; fichas de colección para listas, géneros y etiquetas; el iPod con letra sincronizada, traducción y modo vídeo; los editores de metadatos de canción (individual o múltiple) y de álbum, con autorrelleno (iTunes + Genius) y buscador de letras (lrclib.net); el buscador de fragmentos de canciones que no tienes; UltiMusic Recount, el resumen anual; y unos ajustes con ecualizador, amplificador, idioma (español/inglés), carpetas, lista gris y servicios externos.

Reglas del proyecto que se ven por todo el código
  • Color dinámico: todo lo que era amarillo (o amarillo oscuro) se pinta con el acento de la canción que suena (DynamicColor, AccentTint).
  • Lo nuevo se ve al instante en toda la app tras una edición: casi todo cuelga de Flow de Room, y lo que no (archivos, la copia de cada canción en el Service, el contenido de una carátula) tiene su propio mecanismo de refresco (tick, refreshSong, CoverArt.revision).
  • Toda modificación del esquema lleva su migración escrita a mano, para no perder nunca la fonoteca del usuario (Migrations.kt).
  • Todos los textos existen en español e inglés (values/ y values-en/).

Conceptos base

Ideas de Android, Kotlin y Room que se repiten por todo el código. Si algún término te suena raro más adelante, vuelve aquí.

Kotlin · data class

Una data class es una clase pensada para guardar datos. Kotlin le genera automáticamente cosas útiles (comparación, copia con copy(), texto legible). Casi todos los «modelos» son data classes.

Kotlin · object y companion object

object X { } crea un singleton: una única instancia global para toda la app (útil para utilidades sin estado). Un companion object dentro de una clase es como su «zona estática»: constantes y funciones que pertenecen a la clase, no a cada objeto (p. ej. UltiMusicDatabase.get(...)).

Kotlin · coroutines, suspend y Dispatchers

Una corrutina es una tarea que puede pausarse y reanudarse sin bloquear el hilo. Una función suspend solo se llama desde dentro de una corrutina. withContext(Dispatchers.IO) mueve el trabajo a hilos de entrada/salida (disco, red, base de datos), dejando libre el hilo principal para que la interfaz no se congele.

Kotlin · Flow y StateFlow

Un Flow es un «grifo» de valores que van llegando con el tiempo. Si te suscribes, recibes cada nuevo valor. Room puede devolver un Flow de una consulta: cuando la tabla cambia, el Flow reemite la nueva lista solo. Un StateFlow es un Flow que además recuerda siempre su último valor (ideal para la interfaz).

Android · Activity, Fragment y ViewModel

Una Activity es una pantalla del sistema. Un Fragment es un trozo reutilizable de pantalla dentro de una Activity (aquí, cada pestaña). Un ViewModel guarda los datos de la pantalla y sobrevive a girar el móvil o a recrear la vista; separa «los datos» de «cómo se dibujan».

Android · RecyclerView y Adapter

Un RecyclerView es una lista eficiente: solo crea las filas visibles y las recicla al hacer scroll. El Adapter es el puente entre tus datos y esas filas: dice cuántas hay, crea cada fila (ViewHolder) y rellena su contenido.

Android · Room

Room es la librería oficial para usar una base de datos SQLite con comodidad. Tú describes las tablas con clases anotadas (@Entity), las consultas en una interfaz (@Dao), y Room genera todo el código SQL por ti, comprobando los errores al compilar.

Capa de modelos — model/

Los modelos de dominio: objetos limpios que consume la interfaz. No saben nada de Room ni del disco; son solo «una canción», «un álbum», «un artista». La capa de datos los produce a partir de las tablas.

Patrón · SortableLibraryItem

Casi todos los modelos que se pintan en una pestaña (Song, AlbumSummary, PersonSummary, GenreSummary, TagSummary, PlaylistSummary) implementan la interfaz SortableLibraryItem de LibrarySort: exponen sortName, sortDuration, sortYear, sortPopularity y sortSongCount. Así un único ordenador genérico sirve para todas las pestañas, y cada modelo decide qué significa cada criterio para él (un género no tiene año, así que su sortYear es null).

model/Song.ktdata class · una canción

Representa una canción tal como la ve la interfaz, ya con sus artistas, productores y álbumes incrustados como listas.

Estructura

  • id, filePath, title, duration, year, genres. Ojo: desde la migración a SAF, filePath ya no es una ruta de archivo real sino un docPath (ruta lógica dentro de una carpeta concedida, ver SafStorage), o un URI completo para un archivo abierto con «Abrir con UltiMusic».
  • artists: List<Artist> y producers: List<Producer> — una canción puede tener varios de cada uno (colaboraciones).
  • albums: List<SongAlbumEntry> — una canción puede estar en varios álbumes a la vez (el álbum original y un recopilatorio, por ejemplo), en el orden en que se enlazaron. Cada SongAlbumEntry lleva el Album y la posición trackNumber/discNumber que ocupa dentro de ese álbum concreto: la misma canción puede ser la pista 5 de uno y la 12 de otro, así que la posición es del enlace, no de la canción (ver SongAlbumCrossRef). Entre v13 y v26 la relación fue N:1; en v27 volvió a ser N:M.
  • album, trackNumber, discNumber — propiedades calculadas que devuelven el primer álbum de albums y su posición. Las usa todo lo que solo necesita enseñar uno (la notificación, el «ir al álbum» del menú…). null si no está en ningún álbum.
  • imageName, comment, lyrics, language — metadatos editables.
  • videoUrl — enlace de YouTube del videoclip, para el modo vídeo del iPod. Lo pone siempre el usuario (a mano en el editor, o eligiéndolo en el buscador que abre el propio iPod).
  • videoThumbnailName — miniatura de ese vídeo recortada al cuadrado y cacheada en la carpeta de imágenes (ver CoverArt). Carátula de reserva cuando la canción no tiene imagen propia ni arte embebido.
  • videoOffsetMs — milisegundos que se adelanta (positivo) o atrasa (negativo) el vídeo respecto al audio local. Nunca toca el audio: solo la posición a la que se pide el vídeo.
  • lyricsOffsetMs — lo mismo pero para la letra sincronizada: corrige letras de lrclib.net que no van del todo a tiempo. Se aplica en LrcParser.currentIndex; no afecta a letras sin marcas de tiempo.
  • ogTitle / ogArtist / ogYear — info de la canción original de un remix (el prefijo «og» = original). Al ser campos secundarios, no crean perfil de artista ni de álbum. Rellenar ogTitle añade sola la etiqueta del sistema «Remix/Cover» (ver Tag).
  • youtubeViewCount — visitas del vídeo de videoUrl, o null si no hay vídeo o aún no se han pedido. Es el criterio «popularidad» al ordenar canciones (ver YouTubeStatsApi).
  • dateAdded — epoch ms en que se añadió a la fonoteca; alimenta la etiqueta «Añadidas recientemente» y el orden por fecha.

model/MetadataSuggestion.ktdata class · candidato de autorrelleno

Un candidato encontrado en iTunes para el autorrelleno de metadatos. Representa siempre una publicación concreta (un álbum, un single…), nunca «la canción» en abstracto —ver ItunesApi— porque eso es justo lo que permite elegir, por ejemplo, el año y la portada del single en vez de los del álbum.

Es un único modelo compartido por canción y álbum en vez de dos clases separadas, porque el diálogo de sugerencias, su lista y su ViewModel son los mismos para ambos casos; solo cambia qué campos trae rellenos cada uno (una sugerencia de álbum no tiene trackNumber/discNumber, y su albumTitle se queda a null porque su title YA es el álbum).

coverUrl es la miniatura de iTunes; en una sugerencia de canción con Genius disponible, la fila la sustituye después por la carátula propia de la canción si la encuentra (ver MetadataSuggestionsViewModel.coverArtOverride). genre es el único género que iTunes da por publicación (primaryGenreName), ya traducido al idioma de la tienda consultada.

El mismo archivo declara los dos enums que lo acompañan: SuggestionKind (canción o álbum, lo que decide qué se busca) y ReleaseType (Álbum / Single / EP, la etiqueta de cada fila). iTunes no da el tipo como campo: se deduce del nombre de la colección y del número de pistas, y siempre sale uno.

model/LyricsSuggestion.ktdata class · candidato del buscador de letras

Un candidato encontrado en lrclib.net para el buscador de letras del editor de metadatos. A diferencia de MetadataSuggestion, aquí la búsqueda ya trae la letra completa (syncedLyrics/plainLyrics) de cada candidato: no hace falta pedir nada más cuando el usuario elige uno.

syncedLyrics es texto con marcas de tiempo [mm:ss.xx] por línea (formato «LRC»); plainLyrics es la misma letra sin marcas, de respaldo.

durationMatches no viene de lrclib.net: lo calcula LrcLibApi.search comparando la duración del candidato con la del archivo que se está editando. Dice si la letra se sincronizó contra ESA misma grabación.

model/Summaries.ktdata class · resúmenes de las pestañas

Los modelos que consumen las pestañas de Álbumes, Artistas, Géneros y Etiquetas y sus fichas de detalle. No son las entidades completas porque lo que se pinta ahí son datos agregados (cuántas canciones, cuánto dura todo), que la entidad por sí sola no conoce.

  • AlbumSummary — id, title, artistName, year, songCount, totalDuration y un CoverRef.
  • PersonSummary — name, songCount, albumCount, totalDuration, CoverRef y popularity: los suscriptores del canal de YouTube que más se repite entre las canciones donde el artista es el principal (las colaboraciones como invitado no cuentan). Su companion define OTHERS_ARTIST_ID = -1, el id del perfil agregado «Otros» (ver ArtistGroupingPreferences): Room nunca genera ids negativos, así que no puede chocar con un artista real.
  • GenreSummary — name, songCount y totalDuration: sin id ni CoverRef, porque un género no es una entidad de la BD; es solo el texto de Song.genres, agrupado en Kotlin (ver LibraryRepository.genres).
  • TagSummary — id, name, colorArgb, songCount, totalDuration, systemKey e isAutoAssigned. A diferencia de un género, una etiqueta SÍ es entidad propia (de ahí el id), pero su recuento se calcula en Kotlin porque 3 de las predefinidas no tienen membresía guardada. systemKey e isAutoAssigned viajan aquí para que la UI sepa, sin resolver nada aparte, si mostrar la X de «quitar» o si ofrecerla en el buscador de «+ Añadir». isAutoAssigned cubre las etiquetas de idioma, que no tienen systemKey pero sí las mismas restricciones.

model/Recount.ktdata classes · UltiMusic Recount

Los modelos de UltiMusic Recount. Ninguno se guarda: todos se calculan al abrir la pantalla, cruzando las escuchas crudas (PlayEventEntity) con la fonoteca tal y como está en ese momento. Por eso llevan un label de texto en vez de ids: son el resultado de una agregación, no entidades.

  • RecountEntry — una fila de cualquiera de los tres tops (canciones, artistas, géneros): label, plays, playedMs, share, y opcionalmente songId/cover. isDeletedBucket marca la fila especial «Canciones borradas», que agrupa las escuchas de canciones que ya no existen: compite por el top 10 de canciones pero nunca aparece en artistas ni géneros. share se reparte en reproducciones, no en tiempo, y siempre sobre el total real del año; por eso en artistas y géneros las fracciones pueden sumar más del 100% (una canción con tres artistas cuenta entera para los tres).
  • GenreSlice — un sector de la tarta de géneros (fraction entre 0 y 1; isOther para el sector agregado «Otros»).
  • RecountData — todo lo de un año: totales, los tres tops y los sectores. isEmpty distingue «no hay nada de este año» para enseñar el estado vacío.
  • HistogramBar / HistogramData — el histograma de canciones por año de publicación. Una racha de 3+ años vacíos se colapsa en dos columnas borde (isGapEdge) con una raya entre ellas, para que un disco de 1968 no aplaste el resto del gráfico. Las canciones sin año se cuentan aparte en unknownYearCount.

Capa de escaneo — data/scan/

La parte de «lectura» de la fonoteca. Recorre las carpetas concedidas y extrae las etiquetas de cada archivo de audio, sin tocar la base de datos.

data/scan/ScannedSong.ktdata class · etiquetas crudas

El resultado de escanear un archivo: solo las etiquetas leídas (título, artista, álbum, artista del álbum, géneros, año, duración, productor, nº de pista y disco) más dateAdded. Sin IDs ni relaciones. Es lo que el escáner entrega a la capa de datos. Esto no es MediaStore: son las etiquetas del propio archivo.

dateAdded llega ya resuelta por el escáner (la fecha de modificación que el proveedor SAF da al listar la carpeta), porque desde la migración a SAF filePath ya no es una ruta sobre la que se pueda llamar File.lastModified().

Los campos de artista/álbum pueden ser null; si faltan, la capa de datos no crea entidad ni enlace para ellos.

data/scan/MusicScanner.ktobject (singleton) · escáner de carpetas SAF

Busca canciones directamente en las carpetas concedidas por Storage Access Framework (ver SAF), fiel a la filosofía «libre de MediaStore».

Estructura

  • AUDIO_EXTENSIONS — extensiones reconocidas (mp3, flac, m4a, aac, ogg, oga, opus, wav, wma, mkv).
  • UNKNOWN_ARTIST / UNKNOWN_ALBUM — «Artista desconocido» y cadena vacía.
  • ScanResult(newSongs, currentPaths) — newSongs son las etiquetas de los archivos no catalogados todavía; currentPaths, los docPath de todos los archivos encontrados. Hace falta el segundo conjunto para que LibraryDao.reconcile sepa qué canciones han desaparecido.
  • scan(context, knownPaths, onProgress) — recorre todas las SafStorage.grantedRoots() (UltiMusic + las raíces adicionales) y solo abre con MediaMetadataRetriever los archivos que no están en knownPaths. Releer las etiquetas de cada archivo ya conocido en cada arranque era la parte lenta y no servía para nada. onProgress alimenta el contador de escaneo de la interfaz.
  • libraryFolderReadable(context) — ¿se pueden leer ahora mismo todas las carpetas concedidas? Sin ninguna concedida tampoco cuenta como legible. Lo consulta quien vaya a dar una canción por perdida, para no confundir «la canción ya no está» con «la carpeta no se puede leer» (permiso revocado, etc.).
  • findByFilename(context, name) — busca un archivo de audio por su nombre en las carpetas concedidas. Solo lista directorios, no abre archivos: muy rápido. Sirve para relocalizar al vuelo una canción que el usuario ha movido.
  • readTagsFromUri(context, uri) — lee las etiquetas de un archivo suelto llegado por «Abrir con UltiMusic» desde otra app, con el mismo lector, para que se vea igual que uno de la fonoteca. Nunca se persiste.
  • collectAudioEntries(context, treeUri, rootDocPath) — lista los audios de una raíz sin leer etiquetas; lo usa LibraryRepository.relinkAfterGrant para reemparejar las canciones catalogadas antes de la migración a SAF.

Flujo / por qué

Todo corre en Dispatchers.IO. El recorrido es iterativo (una pila ArrayDeque) sobre SafStorage.listChildren, e indexa por docPath en un LinkedHashMap para no repetir si dos raíces se solapan.

Android · MediaMetadataRetriever

Es la clase del sistema que abre un archivo de audio/vídeo y extrae sus metadatos (título, artista, duración, carátula embebida…). Hay que release()-arla siempre al terminar; por eso se usa dentro de try/finally. Con SAF se le pasa un Uri de documento en vez de una ruta.

El antiguo MusicLibraryObserver (que vigilaba la carpeta con FileObserver) se eliminó: con SAF no hay rutas reales que observar, así que la fonoteca se reconcilia al arrancar y al volver a primer plano.

Tablas de la base de datos — data/db/entities/

Cada clase aquí es una tabla de la base de datos. La interfaz no las usa directamente; son la forma «normalizada» de guardar los datos. Hoy son 13 tablas (esquema v30).

Room · @Entity, clave primaria e índices

@Entity convierte una clase en una tabla. La clave primaria (@PrimaryKey) identifica cada fila de forma única; autoGenerate deja que Room asigne un número. Un índice (@Index) acelera las búsquedas por una columna y, si es unique, impide filas repetidas en esa columna.

Concepto · normalización y «clave de emparejamiento»

En vez de repetir «DECO*27» en cada canción, se guarda el artista una sola vez en su tabla y las canciones lo referencian. Eso es normalizar: editar el artista una vez lo cambia en todas sus canciones. Para reencontrar al mismo artista en escaneos futuros, cada artista/álbum guarda su valor de etiqueta original (tagName, tagTitle…) como clave estable de emparejamiento, independiente del nombre editable que se muestre.

data/db/entities/SongEntity.kttabla songs

Una fila por canción. filePath tiene índice único: es el ancla estable que identifica la canción entre escaneos (aunque el id autogenerado cambie).

Desde la migración a SAF, filePath ya no es una ruta de archivo real: es la ruta relativa al volumen del documento (p. ej. UltiMusic/Bootlegs/track.mp3, sin barra inicial ni esquema). Se guarda así, y no el content://, para que reconcile y la lista gris sigan pudiendo comparar con substringAfterLast('/') / startsWith(prefijo + "/"): un content:// en crudo lleva el id del documento codificado como un único segmento opaco. El URI abrible se reconstruye al vuelo con SafStorage.resolveUri.

Guarda los campos editables (title, duration, year, genres, lyrics, language, imageName, comment), los del vídeo (videoUrl, videoThumbnailName, videoOffsetMs), lyricsOffsetMs, hiddenByGreylist, los og* de remix (a null al escanear), dateAdded y dos campos que sí salen de la API de YouTube: youtubeViewCount y youtubeChannelId.

Ni el álbum ni el productor viven aquí: los dos se enlazan por tabla de cruce (song_album, song_producer), igual que los artistas. dateAdded lleva @ColumnInfo(defaultValue = "0") a propósito: SQLite exige un DEFAULT para añadir una columna NOT NULL a una tabla con filas, y sin la anotación el esquema que Room espera no coincidiría con el que deja la migración.

Diseño · hiddenByGreylist, ocultar sin borrar

hiddenByGreylist es la columna que hace funcionar la lista gris: cuando una subcarpeta está excluida, sus canciones se marcan con true y todas las consultas de lectura las excluyen. Al desactivar el switch, se marcan de vuelta a false y reaparecen exactamente igual.

La alternativa obvia —excluir esas carpetas del escaneo y dejar que reconcile() borre las canciones que «desaparecen»— se descartó a propósito: borraría de verdad esas filas (con sus ediciones, carátula, vídeo y sitio en las playlists) y al reactivar la carpeta volverían como canciones nuevas. hiddenByGreylist es solo un filtro de lectura.

Por qué videoUrl lo pone siempre el usuario. Las Developer Policies de YouTube obligan a borrar o refrescar cada 30 días cualquier dato obtenido de su API. Un enlace que teclea o elige el usuario no es dato de la API: es dato nuestro y se puede conservar indefinidamente. videoThumbnailName se acoge a la misma lógica (miniatura pública del CDN img.youtube.com). En cambio youtubeViewCount/youtubeChannelId sí vienen de la API, y por eso se refrescan como mucho una vez al día (ver YouTubeStatsRefresh), lo que cumple de sobra esa política.

Room · relaciones N:N y claves foráneas

Una canción puede tener varios artistas y un artista varias canciones: es una relación muchos-a-muchos. En SQL eso se resuelve con una tabla de cruce (cross-ref) que empareja los IDs de ambos lados. Una clave foránea (@ForeignKey) con onDelete = CASCADE hace que, al borrar una canción, se borren solas sus filas de cruce.

Canción↔álbum ha ido y vuelto: nació N:M, la v13 la simplificó a N:1 (columna albumId en songs) y la v27 la devolvió a N:M con SongAlbumCrossRef, para poder catalogar una canción en el álbum original y en un recopilatorio.

data/db/entities/SongArtistCrossRef.kt · AlbumArtistCrossRef.kt · SongProducerCrossRef.kttablas de cruce N:N
  • song_artist — empareja songId ↔ artistId.
  • album_artist — albumId ↔ artistId.
  • song_producer — songId ↔ producerId. Gemela de song_artist.

Las tres llevan una columna position: el orden en que el usuario (o la etiqueta) puso a cada artista/productor. Hace falta porque un @Relation de Room no garantiza ningún orden (en la práctica sale por id), y el primero de la lista importa: es el «artista principal», el que cuenta para la popularidad de YouTube y el que se usa para crear álbumes nuevos.

Cada una tiene clave primaria compuesta, claves foráneas en cascada e índice en la columna secundaria (Room exige indexar las columnas foráneas).

Diseño · sin clave foránea, a propósito

Todas las demás tablas que apuntan a songs lo hacen con CASCADE. Esta no: una cascada borraría las escuchas justo al borrar la canción, que es cuando hacen falta para el cubo «Canciones borradas». year va desnormalizado: calcularlo al consultar con 'localtime' usaría la zona horaria del momento de la consulta, y quien se mudara de país vería saltar escuchas de diciembre de un año a otro. Se decide una vez, al empezar a sonar.

La regla de oro de reconcile(newSongs, currentPaths)

Una canción cuya ruta ya está guardada no se toca: así ningún reescaneo puede pisar lo que editaste. La reconciliación compara conjuntos de rutas, en fases:

  1. Se separan las rutas desaparecidas (gone: guardadas pero no en currentPaths) de las aparecidas (appeared).
  2. Emparejamiento por nombre de archivo: misma basename en gone y appeared = el mismo archivo movido. Solo se reapunta con updateSongPath().
  3. Emparejamiento por duración exacta (ms): para un archivo movido y renombrado a la vez. Solo si esa duración es única a ambos lados; con ambigüedad no se adivina.
  4. Altas reales: se insertan, resolviendo antes el álbum (clave = primer artista, para que las colaboraciones no partan un álbum en varios) y enlazando artistas y productores (una etiqueta «A, B» son dos personas).
  5. Bajas reales: se borran y se podan huérfanos. Excepción: una fila con ruta absoluta (empieza por /) es una canción de antes de SAF todavía sin re-enlazar; entra en gone para poder emparejarse, pero nunca se borra aquí, porque solo significa que su carpeta aún no está concedida.
  6. Siempre, al final: mergeDuplicateAlbums() funde álbumes con el mismo tagTitle y primer artista (sobrevive el de menor id, que hereda año/portada si le faltaban).
Diseño · por qué detectar movimientos y no borrar+insertar

La fila de una canción guarda mucho más que su ruta: su id (del que cuelgan sus escuchas del Recount), todo lo editado, la carátula importada y sus enlaces. Tratar un movimiento como «borrado + alta» perdería todo eso. El emparejamiento por nombre asume que no hay dos archivos con el mismo nombre en carpetas distintas —la misma suposición que las playlists—; el de duración no la necesita, pero exige unicidad.

Respecto a la lista gris: una canción nueva dentro de una carpeta ya excluida entra directamente oculta, y un archivo movido hacia dentro o fuera de una carpeta excluida recalcula su visibilidad en el mismo paso.

Cómo guarda el editor: saveSongEdits(song, artistNames, albums, producerNames)

Una sola @Transaction que rehace desde cero los enlaces de la canción con artistas, álbumes y productores (en orden, guardando position) y escribe la fila entera. albums es una lista de AlbumEdit(title, trackNumber, discNumber): cada álbum trae su propia posición. Una lista vacía desengancha la canción de cualquier álbum.

Los nombres que escribe el usuario reenlazan: se busca la entidad con ese nombre (primero visible, luego de etiqueta) y, si no existe, se crea. Nunca se renombra una entidad existente desde aquí, porque afectaría a todas las demás canciones que cuelgan de ella. Ni artista, ni álbum, ni productor tienen valor por defecto: vaciar el campo deja la canción sin ninguno. Al final se podan huérfanos y se funden duplicados.

saveAlbumEdits(album, artistNames) es su gemela para el álbum: fila del álbum + reenlazado de album_artist, sin tocar canciones.

La fachada de la biblioteca y las piezas de data/ que no son ni Room ni red: preferencias persistidas y el proceso de «Añadir todas las letras». La fachada del Recount tiene su propia sección (ver UltiMusic Recount).

data/LibraryRepository.ktfachada de la biblioteca · singleton

El único punto por el que el resto de la app accede a la biblioteca. Orquesta el escáner y la base de datos, y esconde los detalles. Se obtiene con LibraryRepository.get(context). Tiene su propio observerScope (un CoroutineScope con SupervisorJob en Dispatchers.IO) para el trabajo que no debe morir con la pantalla que lo pidió.

Lecturas reactivas

  • songs: Flow<List<Song>> — la lista reactiva ya en modelos de dominio.
  • albums / artists — los resúmenes de sus pestañas. artists no es la lista cruda: pasa por la agrupación «Otros» (ver abajo). smallArtistIds expone los ids agrupados, para redirigir a «Otros» cualquier navegación directa a uno de ellos.
  • genres / songsOfGenre(genre) — la pestaña de Géneros, derivada en Kotlin a partir de songs (el género no tiene tabla): se agrupa por texto exacto y una canción con varios géneros cuenta entera en cada uno.
  • tagSummaries(...), songsOfTag(id, ...), tagsOfSong(songId, ...) y songTagsById(...) — la pestaña de Etiquetas, la ficha de una etiqueta, las etiquetas de una canción y las de todas a la vez (la pestaña Canciones las pinta en una tercera línea: resolverlas una vez para toda la biblioteca es mucho más barato que una vez por fila). Todas reciben filenamesInAnyPlaylist como parámetro (ver el recuadro).
  • album(id) / artist(id), albumArtistNames(id), albumEntityForEdit(id), albumTracks(id), artistSongs(id), artistAlbums(id) — las fichas de detalle y el editor de álbum. Para el id OTHERS_ARTIST_ID, artistSongs filtra las canciones cuyos artistas son todos pequeños (una colaboración con un artista «grande» ya sale en la ficha de este) y artistAlbums devuelve vacío.
  • greylistFolders, libraryRoots, artistNames / albumTitles / producerNames (autocompletado).
  • reconciling: Flow<Boolean> y reconcileProgress: Flow<Int> — si hay una reconciliación en marcha y su porcentaje, para el aviso «Actualizando la base de datos… N%».

Escaneo y carpetas

  • reconcile(onProgress) — pide las rutas ya catalogadas, escanea solo lo nuevo y delega en LibraryDao.reconcile. El trabajo se lanza en observerScope y quien llama solo espera (join): antes, cerrar el diálogo de ajustes a mitad de escaneo cancelaba la reconciliación en silencio.
  • startWatchingLibraryChanges(requester) / stopWatchingLibraryChanges(requester) — el reescaneo periódico (cada 3 minutos) que sustituye al viejo FileObserver: SAF no puede avisar de cambios en un árbol concedido. Lo piden por separado MainActivity (en primer plano) y PlaybackService (mientras suena algo), cada uno con su LibraryWatchRequester; se guarda un conjunto de interesados (no un contador, para que pedirlo dos veces no lo deje encendido para siempre) y solo se para al soltarlo el último. La primera vuelta espera el intervalo entero para no duplicar el escaneo de arranque.
  • addGreylistFolder / removeGreylistFolder / setGreylistFolderExcluded — envoltorios finos sobre el DAO, sin reescaneo.
  • addLibraryRoot(treeUri) / removeLibraryRoot(treeUri) — raíces adicionales ya concedidas con el selector del sistema.
  • grantUltiMusicRoot(treeUri) — concede la carpeta UltiMusic (obligatoria) y llama a relinkAfterGrant: recorre el árbol concedido y, para cada archivo, compone la ruta absoluta que habría tenido antes de SAF (/storage/emulated/0/ + docPath) y reapunta la fila que tuviera exactamente esa ruta. hasUnlinkedLegacySongs() dice si queda alguna fila con ruta absoluta, para ofrecer re-conceder también Download/Music.
  • resolvePlayablePath(song) — devuelve un docPath que de verdad se puede reproducir, o null (ver el recuadro). libraryFolderReadable() reexpone la comprobación del escáner.

Ediciones (se reflejan al instante vía el Flow)

  • saveSongEdits(song, artistNames, albums, producerNames, previousLanguage) — el guardado completo del editor de metadatos. albums es una lista de AlbumEdit. Después sincroniza las etiquetas automáticas: syncSyncedVideoTag (según videoOffsetMs), syncRemixCoverTag (según ogTitle) y syncLanguageTag (mueve la canción de la etiqueta del idioma anterior a la del nuevo, creándola si no existía).
  • saveAlbumEdits(album, artistNames), updateSong/Artist/Album/Producer.
  • renameArtist(id, newName) / renameGenre(old, new) — renombrados globales desde la ficha (ver LibraryDao).
  • setVideoUrl(song, url) — guarda el enlace y gestiona la miniatura (borra la vieja, descarga la nueva) y pide las visitas del vídeo nuevo al instante. Lo usan el editor y el buscador del iPod. setVideoOffsetMs(song, ms) — el desplazamiento vídeo/audio.
  • setLyrics(song, lyrics) — guarda una letra elegida fuera del editor (desde el iPod o desde «Añadir todas las letras») y deduce su idioma con LanguageDetector para mover la etiqueta de idioma. backfillMissingLanguageTags() repara, en cada arranque, las canciones que se quedaron con letra pero sin idioma antes de que existiera esto.
  • Etiquetas: addSongToTag / removeSongFromTag, applyTagsToSongs(songIds, add, remove) (edición múltiple), createTag / updateTag / deleteTag.
  • refreshYouTubeStatsIfDue(force) — refresca, como mucho una vez al día, las visitas y el canal de cada canción con vídeo y recalcula la popularidad de cada artista (la moda del canal entre sus canciones principales; SQL solo cuenta, Kotlin decide). force se usa al guardar una clave nueva. refreshYouTubeStatsForSong(id, url) es la excepción puntual tras cambiar el vídeo de una canción (y recalcula solo su artista principal). Todo best-effort en observerScope.
  • songsByIds(ids) / songByPath(path) — lecturas puntuales (restaurar colas, «Abrir con UltiMusic»).

Imágenes, borrado y copia

  • importCoverImage(uri, title) — copia la portada elegida a UltiMusic/images y devuelve su nombre. Se copia en vez de guardar la URI porque esa URI es un permiso temporal. Devuelve el nombre que de verdad creó el proveedor SAF (SafStorage.createFile), no el pedido: si había colisión, createDocument no sobrescribe, crea «Título (1).img», y guardar el nombre pedido dejaba la carátula apuntando a un archivo inexistente.
  • renameImage(...), downloadVideoThumbnail(videoId, title), deleteCoverImage(name), deleteVideoThumbnail(name).
  • deleteSong(song) — borra la canción de verdad: archivo (vía SAF), carátula, miniatura y fila. No toca las playlists: quien llame debe sacarla con PlaylistRepository.removeSongFromAll.
  • exportDatabaseCopy() — checkpoint del WAL y copia de la BD a UltiMusic/databases (solo si UltiMusic está concedida).
Diseño · la agrupación «Otros»

Con el umbral de ArtistGroupingPreferences por encima de 0, los artistas con ese número de canciones o menos dejan de listarse sueltos y se agrupan en un perfil «Otros». Es una vista calculada en Kotlin con combine(rawArtists, songs, threshold): no hay fila «Otros» en Room ni se reasigna ninguna canción, así que no necesita migración. Las cifras de «Otros» salen de las mismas canciones que lista su ficha, no de sumar las de cada artista (eso contaría dos veces una colaboración entre dos pequeños). Lista, ids pequeños y perfil «Otros» se calculan juntos para que siempre cuadren.

Diseño · etiquetas reales y calculadas

resolveAllTags resuelve cada etiqueta contra la biblioteca: las de membresía real leen song_tag; «Añadidas recientemente» son las 20 de dateAdded más reciente; «Sin etiquetas personalizadas», las que no tienen ninguna etiqueta de usuario (una de idioma no cuenta); «En ninguna lista» necesita saber qué hay en las playlists, que viven en archivos ajenos a este repositorio. En vez de leerlos aquí (acoplaría los dos repositorios y rompería la reactividad, porque un archivo no reemite), ese conjunto se recibe como parámetro: lo conecta TagsViewModel al tick de PlaylistsViewModel.

Diseño · la ventana en la que una ruta guardada miente

La reconciliación no es instantánea y, con SAF, además solo se repite cada pocos minutos. Mientras tanto la BD puede seguir apuntando a la carpeta antigua de un archivo movido, y pasarle esa ruta a ExoPlayer lo dejaba clavado en 0:00 sin decir nada. resolvePlayablePath() cierra esa ventana: si el archivo no está, lo busca por nombre con MusicScanner.findByFilename() (barato) y, si aparece, corrige la fila de paso.

SQLite · WAL y checkpoint

Room usa el modo WAL (Write-Ahead Log): los cambios se escriben primero en .db-wal y más tarde se consolidan en el .db. Para una copia consistente, primero se ejecuta PRAGMA wal_checkpoint. La copia es unidireccional y best-effort; se hace porque en algunos móviles no se puede entrar en /data/data, y es la que restaura UltiMusicDatabase tras reinstalar.

Playlists en disco — data/playlist/

Las listas de reproducción son la única parte de la biblioteca que no vive en Room, sino en archivos de texto. Se decidió así porque una playlist es, conceptualmente, un documento del usuario: debe poder verse y editarse desde fuera de la app y sobrevivir a reinstalaciones sin tocar la base de datos.

data/playlist/PlaylistRepository.ktclase singleton · almacén de playlists

Guarda y lee las playlists de UltiMusic/Playlists, a través de SafStorage (la carpeta concedida). Cada playlist es un archivo <nombre>.txt: el nombre del archivo (sin la extensión) es el nombre de la lista, y su contenido es un nombre de archivo de canción por línea, en orden de reproducción (solo el «basename»: cancion.mp3).

Desde SAF ya no es un object: necesita un Context para resolver la carpeta concedida, así que UltiMusicApp lo inicializa con init(context) y el resto de la app lo pide con PlaylistRepository.get(). Si UltiMusic no está concedida, las lecturas devuelven vacío.

Qué ofrece

  • listPlaylistNames() — los nombres de todas las playlists, ordenados sin distinguir mayúsculas.
  • readFilenames(name) / setFilenames(name, list) — leer y reescribir el archivo entero (más simple y seguro que parchear líneas; es lo que usa la reordenación por arrastre).
  • createPlaylist / deletePlaylist / renamePlaylist — crear (archivo vacío), borrar y renombrar. isValidName(name) rechaza los caracteres que no admite FAT32/exFAT (/ \ : * ? " < > |); es pública para que la UI avise con un toast antes de tocar disco, en vez de que SAF falle en silencio.
  • addSongs(name, filenames) / removeSongs(name, filenames) — añaden al final (las que no estuvieran) o quitan varias de una vez, con una sola reescritura.
  • playlistsContainingAll(filenames) — en qué playlists están todas las canciones dadas (las casillas del diálogo «Añadir a playlist»).
  • allFilenamesInAnyPlaylist() — la unión de todas las playlists, para la etiqueta «En ninguna lista».
  • resolveSongs(name, byFilename) — convierte los nombres de archivo en Song reales usando un índice basename → Song que arma quien llama; descarta lo que ya no existe.
  • removeSongFromAll(filename) — quita una canción de todas las playlists y devuelve cuáles se han tocado. Para cuando el archivo ha desaparecido de verdad o el usuario lo ha borrado.
Diseño · las playlists no se quedan vacías

writeRemaining(name, remaining) es el punto único tras quitar canciones: si la lista resultante está vacía, borra el archivo en vez de dejar una fila fantasma en la pestaña. La excepción a propósito es createPlaylist, que sí crea un archivo vacío porque el usuario la acaba de pedir.

Concepto · archivos no reactivos vs. Room

Room reemite un Flow solo cuando cambia una tabla; un documento SAF no avisa a nadie. Por eso el PlaylistsViewModel debe volver a leer tras cada cambio: mantiene un contador («tick») que incrementa al mutar y que fuerza el recálculo.

Limitación asumida por diseño: se casa por basename. Si dos archivos en carpetas distintas se llaman igual, gana el que esté en el índice. Las otras preferencias de playlist (posición guardada, historial, aleatorio) no viven aquí sino en util/: PlaylistResumeStore, PlaylistHistoryStore y PlaylistShuffleStore.

Android · HttpURLConnection

Es la clase de red que trae el propio Android, sin ninguna librería aparte (a diferencia de OkHttp o Retrofit). Como la app solo hace un puñado de tipos de llamada, no compensa añadir una dependencia: se abre la conexión, se ponen las cabeceras, se lee la respuesta como texto y se cierra.

JSON · org.json

JSON es el formato de texto con el que casi todas las APIs web devuelven sus datos: llaves { } para objetos, corchetes [ ] para listas, y pares "clave": valor. org.json (JSONObject/JSONArray) es el lector que trae Android; se usa en vez de Gson o Moshi porque son muy pocos campos y así no hace falta ninguna dependencia nueva.

Infraestructura compartida

data/remote/HttpJson.ktinternal object · el GET común

El GET que usan todas las APIs (salvo Lingva, que prueba varias instancias por su cuenta). Antes cada cliente tenía el suyo; se unificaron porque la caché y el manejo de límites tienen que valer igual para todos. Devuelve el cuerpo sin parsear. El orden importa:

  1. Caché (ApiCache): si hay una respuesta reciente para esa URL exacta, se devuelve sin tocar la red — ni siquiera un servicio castigado impide usar lo ya descargado.
  2. Castigo (RateLimitGuard): si ese servicio nos ha limitado hace poco, se corta aquí sin abrir la conexión.
  3. Petición, con hasta 3 intentos ante fallos de conexión (DNS, timeout…), que casi siempre son intermitentes. Un código HTTP ya respondido no se reintenta: 429 (o 403 de Genius) → ApiRateLimitException; 401 → ApiUnauthorizedException; cualquier otro distinto de 200 → IOException.
  4. Guardado: solo los 200 entran en la caché.

El cuerpo se lee como UTF-8 explícitamente: iTunes sirve el JSON como text/javascript sin declarar codificación, y con el valor por defecto los títulos en japonés o con acentos llegaban rotos. useCache = false lo usa Deezer (URLs firmadas que caducan).

data/remote/ApiCache.ktobject · política de la caché HTTP

La capa por encima de la base de datos de caché: get(url, ttlMs) devuelve el cuerpo si sigue siendo joven, put(url, body) lo guarda y poda por tamaño (más de 500 entradas → tira las 100 más viejas), y pruneExpired() tira lo caducado una vez por arranque. TTL por defecto: una semana (los metadatos de un disco publicado no cambian de un día para otro). Nunca lanza: fallar al leer una caché no puede tumbar una búsqueda que sin ella funcionaría igual.

Se inicializa desde UltiMusicApp y no desde MainActivity para que no pueda darse el caso de «todavía no inicializada»: si hubiera que acordarse de llamarla desde cada sitio, el día que se olvidara la caché se desactivaría en silencio.

data/remote/ApiRateLimit.kt · ApiUnauthorized.ktexcepciones tipadas + RateLimitGuard

ApiRateLimitException(service, retryAfterMs) y ApiUnauthorizedException(service, error) son IOException (así el runCatching de quien llama las sigue capturando igual) pero con tipo propio, para poder decirle al usuario «espera N segundos» o «tu token ya no vale» en vez de un «no se ha podido buscar» que no es verdad.

RateLimitGuard hay uno por servicio. Tras un 429 corta las siguientes peticiones sin abrir la conexión durante el castigo: lo que diga Retry-After o, si no lo manda, un backoff que se dobla con cada 429 seguido (1 min → máx. 15 min) y se borra en cuanto una petición sale bien. Sin esto un límite temporal se convierte en un bloqueo largo.

invalidToken distingue las dos causas de un 401 (RFC 6750): invalid_token (hay que borrar el guardado y avisar) frente a una cabecera mal formada (borrarlo destruiría un token válido). Ante la duda —sin cabecera WWW-Authenticate— se asume token inválido, porque la cabecera ya sale garantizada limpia (ver GeniusTokenStore).

data/remote/GeniusTokenStore.kt · YouTubeApiKeyStore.ktobjects · credenciales que pone cada usuario

El token de Genius y la clave de la YouTube Data API los pone cada usuario (desde GeniusTokenDialogFragment y YouTubeApiKeyDialogFragment) y se guardan en SharedPreferences. Antes viajaban en el APK vía BuildConfig, con dos problemas que no se arreglan con código: la cuota va por credencial, así que todos los usuarios compartían una sola; y un token incrustado se extrae con strings en un minuto, y la cuenta sancionada sería la del desarrollador.

  • token / key — el del usuario o, si no hay, el de local.properties solo en compilaciones de depuración. Se corta por dos sitios (build.gradle.kts lo declara vacío en release, y aquí se exige BuildConfig.DEBUG): una credencial incrustada en el APK publicado haría que el diálogo de configuración no le saliera a nadie.
  • sanitize descarta lo que no tenga forma de credencial ([A-Za-z0-9_-] con una longitud razonable). Es lo que garantiza que la cabecera Authorization nunca salga mal formada: un salto de línea la partiría en dos.
  • shouldOfferSetup (ni hay credencial ni el usuario la ha rechazado), save, decline (botón «Salir»: no se vuelve a insistir), looksLikeToken/Key y, en Genius, clear() cuando Genius responde que el token ya no vale.

data/remote/ItunesApi.ktobject · cliente de la iTunes Search API

La iTunes Search API es el buscador público del catálogo de la tienda de Apple, accesible por HTTP sin clave ni cuenta. Este archivo le pregunta por candidatos con los que rellenar el editor, a partir de título+artista (canción) o álbum+artista (álbum). Es un object sin estado.

iTunes · la tienda (storefront) manda

iTunes es una tienda por país, y cada petición consulta una (parámetro country). La tienda decide qué hay publicado y en qué idioma vienen títulos, artistas y géneros. UltiMusic usa la región del dispositivo y cae a US —la de catálogo más amplio— si el idioma configurado no lleva región.

Qué ofrece

  • searchSongs(title, artist, offset) — GET /search?entity=song. Cada resultado YA es «esta grabación dentro de esta publicación», justo la unidad de MetadataSuggestion; solo hay que deduplicar por collectionId.
  • searchAlbums(album, artist, offset) — GET /search?entity=album.
  • fullResCoverUrl(url) — cambia el segmento de tamaño de la URL (…/100x100bb.jpg) para pedir la misma carátula a máxima resolución.

Catálogo por artista

En la primera página, antes que el texto libre, se prueba el catálogo real de los artistas buscados: resolveArtistId busca el artista (entity=musicArtist, nombre exacto normalizado) y artistCatalog pide hasta 200 publicaciones con GET /lookup?id=…, quedándose con las que casan en título. Van delante en la lista combinada para ganar el hueco de su collectionId. Lo motivó «St. Anger» de Metallica: por texto libre no aparecía nunca, aunque sí está en su catálogo. /lookup no pagina, de ahí que solo se use en la primera página.

Los buscadores mandan título y artista en el mismo term, y si no encuentran nada repiten solo con el título: iTunes exige que todas las palabras casen, así que un artista acreditado con otro nombre vaciaría la búsqueda. Cada página se reordena además por coincidencia real (artista y título normalizados), de forma estable: iTunes ordena por popularidad. El título de cada candidato lleva su tipo (collectionNameWithType) para distinguir un single de su álbum de un vistazo.

Apple recomienda no pasar de unas 20 peticiones por minuto; el único sitio que puede encadenar varias es el scroll infinito, y ahí el respiro vive en MetadataSuggestionsViewModel. Lo que iTunes no da es el país de publicación ni los tipos secundarios (directo, recopilatorio…): por eso la etiqueta de cada fila se queda en Álbum / Single / EP.

data/remote/GeniusApi.ktobject · cliente de Genius (opcional)

Genius es una base de datos colaborativa centrada en la autoría de las canciones. No sustituye a iTunes, lo completa: la lista de candidatos la manda siempre iTunes (una fila por publicación); Genius da un único álbum por canción.

  • detailsFor(title, artist) — para el candidato que el usuario elige: busca la canción (/search) y pide su ficha (/songs/:id). Aporta primary_artist + featured_artists (artistas bien separados, cosa que la cadena única de iTunes no permite sin romper a «Simon & Garfunkel») y producer_artists (los productores).
  • songArtFor(title, artist) — la carátula de la canción (song_art_image_url), no la del disco. Viene en la propia búsqueda, así que se pide fila a fila según se enseñan en la lista de sugerencias.
  • validateToken(candidate) — comprueba un token recién pegado con una petición de verdad (sin caché, que va por URL y no incluye el token; sin tocar el castigo del anterior; con timeout corto porque hay alguien mirando).

Genius también da la canción original de un remix y el enlace del videoclip, pero el autorrelleno ya no los ofrece: se equivocaba demasiado. Siguen siendo editables a mano. Todo fallo se traduce en null (el enriquecimiento nunca empeora lo de iTunes), y el candidato solo se acepta si casa en título y artista con el elegido (ver TextMatch). Excepciones: ApiRateLimitException se propaga para avisar, y un 401 con token inválido borra el guardado (GeniusTokenStore.clear()) y abre GeniusApiErrorDialogFragment. Genius no sirve letras por su API: esas siguen viniendo de lrclib.net.

data/remote/LrcLibApi.ktobject · cliente de lrclib.net

lrclib.net es una base de datos libre y colaborativa de letras sincronizadas (formato «LRC», [mm:ss.xx]texto), lo que permite ir resaltando la línea que toca mientras suena la canción. Es pública y gratuita, sin clave, y no obliga a borrar ni refrescar lo guardado.

Dos variantes de search: por title+artist (GET /api/search?track_name=…&artist_name=…) y por texto libre (q=…), para cuando el usuario reescribe la búsqueda. Devuelve todos los candidatos de una vez y la respuesta YA trae la letra completa de cada uno.

Descarta las pistas instrumental y las que no traen letra. Marca cada candidato que dure lo mismo que el archivo (durationMatches, ±1 s porque lrclib.net guarda segundos redondeados) y ordena, de forma estable, primero las sincronizadas y, dentro de cada grupo, las que coinciden en duración: son las que se sincronizaron contra ESA grabación.

Un ViewModel vive mientras vive la Activity; un Service en primer plano (con notificación) es la pieza que el sistema respeta y no mata por presión de memoria. android:stopWithTask="false" evita que cerrar la app desde «recientes» se lo lleve si está sonando algo.

Envuelve el ExoPlayer en una MediaSession y regala la notificación MediaStyle (operable desde la pantalla de bloqueo), el foco de audio, pausarse al desenchufar los auriculares y los botones Bluetooth, sin una línea de código propia.

La cola

  • Cola suelta (play(song)): al agotarse se alarga con una canción al azar de toda la biblioteca. playFromGenre(song, genre) es igual pero anclada a un género: la canción al azar sale de ese género.
  • Colección (playCollection): álbum, artista, género, etiqueta o Lista. Para una Lista, la cola se construye con el sistema «sin repeticiones» (buildListaQueue): lo que ya sonó esta vuelta (según PlaylistHistoryStore) va delante de la canción tocada, en el orden en que sonó; lo pendiente va detrás, en el orden de la lista o barajado si la Lista tiene el aleatorio activado (PlaylistShuffleStore). setListaShuffle y resetListaHistory reordenan al instante lo que queda por sonar si esa Lista es la que suena, sin cortar la canción actual.
  • selectFromQueue(position) — tocar una fila cualquiera de la cola del iPod. Si es una Lista y la fila ya sonó, reconstruye la cola para respetar la elección; si no, se comporta como jumpTo y no destruye un reordenado manual.
  • removeFromQueue(ids) — quita las marcadas, nunca la que suena.
  • skipToPrevious() — pasados unos segundos de canción, reinicia la actual en vez de ir a la anterior, como el resto de reproductores.
  • loadCurrent() valida la ruta con LibraryRepository.resolvePlayablePath(), construye el MediaItem con SafStorage.uriForDomainPath (docPath o URI suelto → content://), graba el historial de la Lista y abre una sesión del PlayTracker. Es el único punto por el que pasa cualquier cambio de canción actual.

Ciclo de vida

  • by lazy en library, las preferencias y player: un Service no tiene Context válido al construirse, solo a partir de onCreate().
  • serviceScope con Dispatchers.Main.immediate: el ExoPlayer solo se puede tocar desde el hilo de su Looper.
  • onCreate() sondea el ecualizador, restaura ajustes y cola, construye la MediaSession (con QueueAwarePlayer, CoverBitmapLoader y un PendingIntent a MainActivity), registra UltiMusicNotificationProvider y pide el vigilante de la fonoteca (startWatchingLibraryChanges(PLAYBACK_SERVICE)), para que una canción nueva aparezca aunque la Activity esté en segundo plano.
  • Un Player.Listener informa al PlayTracker de cada cambio play/pausa y de cada salto explícito (onPositionDiscontinuity con motivo SEEK).
  • onDestroy() hace playTracker.flush() (salva la última escucha), suelta el vigilante, guarda el estado y libera efectos, sesión y reproductor.
  • findSong(id), buildMediaItem(song, path) (con MediaMetadata y un URI de carátula inventado, ultimusic://cover/<id>) e instanceFlow (el puente con PlayerViewModel).
Diseño · QueueAwarePlayer, por qué hace falta envolver el ExoPlayer

UltiMusic carga una canción cada vez (setMediaItem, no setMediaItems) y decide la siguiente con lógica propia. Pero el botón «siguiente» de la notificación, la pantalla de bloqueo o unos auriculares Bluetooth lo maneja Media3 directamente sobre el Player de la sesión. QueueAwarePlayer (un ForwardingPlayer) sobreescribe seekToNext/Previous(MediaItem) y hasNext/PreviousMediaItem() para usar la cola real, y tanto getAvailableCommands() como isCommandAvailable(), porque el segundo no se calcula a partir del primero.

playback/PlayTracker.ktclase · cuenta las escuchas para Recount

Máquina de estados de una sola sesión: se abre (start(song)) cuando una canción pasa a ser la actual, se pausa y se reanuda con la reproducción (setPlaying) y se cierra cuando llega otra o muere el servicio (flush). Al cerrarse, si la sesión llegó al 50% de la duración, anota una fila en play_events con RecountRepository.record.

  • Mide tiempo sonado, no posición: saltar al 90% y dejar que termine no cuenta; pausar y volver no regala nada; rebobinar y volver a oír sí suma (por eso playedMs puede superar la duración).
  • Un solo salto hacia delante (onSeek) descalifica la sesión entera, aunque luego se escuche el resto. El salto que coloca la canción en su posición guardada al reanudar no cuenta, porque llega antes de que haya sonado nada.
  • Escuchar la misma canción dos veces seguidas son dos escuchas.

El reloj es SystemClock.elapsedRealtime, que nadie puede mover: con el reloj de pared, cambiar la hora a mano sumaría el salto entero al tiempo escuchado. currentTimeMillis solo se usa para el sello de inicio (que decide el año). Todo es @Synchronized (los avisos llegan por el hilo principal, pero flush también desde onDestroy) y usa un scope propio, no el del Service: onDestroy cancela ese, y la última escucha se perdería.

El botón de la derecha de la cabecera cambia la pantalla por el videoclip de la canción. Políticas de YouTube · solo suena una cosa a la vez

Antes el vídeo era una capa muda que seguía al audio local. Ya no: las políticas de desarrollador de la API de YouTube prohíben poner una pista de audio distinta a su vídeo (III.I.7), modificar o bloquear funciones del reproductor (III.I.6) y un reproductor que suene sin estar a la vista (III.I.9). Por eso ahora:

  • Al entrar (startVideo) se congela el audio local y el vídeo arranca desde esa misma posición (más el desplazamiento) con su propio sonido (setAudible(true)).
  • Los mandos del iPod (play/pausa y barra) se esconden: los lleva el reproductor real de YouTube, con sus controles visibles (controls(1)), subtítulos incluidos.
  • Al salir (exitVideo) el vídeo queda mudo y en pausa, y la posición se traduce de vuelta al audio local (localPositionMs()), que se reanuda solo si el vídeo seguía sonando. Si mientras tanto cambió la canción, no se traspasa nada.
  • onPause sale del modo vídeo: en cuanto la ventana deja de estar a la vista, el vídeo no puede seguir sonando.
  • La pantalla pasa de cuadrada a 16:9 (animateAspectRatio) y vuelve a cuadrada al salir. topBox y queueList se recortan cada uno con su propio ViewOutlineProvider de esquinas redondeadas.
  • Debajo aparece la caja de desplazamiento (videoOffsetBox): una ValueRuler en muescas de 100 ms más una cifra editable a mano en ms exactos. Arrastrar o escribir previsualiza al instante (VideoScreenController.setOffset); se guarda en Room (setVideoOffsetMs) solo al soltar la regla o confirmar la cifra. Antes vivía en un diálogo de «ajustes del reproductor de vídeo» aparte; ese diálogo ya no existe.
  • Si el vídeo falla, se sale solo del modo vídeo. Durante el modo vídeo la letra sigue resaltándose con la posición del vídeo (onPositionTick).
Por qué no hay búsqueda automática del vídeo

La cuota de la API de YouTube es por proyecto (10.000 unidades diarias, y cada search.list cuesta 100: unas 100 búsquedas al día para todos los usuarios), y lo obtenido de la API hay que borrarlo o refrescarlo cada 30 días. Un enlace elegido por el usuario no tiene ninguna de las dos limitaciones y además acierta más. Encaja con la filosofía del proyecto: el usuario controla el dato.

Los errores del reproductor: dos familias distintas

Errores de la API, que llegan a onError: identificador mal formado (2), HTML5 (5), vídeo no encontrado (100), reproducción embebida desactivada por el autor (101/150, habitual en videoclips de discográficas) y falta de referer (153). Y errores internos que se pintan dentro del WebView («Este vídeo no está disponible», familia 152) y no pasan por onError. La causa típica del 152 es la identidad del incrustador: desde julio de 2025 YouTube exige un origin, y por eso la app fija como mínimo la versión 13.0.0 de la librería. Aun así puede aparecer en vídeos con restricciones de región.

Por qué el WebView no lleva setLayerType(LAYER_TYPE_SOFTWARE)

Un WebView con vídeo promociona el fotograma a una capa compuesta fuera del árbol de vistas, así que queda por encima de todo. Forzar capa de software lo devolvería al árbol normal, pero deja el vídeo en negro: Chromium no puede presentar un fotograma decodificado por hardware por esa vía. Por lo mismo, el redondeado lo hace el contenedor (topBox) y no el propio reproductor.

¿Se puede saltar el límite de volumen de Android?

No del todo, y conviene tener claro qué se puede y qué no:

  • El 100 % del volumen del sistema es el máximo de la escala de Android. Una aplicación normal no puede subirlo por encima: ese tope lo fija el sistema y el driver de audio.
  • El aviso de «volumen alto» que sale con auriculares en los móviles europeos (normativa EN 50332) también es del sistema. Ninguna aplicación puede quitarlo.
  • Lo que sí puede hacer una aplicación es amplificar su propio sonido antes de que salga, para que dentro de ese 100 % suene más fuerte de lo que sonaría sin tocarlo. Eso es exactamente lo que hace el amplificador de UltiMusic.

La herramienta es LoudnessEnhancer, un efecto de audio de Android que se engancha a la sesión de audio de un reproductor y le añade ganancia con compresión de rango dinámico (comprime los picos, para que subir el volumen no lo rompa en distorsión). No hace falta root ni ningún permiso peligroso: solo MODIFY_AUDIO_SETTINGS, que es un permiso normal y el sistema concede al instalar.

ui/settings/SettingsDialogFragment.ktDialogFragment · la pantalla de ajustes

Es un DialogFragment a pantalla completa con Theme.UltiMusic.FullScreenDialog, el mismo patrón que el editor: se abre encima de la principal sin cambiar de Activity, así que la música no se corta y «atrás» devuelve a la pestaña en la que se estaba.

Aquí no vive el estado. Lo de audio (amplificador, ecualizador) lo guarda PlaybackService, que es quien tiene el reproductor y aplica de verdad los efectos; el fragmento habla con él a través de PlayerViewModel (activityViewModels(), el mismo que el mini-reproductor). Estructura / flujo

  • Título y subtexto del ajuste: «Amplificador de volumen» / «Permite que el sonido suene más fuerte».
  • El mando, que cambia según el límite:
    • Con el límite puesto (lo normal), un Slider de Material del 100 % al 150 %, con stepSize="1" para que solo dé valores enteros.
    • Con el límite quitado, el slider se sustituye por un ValueRuler, una cinta métrica que se arrastra. El motivo del cambio es que un slider dibuja su recorrido, así que necesita un máximo cercano; con el rango que se abre al quitar el límite (hasta BOOST_MAX_PERCENT), un píxel de slider valdría decenas de unidades.
    • Los dos viven apilados en un FrameLayout y solo uno está visible a la vez.
  • El número exacto, a la derecha del todo, en un EditText numérico: se puede teclear el valor en vez de buscarlo con el dedo. Su maxLength va emparejado con BOOST_MAX_PERCENT: si la caja admitiera más dígitos de los que el tope permite, el texto se truncaría por su cuenta y enseñaría un número distinto del que está aplicado.
  • La casilla «Desactivar límite», debajo. Solo funciona si el sonido no va a un oído. Con auriculares puestos sale un toast explicándolo y la casilla vuelve sola a su sitio; con un altavoz Bluetooth o el coche sí se puede. Si hay un aparato Bluetooth que no se puede identificar por falta de permiso, en vez de rechazar sin más se le pide el permiso al usuario (registerForActivityResult) y, si lo concede, se reintenta solo. Ese registro va como campo de la clase porque registerForActivityResult exige llamarlo antes de que el fragmento llegue a STARTED: hacerlo desde el clic de la casilla ya sería tarde y reventaría.
El problema de los tres controles que muestran lo mismo

Slider, regla y caja de texto enseñan el mismo número, así que al mover uno hay que actualizar los otros dos. Hecho sin cuidado, eso es un bucle infinito: el slider avisa de que ha cambiado → se escribe en la caja → la caja avisa de que ha cambiado → se mueve el slider → …

La solución es una bandera, updatingUi. Mientras vale true, los avisos de los controles se ignoran: significa «este cambio lo he provocado yo al repintar, no el usuario». Es el mismo truco que usa el editor de metadatos y una pieza clásica de cualquier interfaz con controles espejados.

El slider tiene además su propio mecanismo para lo mismo, el parámetro fromUser de addOnChangeListener, que distingue moverlo con el dedo de moverlo por código.

Detalle de la caja de texto: mientras se teclea «120» se pasa por «1» y por «12». Corregir eso al vuelo al mínimo sería pelearse con el usuario, así que solo se aplica lo escrito cuando ya es un número válido (≥ 100), y lo que quede fuera de rango se cuadra al terminar — al pulsar «hecho» en el teclado o al perder el foco.

Los mandos se tiñen con el color de la canción que suena, igual que las pestañas y el mini-reproductor (ver DynamicColor). Lo mismo hacen los tres títulos de sección («Amplificador de volumen», «Lista gris», «Ecualizador», antes amarillo fijo del XML) y el interruptor maestro del ecualizador (eqSwitch): todos se repintan en el mismo accentColor.collect. Los switches de cada fila de la lista gris los tiñe GreylistAdapter por su cuenta, ver ahí.

Las dos casillas (noLimitCheck, additionalOptionsCheck) llevan app:rippleColor="@color/um_ripple_white" fijo en el XML (MaterialCheckBox.setRippleColor existe pero es private, así que no se puede pisar desde código), y eqSwitch lleva android:theme="@style/ThemeOverlay.UltiMusic.SwitchRippleWhite", también en el XML. Por defecto una casilla pulsa en el amarillo fijo del tema al marcarla, y el ripple del interruptor sale amarillo al apagarlo (no al encenderlo); ver el caso de MaterialSwitch en el «Qué queda fuera» de AccentTint, que explica por qué ninguno de los dos sigue el patrón habitual de AccentTint/DynamicColor en código.

La sección «Ecualizador»

En «Ajustes auditivos», debajo del amplificador, un interruptor maestro (MaterialSwitch) con un desplegable de presets al lado, botones para guardar/borrar preset, una ganancia maestra y un slider vertical por cada banda del ecualizador. Este estado tampoco vive en el fragmento sino en PlaybackService, igual que el amplificador (es audio, no biblioteca).

  • El número de bandas y su rango los decide el dispositivo, no la aplicación (ver el recuadro de abajo), así que los sliders verticales no están fijos en el XML: setupEqualizer() infla un item_eq_band.xml por cada EqBand de playerViewModel.eqBands, le pone su valueFrom/valueTo en milibelios y su etiqueta de frecuencia formateada («230 Hz», «1.2 kHz»).
  • Si el dispositivo no tiene el efecto (eqBands vacía), la sección entera se deshabilita y aparece un aviso, en vez de dejar sliders que no hacen nada. Si algún efecto de los de abajo no está soportado en este dispositivo (bassBoostSupported, virtualizerSupported, reverbSupported, dynamicsProcessingSupported), solo se deshabilita ese control suelto con su propio aviso.
  • Con el interruptor apagado, los sliders de bandas, la ganancia maestra y los cuatro controles de «Opciones adicionales» se ven pero no se pueden tocar (isEnabled = false), en vez de ocultarse: así no se pierde de vista qué valores hay puestos. El desplegable de presets y sus botones quedan al margen de esto: elegir o guardar un preset no necesita que el ecualizador esté sonando.
  • «Restablecer» pone todas las bandas y los cuatro refuerzos a cero, la ganancia maestra a su punto neutro (50 %), y deja seleccionado el preset «Plano», sin tocar si el interruptor está encendido o apagado.
El desplegable de presets: predefinidos, «Usuario», guardados

El desplegable (eqPresetsSpinner) lista, en este orden, los presets predefinidos (Plano, Rock, Pop, Jazz, Clásica, Heavy Metal, Hip-Hop, Dance), la entrada fija «Usuario» y, al final, los presets guardados por el usuario — el orden lo pidió expresamente el encargo. El amplificador por dentro

La lógica de audio no está en el fragmento sino en PlaybackService, que es donde vive el ExoPlayer (PlayerViewModel solo reenvía). Lo que hay allí:

  • loudnessEnhancer — el efecto, enganchado a player.audioSessionId. Es nullable y se crea dentro de un try/catch porque hay móviles y emuladores sin este efecto: si falla, la aplicación sigue funcionando exactamente igual, solo que sin amplificar. Además solo existe mientras hace falta: applyBoost() lo crea la primera vez que el amplificador sube de 100 % y lo suelta (release()) en cuanto vuelve a 100 %, en vez de crearlo una vez en init y dejarlo enganchado (apagado) para siempre — ver el recuadro «Por qué los efectos se crean bajo demanda» más abajo.
  • volumeBoost y limitDisabled — el estado, en StateFlow, persistido en unas SharedPreferences propias (audio_settings), aparte de las de la reproducción porque son cosas distintas.
  • setVolumeBoost(percent) — recorta el valor siempre, venga de donde venga: nunca por debajo de 100 y, con el límite puesto, nunca por encima de 150. Así el tope no depende de que la interfaz se acuerde de respetarlo.
  • setLimitDisabled(disabled) — devuelve por qué no se ha podido quitar el límite: Check.NONE significa que sí se ha aplicado, y cualquier otro valor que se ha rechazado. Devolver el motivo y no un simple false es lo que permite a la pantalla de ajustes reaccionar distinto ante «hay auriculares» y ante «hay un Bluetooth que no puedo identificar». Al volver a poner el límite, recorta la amplificación si se había pasado.
  • applyBoost() — traduce el porcentaje y se lo da al efecto.
De porcentaje a milibelios: amplitud contra percepción

LoudnessEnhancer no trabaja en porcentajes sino en milibelios (mB), o sea décimas de decibelio. La conversión merece explicación porque la respuesta «obvia» está mal, y de hecho la primera versión de esto la tenía mal.

Un decibelio mide amplitud, y multiplicar la amplitud de la onda por un factor son 20 · log10(factor) decibelios. Con esa cuenta, el 150 % serían 3,5 dB. Es la fórmula correcta… para la física de la onda.

El problema es que el oído no percibe la amplitud, sino algo mucho más comprimido. La regla estándar de psicoacústica (la escala de sonios) dice que hacen falta +10 dB para que algo suene el doble de fuerte, no los ~6 dB que doblan la amplitud. Así que aquellos 3,5 dB, que sobre el papel eran «una vez y media», el oído los registraba como un 10 % largo: técnicamente impecable y prácticamente inútil.

Como el número que ve el usuario tiene que significar lo que oye, se usa la escala de la percepción, que es la inversa de la regla de los sonios (percepción = 2^(dB/10)):

dB = 10 · log2(factor)

La regla de «+10 dB = el doble» es una aproximación, no una ley exacta: vale bien a volúmenes normales y con sonido de banda ancha (la música lo es), pero depende algo del nivel y del contenido. Aun así es el estándar de la industria y se acerca muchísimo más a lo que uno oye que la fórmula de la amplitud.

La cuenta vive en boostGainDb(percent), una función internal de nivel superior en PlayerViewModel.kt, que usa también el Service.

Diseño · por qué los decibelios no se le enseñan al usuario

Hubo una versión que escribía «+5,9 dB sobre el volumen normal» debajo del mando. Se quitó, y el motivo merece quedar escrito porque es fácil querer volver a ponerlo.

Ese número son los decibelios añadidos, no el volumen que llega al oído. El absoluto la app no puede saberlo: depende del volumen del sistema, de la sensibilidad de los auriculares y hasta del contenido de la canción. Y un usuario sin ningún punto de referencia no puede hacer nada con «+5,9 dB»: no le dice si está en terreno seguro ni cuánto le queda por subir. Como dato aislado no informa, solo decora — y peor aún, se puede confundir con el nivel absoluto y dar una falsa sensación de seguridad.

Con el amplificador al 100 % el efecto se suelta del todo (ver el recuadro de abajo) en vez de dejarlo creado con ganancia 0: quien no lo use no tiene ningún procesado de audio de por medio, y tampoco ocupa sitio en el procesador de efectos del sistema.

Por qué los efectos se crean bajo demanda (y no una vez en init)

La primera versión de esto creaba los seis efectos (LoudnessEnhancer y los cinco del ecualizador) una vez en init y los dejaba enganchados a la sesión de audio toda la vida de la aplicación, apagándolos con enabled = false cuando el usuario no los usaba. El fallo: un AudioEffect enganchado ocupa un hueco del procesador de efectos del sistema aunque esté apagado, y ese procesador es un recurso compartido con el resto de aplicaciones del móvil, no algo privado de UltiMusic. Con los seis siempre enganchados —los usara el usuario o no— UltiMusic ocupaba de más ese recurso compartido; en algunos dispositivos, tener otra aplicación de audio abierta a la vez (YouTube, Instagram…) agotaba el hueco compartido y dejaba **sin sonido a las dos aplicaciones**, no solo a UltiMusic, hasta que se cerraba una de las dos.

La solución es crear cada efecto solo mientras está activo y soltarlo (release()) en cuanto se apaga, en vez de crearlo una vez y limitarse a alternar enabled:

  • applyBoost() crea loudnessEnhancer la primera vez que el amplificador sube de 100 % y lo suelta al volver a 100 %.
  • ensureEqEffects() crea los cinco efectos del ecualizador cuando se enciende eqEnabled; releaseEqEffects() los suelta al apagarlo. Las llama applyEq(), que es quien decide si tocan crearse o soltarse.
  • Lo único que se sigue calculando una vez, en onCreate, es probeEqCapabilities(): crea cada efecto un instante para preguntarle sus límites (número de bandas, rangos, si soporta fuerza variable…) y lo suelta enseguida, antes de que la pantalla de ajustes exista siquiera. No hace falta dejarlo enganchado solo para saber sus límites — esos no cambian.

Esto no cambia nada para quien no usa el amplificador ni el ecualizador: por defecto (100 %, ecualizador apagado) UltiMusic no tiene ningún efecto de audio enganchado a su sesión.

La protección de los auriculares

Quitar el límite solo se permite cuando el sonido sale al aire, porque directo al oído puede dañarlo de verdad. Ojo al matiz: lo que descalifica no es «tener algo conectado» sino que ese algo vaya en la oreja. Con un altavoz Bluetooth o el coche sí se puede quitar; distinguirlos es trabajo de Headphones.kt, que devuelve tres respuestas en vez de un sí/no.

Comprobarlo una vez, al marcar la casilla, no basta: alguien podría subir al 400 % por altavoz y enchufar los cascos después, con la música ya sonando. Por eso el Service registra un AudioDeviceCallback en el AudioManager, que avisa cada vez que aparece una salida de audio nueva. Si aparece un auricular con el límite quitado, el límite se repone solo y se emite limitForcedByHeadphones para que la pantalla de ajustes lo cuente, si está abierta. La vigilancia vive en el Service y no en el fragmento justamente para que funcione esté esa pantalla abierta o cerrada.

En esa vigilancia, un Bluetooth sin identificar cuenta como auriculares: puede saltar con la app en segundo plano, donde no hay a quién pedirle ningún permiso, así que se protege el oído. En la pantalla de ajustes, en cambio, sí se le ofrece al usuario conceder el permiso y se reintenta.

El callback se da de baja en onDestroy(), junto con el release() del efecto: los efectos de audio son un recurso escaso del sistema y, si no se sueltan, se acaban agotando.

El ecualizador por dentro

Tampoco está en el fragmento sino en PlaybackService, junto al amplificador y enganchado a la misma sesión de audio del ExoPlayer — solo mientras está activado, ver «Por qué los efectos se crean bajo demanda» arriba. Son cinco efectos más de android.media.audiofx, todos nullable y creados dentro de un try/catch por el mismo motivo que LoudnessEnhancer: hay móviles y emuladores sin ellos.

  • Equalizer — sube o baja el volumen de bandas de frecuencia concretas, en milibelios. numberOfBands, bandLevelRange y getCenterFreq(banda) los decide el propio dispositivo, no son un número fijo de la aplicación: por eso eqBands (una lista de EqBand(centerFreqHz, minLevelMb, maxLevelMb)) se calcula una única vez en probeEqCapabilities() (llamada desde onCreate) leyendo esas propiedades de un Equalizer temporal, y es lo que usa la pantalla de ajustes para construir sus sliders verticales en código.
  • BassBoost («refuerzo de graves») y Virtualizer («sonido envolvente», ensancha el estéreo simulando altavoces separados) no tienen bandas: cada uno tiene una única fuerza de 0 a 1000 (setStrength()). El Service la expone como porcentaje (0-100), igual que el resto de la aplicación, y multiplica por 10 al aplicarla. Si el dispositivo no admite variar esa fuerza (getStrengthSupported() == false), bassBoostSupported/virtualizerSupported quedan en false y la pantalla de ajustes deshabilita ese slider en concreto.
  • PresetReverb («reverberación») simula el eco de un espacio (habitación, sala, auditorio…). A diferencia de los dos anteriores no tiene una fuerza continua: solo admite elegir una sala entre sus siete constantes (PRESET_NONE..PRESET_PLATE), así que reverbPreset guarda un índice (0 = «Ninguno», apaga el efecto) sobre reverbPresetNames, una lista de nombres escrita a mano en PlaybackService.kt (son nombres de una API de Android, no texto traducible de la interfaz — igual criterio que predefinedPresetNames).
  • DynamicsProcessing («compresor de rango dinámico») sube el sonido flojo y baja el fuerte en tiempo real, algo que ningún ajuste estático (bandas, refuerzos, ganancia maestra) puede hacer. Es el más complejo de los cinco: solo existe desde Android 9 (API 28), así que se comprueba Build.VERSION.SDK_INT antes de crearlo, y no viene con una configuración por defecto útil — hay que construirlo con un DynamicsProcessing.Config que le dice de antemano cuántos canales tiene (2, a capón: el audio de ExoPlayer es casi siempre estéreo y no merece la pena leer el formato real) y qué «etapas» quiere usar (aquí solo el compresor multibanda, con una única banda que cubre todo el espectro, más un limitador de seguridad para que la compresión no sature). dynamicsStrength (0-100 %) se traduce a los parámetros de esa banda en buildCompressorBand(): a más fuerza, el umbral baja (de −10 a −30 dB) y la razón sube (de 1:1, sin comprimir, a 4:1), con una ganancia de compensación de hasta +6 dB.
  • eqEnabled — un único interruptor para los cinco efectos: no tiene sentido tener el ecualizador «a medias». setEqEnabled(enabled) cambia eqEnabled y llama a applyEq(), que crea los cinco efectos (ensureEqEffects()) o los suelta (releaseEqEffects()) según toque.
  • eqBandLevels, bassBoostStrength, virtualizerStrength, reverbPreset, dynamicsStrength, eqPreGain — el estado, en StateFlow, persistido en las mismas SharedPreferences del amplificador (audio_settings): una banda por clave (eq_band_0, eq_band_1...) más eq_enabled, bass_boost, virtualizer, reverb_preset, dynamics_strength y eq_pre_gain.
  • setEqBandLevel(banda, mB), setBassBoostStrength(%), setVirtualizerStrength(%), setReverbPreset(índice), setDynamicsStrength(%), setEqPreGain(%) — tocan solo el control que ha cambiado (y llaman a markEqAsModified(), ver abajo). applyEq(), en cambio, aplica todo de golpe a los cinco efectos: la usan el arranque de la aplicación, el interruptor maestro y resetEqualizer() (todas las bandas y los cuatro refuerzos a cero, la ganancia maestra a su punto neutro del 50 %).

EqPreset (ver abajo) sigue empaquetando solo bandas, refuerzo de graves y envolvente, no reverberación ni compresor: aplicar un preset (de fábrica o guardado) no toca esos dos, se quedan como estuvieran. Es una limitación consciente para no rehacer los ocho presets de fábrica al añadirlos; si se quiere que formen parte del preset, hay que extender EqPreset, createPredefinedPresets() y la persistencia de userPresets.

La ganancia maestra: un desplazamiento que no se guarda por banda

eqPreGain (0-100 %) no es una banda más: es un desplazamiento en milibelios que se suma a las eqBandLevels guardadas al mandarlas de verdad al hardware, en vez de guardarse banda por banda. Es bipolar: preGainMb() = (eqPreGain − 50) × 20, así que el 50 % (su valor por defecto) es el punto neutro (0 mB, sin efecto), 0 % son −1000 mB (−10 dB) y 100 % son +1000 mB (+10 dB) — el control sirve tanto para subir como para bajar el conjunto, no solo para subirlo. effectiveBandLevel(índice, nivel) es quien hace esa suma y recorta el resultado al rango de esa banda concreta (eqBands[índice]), y la usan tanto applyEq() como setEqBandLevel() para que las dos vías de aplicar una banda den siempre el mismo resultado. Así, mover la ganancia maestra desplaza toda la curva del ecualizador sin tocar lo que marca cada slider de banda — y no hace falta que esos sliders se muevan para reflejarlo, porque su posición ya es solo un indicador relativo dentro del rango de su propia banda (no muestran ningún número). Útil para compensar cuando se han subido muchas bandas a la vez y el conjunto empieza a saturar, o para bajar el ecualizador entero sin tocar banda por banda.

Presets: predefinidos, guardados por el usuario y el aviso «Usuario»

EqPreset(nombre, bandLevels, bassBoostStrength, virtualizerStrength) es la clase de nivel superior (fuera de PlayerViewModel, en PlayerViewModel.kt) que empaqueta un preset entero. Hay dos fuentes:

  • predefinedPresets — ocho de fábrica (Plano, Rock, Pop, Jazz, Clásica, Heavy Metal, Hip-Hop, Dance), calculados en createPredefinedPresets() después de conocer eqBands: sus valores son proporciones fijas sobre bandas concretas (graves, agudos…) que se adaptan al número de bandas real del dispositivo. predefinedPresetNames expone solo los nombres, en orden, para que la pantalla de ajustes construya el desplegable sin conocer la clase EqPreset.
  • userPresets — los que el usuario ha guardado él mismo con saveUserPreset(nombre), persistidos en audio_settings con un contador (user_preset_count) y cuatro claves por preset (nombre, niveles de banda unidos por comas, refuerzo de graves y envolvente). restoreUserPresets() los recompone en onCreate, descartando cualquiera cuyo número de bandas ya no cuadre con eqBands (por ejemplo, tras reinstalar en un dispositivo distinto).

applyPreset(nombre) busca primero en los predefinidos y luego en los del usuario, y recorta sus valores al rango real de este dispositivo antes de aplicarlos — un preset guardado en otro móvil, con otro rango de bandas, no debería poder mandar milibelios fuera de lo que este ecualizador admite. markEqAsModified() es la otra mitad del mecanismo: cualquier set* tocado a mano pone currentPresetName en «Usuario» (la constante USER_MODIFIED_PRESET_NAME) si no lo estaba ya, para que el desplegable refleje que hay cambios sin guardar. Elegir «Usuario» a mano en el desplegable no hace nada: applyPreset() no encuentra ningún preset con ese nombre y no toca nada.

Los efectos de audio se liberan en PlaybackService.onDestroy() junto con loudnessEnhancer y el propio player: son el mismo tipo de recurso escaso del sistema.

ui/common/ScrollbarDrag.ktfunción de extensión · barra de scroll propia (estilo Phonograph)

Función de extensión para RecyclerView: recycler.attachScrollbarDrag { posición -> letra }, o recycler.attachScrollbarDrag() a secas si no se quiere la burbuja de la letra. La barra de scroll nativa de Android tiene dos problemas para lo que se quería aquí: solo se deja agarrar con el dedo si la lista ya estaba en movimiento, y su grosor es proporcional a cuánto ocupa lo visible sobre el total (en una lista larga se vuelve un hilo). Por eso esta función no usa la barra nativa en absoluto — los XML de las listas afectadas llevan android:scrollbars="none" — y la sustituye por una vista propia, calcada del comportamiento de ~/Phonograph (que a su vez usa una librería de terceros para esto; aquí se reimplementó a mano para no añadir esa dependencia).

  • El "pulgar" (thumb) y la burbuja de letra (bubble) son dos View/TextView que la función crea por código y añade como hermanas del RecyclerView dentro de su ViewGroup padre (por eso los seis layouts que la usan meten el RecyclerView en un FrameLayout propio: hace falta un padre donde colgar estas dos vistas). Se posicionan con translationY, no con layout, porque se mueven en cada evento de scroll o de arrastre y recolocar con layout a esa frecuencia sería mucho más caro.
  • Tamaño fijo: el pulgar mide siempre 8dp de ancho por 48dp de alto (THUMB_WIDTH_DP / THUMB_HEIGHT_DP), sea cual sea la longitud de la lista — al contrario que la barra nativa, aquí no depende de la proporción visible/total. Los 8dp son a propósito los mismos que la pista del SeekBar de las canciones (res/drawable/seekbar_line.xml), para que las dos barras de la app tengan el mismo grosor.
  • La burbuja es un cuadrado fijo de 80dp (BUBBLE_SIZE_DP) con radio de esquina de media anchura, que es lo que la convierte en círculo perfecto; la letra va a 32sp. No es WRAP_CONTENT justamente para que su altura no cambie según la letra que toque, porque de esa altura depende la alineación con el pulgar.
  • Pulgar y burbuja comparten centro. Miden distinto (48dp y 80dp), así que si cada uno se colocara por su borde superior acabarían descuadrados en los extremos — que era el fallo que se veía: al llegar abajo del todo el círculo quedaba por debajo del pulgar, y arriba por encima. Ahora moveThumbTo(fracción) calcula un solo centro y de él cuelga a los dos (centro − altura/2 cada uno). El recorrido de ese centro deja de margen arriba y abajo media altura del más alto de los dos (halfTallestPx), así que ninguno se sale de la lista jamás.
  • No siempre visible: el pulgar nace con alpha = 0f y solo se enseña (showThumb()) al hacer scroll o al empezar a arrastrar; al cabo de un segundo sin actividad (AUTO_HIDE_DELAY_MS) se vuelve a ocultar solo, con un Handler que se reprograma (scheduleHide()) cada vez que hay actividad nueva.
  • Hitbox siempre activo: en el ACTION_DOWN se comprueba si el toque cae en la franja de la derecha (event.x >= width - hitboxWidthPx) sin mirar si el pulgar está visible en ese instante — por eso se puede empezar a arrastrar aunque la barra esté oculta. Sí se comprueba isScrollable() (que haya algo que desplazar): si la lista es tan corta que no hace falta scroll, el toque no se intercepta y llega normal a los elementos de debajo.
  • Se escucha con addOnItemTouchListener, no con setOnTouchListener (ver el recuadro de abajo): con lo segundo la barra solo agarraba si la lista ya venía moviéndose, que era exactamente el fallo que se arrastraba. Al quedarse el gesto también se llama a parent.requestDisallowInterceptTouchEvent(true), para que un temblor horizontal del dedo no le haga cambiar de pestaña al ViewPager2 que hay por encima.
  • Un toque suelto en la franja (sin arrastrar) no mueve la lista: el salto solo se calcula en los ACTION_MOVE. Lo que sí hace el DOWN es quedarse el gesto, así que ese toque tampoco reproduce la canción que hubiera debajo.
  • hitboxWidthDp (24dp por defecto) es deliberadamente más ancho que el pulgar visible (6dp): la zona donde "se nota" que hay barra para agarrar es mayor que lo que se ve, para no obligar a apuntar con precisión de píxel.
  • En ACTION_MOVE, la fracción vertical del toque (event.y / height) se traduce a una posición del adaptador (itemCount * fracción) y se mueve la lista con RecyclerView.scrollBy hasta el desplazamiento en píxeles que le corresponde, calculado con la misma estimación (computeVerticalScrollRange/Offset/Extent) que usa el pulgar, así que los dos nunca se desincronizan. Antes se usaba scrollToPositionWithOffset, que en la rejilla de Álbumes hacía que la lista se recolocara sola justo después de soltar: ese mecanismo de «ancla pendiente» no está pensado para encadenarse en cada frame; scrollBy es lo que usa el FastScroller nativo. Mientras se arrastra, ignoreScrollSync evita que el listener de scroll recoloque el pulgar a la vez.
  • Letra al arrastrar: en cada ACTION_MOVE se rellena la burbuja con sectionFor(posición) — la lambda que pasa cada pantalla — y se coloca pegada al pulgar (no a la altura exacta del dedo). sectionFor vive en cada fragment porque solo él sabe qué campo mostrar (el título de la canción/álbum, el nombre de la persona o de la playlist); la función sectionLetter(texto) de este mismo archivo hace el trabajo común (primera letra, en mayúscula, o "#" si no hay texto).

Es lo que hace el buscador, donde los resultados no están en orden alfabético sino agrupados por secciones y una letra no significaría nada. Como efecto secundario, sin burbuja el margen que la barra deja arriba y abajo (halfTallestPx, media altura del más alto de los dos) se reduce de 40dp a 24dp, así que el pulgar recorre algo más de pantalla.

Lo llaman todas las listas con barra propia —las pestañas, las fichas de detalle y de colección y el buscador— con playerViewModel.accentColor, el color de lo que suena, para que no haya una barra de un color en una pantalla y de otro en la siguiente.

Android · quién se queda el toque

Un ViewGroup (y un RecyclerView lo es) reparte cada toque en este orden: primero se pregunta a sí mismo si quiere quedárselo (onInterceptTouchEvent), y si dice que no, se lo pasa a sus hijos. El OnTouchListener del contenedor solo entra en juego al final, cuando ningún hijo se lo quedó.

Ahí estaba el fallo original de esta barra: escuchaba con setOnTouchListener, y como las filas son clicables (tocar una canción la reproduce), la fila se quedaba el ACTION_DOWN y la barra nunca se enteraba de que empezaba un arrastre. Solo funcionaba si la lista ya venía moviéndose, porque en ese caso el RecyclerView intercepta el toque de entrada (para frenar el scroll) y entonces sí llegaba al listener.

La solución es addOnItemTouchListener: es el mecanismo que ofrece el propio RecyclerView para mirar el toque antes que los hijos (se consulta dentro de su onInterceptTouchEvent). Si el listener devuelve true en el DOWN, el RecyclerView le adjudica el gesto entero — manda un ACTION_CANCEL a la fila que lo estuviera recibiendo, para que no se quede «pulsada» ni dispare su click — y el resto del gesto llega por su onTouchEvent.

Este comportamiento está cubierto por un test instrumentado (ScrollbarDragTest), que arrastra la barra con la lista parada y comprueba que la lista salta a donde toca.

ui/common/ValueRuler.ktView personalizada · regla de arrastre

Una cinta métrica horizontal: marcas y números que se mueven con el dedo bajo un indicador fijo en el centro. Lo que quede bajo el indicador es el valor elegido.

La usa la pantalla de ajustes como sustituto del slider cuando se desactiva el límite del amplificador, y también los desplazamientos de vídeo y de letra (en el modo vídeo del iPod y en el editor de metadatos), que no usan slider en ningún momento: el rango con sentido ahí ya es demasiado grande para uno. El motivo de fondo es que un slider dibuja su recorrido, así que necesita un máximo cercano para que el dedo tenga un rango cómodo; cuando el rango se dispara, un píxel pasaría a valer decenas de unidades y el slider se vuelve inservible. Una cinta que se arrastra no tiene ese problema: el recorrido es tan largo como haga falta.

Por qué una View propia y no un RecyclerView

La idea de «lista horizontal larguísima» en Android sería un RecyclerView horizontal, con su adaptador y su snap helper. Pero aquí no hay elementos que reciclar — solo rayas y números —, así que sale bastante más simple dibujarlo a mano: se guarda cuánto se ha arrastrado y se pintan solo las marcas que caen dentro de la pantalla. Da igual lo lejos que se llegue: siempre se pintan las mismas ~30 rayas.

Lección aprendida · «infinito» no puede ser literal

La primera versión de esta clase se llamaba InfiniteValueRuler y no tenía máximo, porque la idea era «que se pueda arrastrar indefinidamente». Estaba rota: bastaba arrastrar con un poco de impulso para que el ajuste saltara a números como 148.888.880 % y se quedara pillado ahí.

Fallaban dos cosas a la vez, y las dos son trampas clásicas al escribir una View:

  • Precisión de la coma flotante. Un Float guarda unos 7 dígitos significativos. Pasados unos 16 millones, sumarle el arrastre del dedo no cambia nada: el número es tan grande que el incremento se pierde al redondear. El ajuste se queda congelado en un valor absurdo.
  • Desbordamiento al pasar a Int. El cálculo de la inercia trabaja en enteros, y se le pasaba Int.MAX_VALUE como tope. Al convertir un desplazamiento gigantesco a Int, el número se satura en ese máximo en vez de dar error, así que el fallo pasaba desapercibido en vez de reventar.

La conclusión: «arrastre sin tope» es una idea de interfaz, no de aritmética. El tope tiene que existir; lo que tiene que hacer es estar lo bastante lejos como para que no se note. Ahora la clase tiene maxValue, el amplificador lo pone en BOOST_MAX_PERCENT (1000 %, unos 33 dB — muy por encima de cualquier uso real), y llegar hasta ahí arrastrando son varios metros de dedo.

Estructura / flujo

  • Todo el estado es un único número, scrollPx: cuántos píxeles se ha desplazado la cinta desde minValue. De ahí sale el valor (minValue + scrollPx / pxPerUnit) y de ahí sale dónde va cada marca al dibujar. Se mantiene siempre dentro de 0..maxScrollPx.
  • onDraw calcula qué unidades caben en el ancho de la vista y pinta una raya por cada una: pequeña y gris las normales, grande y del color de acento las múltiplos de 10, que además llevan su número debajo. El indicador central se dibuja al final, encima.
  • onMeasure le da un alto por defecto de 64 dp, lo justo para las marcas y sus números, si nadie dice otra cosa desde el XML.
  • Al soltar, la cinta se cuadra con la marca entera más cercana (snapToNearest) para no quedarse a medio camino entre dos números.
Android · GestureDetector y OverScroller

GestureDetector traduce la lluvia de MotionEvent a gestos con sentido: aquí interesan onScroll (el dedo arrastra: da cuántos píxeles se ha movido) y onFling (el dedo se suelta con impulso: da la velocidad). Sin él habría que medir distancias y velocidades a mano dentro de onTouchEvent.

Cuidado con los signos, que no coinciden entre los dos: distanceX es positivo cuando el dedo va hacia la izquierda, mientras que velocityX es positivo cuando va hacia la derecha. Por eso en onFling la velocidad lleva un menos delante y en onScroll la distancia no.

OverScroller calcula la inercia: se le dice la posición y la velocidad iniciales y él va diciendo, fotograma a fotograma, dónde debería estar la cinta mientras frena sola. Es la misma pieza que usan las listas de Android, así que el tacto es idéntico al del resto del sistema.

La trampa de computeScroll()

computeScroll() es el bucle de animación: Android lo llama en cada fotograma que se dibuja, se lee la posición del scroller, se redibuja y se pide el siguiente fotograma con postInvalidateOnAnimation hasta que la inercia se agota.

Lo que es fácil pasar por alto —y aquí también estaba mal al principio— es que se llama siempre, no solo mientras hay animación. La primera versión aprovechaba la rama del «ya no hay inercia» para encajar la cinta con la marca más cercana, y eso significaba intentar el encaje en cada dibujado, sin que nadie lo hubiera pedido. Como con la coma flotante el desfase nunca llega a ser exactamente cero, el encaje se reprogramaba a sí mismo indefinidamente.

La solución es la bandera pendingSnap: se levanta al soltar el dedo y se baja en cuanto se hace el encaje, así que solo ocurre cuando de verdad ha terminado un gesto.

Dos detalles de convivencia: tocar la cinta corta la inercia en seco (scroller.forceFinished(true) en onDown), como en cualquier lista; y mientras se arrastra se llama a requestDisallowInterceptTouchEvent(true) para que el ScrollView que la contiene no le robe el gesto y convierta el ajuste en un scroll de la pantalla.

Almacenamiento — Storage Access Framework

UltiMusic ya no pide MANAGE_EXTERNAL_STORAGE («Acceso a todos los archivos»): Google Play rechaza ese permiso para un reproductor. En su lugar usa el Storage Access Framework (SAF): el usuario concede cada carpeta raíz con el selector del sistema y la app solo puede tocar lo que hay dentro.

Android · Storage Access Framework

Con ACTION_OPEN_DOCUMENT_TREE (ActivityResultContracts.OpenDocumentTree) el sistema muestra su propio selector de carpetas y devuelve un URI de árbol (content://com.android.externalstorage.documents/tree/primary%3AUltiMusic). Con takePersistableUriPermission ese permiso sobrevive a reinicios. Dentro del árbol no hay File: se listan hijos con DocumentsContract y un ContentResolver, se abren con openInputStream/openOutputStream y se crean con createDocument. Un permiso de árbol normalmente no sobrevive a desinstalar la app.

Qué carpetas hay

  • UltiMusic — obligatoria; se pide al primer arranque (MainActivity.checkStoragePermission). Su URI se guarda en SharedPreferences (hace falta antes de que exista Room). Dentro viven Playlists/, images/ y databases/, además de la música.
  • Raíces adicionales — opcionales, desde Ajustes > Carpetas de la fonoteca; se guardan en la tabla library_roots.
  • Lista gris — subcarpetas dentro de las anteriores; no piden permiso nuevo.

  1. La migración de BD 29→30 vacía library_roots y greylist_folders (sus rutas absolutas ya no sirven) pero no toca songs.

  4. Mientras tanto, una fila con ruta absoluta se trata como «carpeta no legible»: reconcile puede emparejarla por nombre o duración, pero nunca la borra.

util/CoverArt.ktcarátulas con Coil

Resuelve la carátula de cada canción con una cadena de reserva: imagen personalizada → arte embebido en el archivo → miniatura de YouTube cacheada → recuadro de reserva. Incluye Fetchers propios para que Coil sepa extraer la imagen embebida de un audio (AudioCoverFetcher) y componer collages (GroupCoverFetcher), sus Keyers de caché, y un ImageLoader compartido (CoverLoader).

Todas las imágenes de la app viven en UltiMusic/images (imagesDocPath(context, createIfMissing)), una subcarpeta visible de la carpeta concedida, así que sobreviven a reinstalar si el usuario vuelve a concederla. Cada archivo se nombra como el título de lo que ilustra (sanitizeFileName); reserveFileName resuelve colisiones con «Título (2).ext»… imageUri(context, name) da el URI abrible vía SafStorage. La carpeta se busca sin distinguir mayúsculas: el volumen emulado trata «images» e «Images» como el mismo nombre al crear, y una comparación exacta acababa creando «images (1)», «images (2)»… en cada guardado.

Para un álbum o artista la cadena tiene un eslabón más: imagen propia → COLLAGE con las carátulas de varias de sus canciones (si hay al menos 4 distintas) → carátula de la primera canción que tenga alguna → recuadro. Lo describe un CoverRef(ownImage, …, group = GroupCoverSource(kind, id)) y lo resuelve GroupCoverFetcher bajo demanda, consultando collageCandidatesForAlbum/Artist en el orden en que se ven en la ficha.

Diseño · revision, repintar aunque nada haya cambiado en Room

Un StateFlow nunca reemite un valor igual al anterior. Si se reemplaza una carátula reutilizando su nombre de archivo (el caso normal), el Song que sale de Room es idéntico campo a campo y ninguna lista se repinta. revision es un contador que cada editor sube al guardar (touch()): las listas lo combinan con su flujo para forzar el repintado, y GroupCoverKeyer lo mete en la clave del collage para invalidarlo. Los Keyers de archivo ya llevan la fecha de modificación, así que un repintado de más solo cuesta una consulta a la caché.

Si un Fetcher devuelve null, Coil entiende «este Fetcher no sabe tratar este dato» y busca otro; al no haberlo, falla diciendo que no encuentra Fetcher, en vez de pintar el recuadro de error. Por eso AudioCoverFetcher y GroupCoverFetcher lanzan una excepción propia (NoEmbeddedArt, NoCollage) cuando no hay imagen.

Saca un color de acento de una carátula para teñir con él la interfaz. Es lo que sustituye al amarillo fijo de UltiMusic cuando hay algo sonando (regla del proyecto: todo lo amarillo usa el color dinámico).

AndroidX · Palette

Palette analiza un Bitmap y devuelve unos cuantos colores representativos («swatches») ya clasificados: vibrante, apagado, oscuro, claro, dominante…

Estructura

  • DEFAULT — el amarillo de siempre (= @color/um_gold), para cuando no hay carátula de la que sacar nada.
  • fromCover(context, data) — carga la imagen con el ImageLoader de la app (allowHardware(false): Palette necesita leer píxeles desde la CPU), elige un swatch y lo hace legible. Cachea el resultado por carátula (ruta + fecha de modificación, la misma idea que los Keyers de Coil): la misma portada da siempre el mismo acento; antes, una carátula con varias zonas parecidas podía dar un color distinto de una pasada a otra.
  • pickSwatch(palette) — de más a menos «vivo», pero exigiendo que el candidato cubra un mínimo de la imagen (un vibrante sacado de un reflejo no es representativo); si ninguno llega, el dominante. Todos pasan por hasColor(): un gris o negro casi puro no vale, porque su matiz en HSL es arbitrario (normalmente 0°, rojo) y readable lo convertía en un rojo que no estaba en la portada. Si la portada es en blanco y negro, devuelve null y se usa GRAYSCALE_FALLBACK (un gris claro), no el amarillo.

  • dim(color) — el acento a un tercio (RGB / 3): sustituye a @color/um_gold_dark. Ver AccentTint.
  • asBackground(color) — versión desaturada y oscura para usar de fondo (cabeceras de las fichas); onColor(fondo) — blanco o negro, lo que se lea encima.

util/AccentTint.ktobject · aplicar el acento a las vistas

DynamicColor calcula el color; este objeto es el que lo pinta. Recoge los tres gestos que se repiten en todas las pantallas al repintar con el acento, y sobre todo deja escrita en un solo sitio la regla de los dos amarillos de UltiMusic:

  • Lo que en el XML sea @color/um_gold se repinta con el acento de la canción que suena.
  • Lo que sea @color/um_gold_dark se repinta con ese mismo acento a un tercio (DynamicColor.dim).

Los dos amarillos fijos cumplen esa misma relación, así que mientras no suena nada la app se ve exactamente igual que siempre: la regla no cambia el diseño, solo lo formaliza.

Estructura

  • icons(root, accent, vararg ids) — tiñe iconos buscándolos por id dentro de root. Usa ImageViewCompat.setImageTintList y no setColorFilter, porque un tinte respeta el estado de la vista (pulsada, deshabilitada) y un filtro de color no.
  • fill(root, id, color) — cambia el relleno del shape que hace de fondo de una vista (el <solid> de su XML).
  • stroke(root, id, color, widthDimen) — cambia su contorno (el <stroke>). Hay que volver a pasarle el ancho porque setStroke lo reescribe entero y no hay forma de preguntarle a un GradientDrawable cuál tenía; por eso los anchos viven en res/values/dimens.xml (ipod_stroke_*) y los comparten el XML del drawable y esta llamada.
  • buttons(dialog, accent) — tiñe el texto de los botones («Aceptar», «Cancelar»…) de un AlertDialog ya mostrado, y de paso fija su ripple (el destello al tocarlos) en blanco fijo, no en accent: por defecto Material lo pinta con colorPrimary (el amarillo fijo del tema), así que sin esto los botones de todos los diálogos de la app pulsarían en amarillo aunque su texto ya siguiera el acento. Se hace con un cast a MaterialButton, seguro en esta app porque el tema es Material3 (la MaterialComponentsViewInflater convierte cualquier <Button> de un AlertDialog.Builder normal en un MaterialButton por su cuenta, sin que haga falta MaterialAlertDialogBuilder).
Android · mutate() y drawables compartidos

Tanto fill como stroke llaman a mutate() antes de tocar nada, y es imprescindible. Android cachea los drawables por recurso: dos vistas que usen el mismo @drawable/… comparten el mismo objeto en memoria. Sin mutar, repintar una repintaría también la otra (y cualquier otra que se infle después). mutate() le da a esa vista una copia propia sobre la que escribir.

Por qué no se detecta solo

Aquí no hay ninguna magia que recorra el árbol de vistas buscando lo que sea amarillo: cada pantalla enumera las suyas en su collect de accentColor. Es a propósito. Android deja escribir colores sin problema pero casi no deja leerlos: el color de un <stroke> de un shape no se puede consultar desde código a ningún nivel de API, y los cinco contornos del iPod son justo eso. Detectarlos automáticamente obligaría a re-parsear los XML de los drawables y a llevar un registro de qué era cada superficie antes del primer repintado. Enumerarlas es más tonto, pero se entiende de un vistazo y no se rompe.

Consecuencia práctica: quien añada una vista amarilla nueva tiene que acordarse de darla de alta en su pantalla.

Qué queda fuera

colorPrimary y colorSecondary del tema siguen siendo el amarillo fijo, así que lo que Material pinta por su cuenta desde ahí no sigue al acento automáticamente. Cambiar un color del tema de verdad exige recrear la Activity, que con un color que cambia en cada canción daría un parpadeo constante. Donde molestaba se ha compensado a mano: el tabRippleColor de las pestañas en MainActivity, los contornos y el cursor del editor de metadatos, y las casillas y botones del diálogo «Añadir a playlist».

Hay un caso más sutil, porque no es el relleno de una vista el que se queda en amarillo fijo, sino su ripple — el destello al tocarla, un gesto que Material calcula aparte y que en varios sitios sale de colorPrimary por defecto en vez del android:colorControlHighlight blanco de siempre. Compensado a mano: buttons() (arriba) para los botones de todos los AlertDialog de la app, y en ajustes las casillas «Desactivar límite» / «Opciones adicionales».

El blanco de estos dos usa @color/um_ripple_white (#33FFFFFF, un 20% de opacidad) y no blanco a secas: es el mismo porcentaje que ripple_material_dark, el valor de fábrica de android:colorControlHighlight con el que ya pulsa el resto de la app (mini-reproductor, filas de listas…). Un blanco opaco pulsaba mucho más fuerte que todo lo demás.

MaterialSwitch tuvo un caso propio, más largo de rastrear porque parecía ya arreglado sin estarlo: su ripple no sale de colorPrimary como el resto, sino de colorControlActivated —que en un tema Material3/MDC como este resuelve a colorAccent y de ahí a colorSecondary, el mismo amarillo— cuando está encendido, y de colorControlHighlight (blanco translúcido, sin relación con el acento) cuando está apagado. Ese atributo no lo toca ni trackTint ni thumbTint: el ripple de un MaterialSwitch lo pinta el android:background que hereda de Widget.AppCompat.CompoundButton.Switch (?attr/controlBackground), un selector de fábrica ajeno del todo a esos dos atributos. DynamicColor.switchTrackTint (ver abajo) solo arregla el relleno sólido de la pista, y deja este ripple tal cual: por eso eqSwitch tocaba en blanco al activarlo (rama «apagado» de ese selector) y en amarillo al desactivarlo (rama «encendido»: sigue marcado como encendido mientras se mantiene pulsado, hasta soltar el dedo), aunque la pista ya estuviera corregida. (Un primer intento fue añadir un tercer estado «pulsado» a switchTrackTint y a thumbTint, forzándolos también a blanco; se descartó al dar con el problema de verdad, porque no arreglaba el ripple —la causa real— y encima pintaba la pista de un blanco sólido redundante encima del cual el ripple seguía en amarillo.) Se corta con ThemeOverlay.UltiMusic.SwitchRippleWhite (styles.xml), que redefine colorControlActivated a blanco solo para esa vista vía android:theme — la única vía pública, porque MaterialSwitch no expone ningún rippleColor propio. Aplicado tanto en eqSwitch (dialog_settings.xml) como en el switch de cada carpeta de la lista gris (item_greylist_folder.xml), el mismo problema de fondo en los dos.

MaterialCheckBox.setRippleColor existe pero es private — no se puede llamar desde fuera de la librería, así que las dos casillas fijan app:rippleColor="@color/um_ripple_white" directamente en dialog_settings.xml en vez de por código. MaterialButton.rippleColor (el que usa buttons()) y trackTintList de MaterialSwitch sí son públicos, por eso esos dos se tocan en Kotlin; su ripple, en cambio, no tiene ningún atributo público propio (de ahí el ThemeOverlay de arriba).

Java · Normalizer y las tildes de Unicode

Unicode permite escribir «á» de dos maneras: como un único carácter, o como una «a» seguida de una marca de acento invisible. Normalizer.Form.NFD pasa todo a la segunda forma (descomponer), y entonces las marcas se pueden borrar con una expresión regular, porque Unicode las agrupa en la categoría \p{Mn} («Mark, nonspacing»: signos que no ocupan sitio propio y se dibujan sobre la letra anterior). util/YouTubeUrl.ktobject · enlaces de YouTube

Traduce cualquier enlace de YouTube al identificador de 11 caracteres que necesita el reproductor. Existe porque loadVideo() no acepta una URL, quiere solo el ID, y porque el mismo vídeo se escribe de muchas maneras según de dónde se copie el enlace.

Formatos que reconoce

  • youtube.com/watch?v=ID (con cualquier parámetro extra detrás: &t=42s, &list=…).
  • youtu.be/ID — lo que da el botón de compartir, normalmente con un ?si=… detrás.
  • /embed/ID, /shorts/ID, /live/ID y /v/ID.
  • El ID pelado, por si el usuario pega solo eso.
  • Da igual el protocolo y el subdominio: se quitan https://, www., m. y music. antes de mirar nada, así que también funciona con lo que el usuario escriba a medias.

Comprobar que el resultado son exactamente 11 caracteres de A-Z a-z 0-9 - _ hace de validación: si lo que se pegó no encaja, devuelve null y quien llama avisa en vez de intentar reproducir algo que no existe. Es también lo que permite al buscador distinguir la página de resultados (que no es un vídeo) de la de un vídeo concreto.

Ofrece además searchUrl(consulta) (la página de resultados con la búsqueda ya escrita) y watchUrl(id) (el enlace canónico, que es lo que se guarda en Song.videoUrl).

Se analiza a mano en vez de con Uri.parse a propósito: así la función no depende de Android y se puede probar sin emulador.

Reconocer «la misma canción» escrita de formas distintas: quita mayúsculas, espacios y puntuación («PinocchioP», «Pinocchio-P» y «pinocchio p» pasan a ser lo mismo) y luego acepta la coincidencia en los dos sentidos, porque cada fuente añade sus propias coletillas al mismo título — iTunes suele poner «Nombre (Radio Edit)» y Genius «Nombre (feat. Una única función, check(context), que la usa el amplificador de volumen: quitar el tope del 150 % solo se permite cuando el sonido sale al aire, porque un volumen así directo al oído puede dañarlo de verdad.

La pregunta no es «¿hay algo conectado?» sino «¿ese algo va en la oreja?». Un altavoz Bluetooth en la otra punta del salón está tan conectado como unos auriculares, pero amplificarlo no tiene ningún riesgo, así que ahí sí se deja quitar el tope. Distinguirlos es la parte interesante de este archivo.

Las tres respuestas

  • Check.NONE — nada pegado al oído: altavoz del móvil, altavoz Bluetooth, coche… Se puede amplificar sin tope.
  • Check.CONNECTED — auriculares, cascos o audífonos. El tope se mantiene.
  • Check.UNKNOWN_BLUETOOTH — hay un aparato Bluetooth pero no se sabe cuál, porque falta el permiso para preguntárselo. Se trata como si fueran auriculares, pero se distingue del anterior para que la pantalla de ajustes pueda ofrecer conceder el permiso en vez de dar un «no» sin explicación.
Android · AudioManager.getDevices

getDevices(GET_DEVICES_OUTPUTS) devuelve todas las salidas de audio disponibles ahora mismo, cada una con su type (una constante de AudioDeviceInfo: altavoz, HDMI, jack, Bluetooth…).

Se usa esto y no el isWiredHeadsetOn() de toda la vida por dos motivos: aquel está obsoleto y, sobre todo, no se entera de los auriculares Bluetooth, que hoy son la mayoría.

Las salidas por cable (jack con y sin micrófono, USB-C y audífonos) no tienen ninguna ambigüedad: si están, hay auriculares y se acabó. El problema es el Bluetooth.

Bug de verdad · el altavoz de llamadas siempre estaba «conectado»

La primera versión de WIRED_IN_EAR_TYPES incluía TYPE_BUILTIN_EARPIECE, el altavocito de llamadas que se pega a la oreja. Parecía razonable: es, literalmente, un auricular. El resultado fue que check() devolvía CONNECTED en cualquier móvil real, siempre, sin nada conectado — desinstalar y reinstalar la aplicación no cambiaba nada, porque el fallo no vivía en ningún estado guardado.

El motivo: getDevices(GET_DEVICES_OUTPUTS) devuelve las salidas disponibles, no las que están sonando ahora mismo. Cualquier móvil con radio de telefonía tiene ese altavoz de fábrica, así que aparece en la lista esté en uso o no — no hace falta estar llamando para que salga. Y como la comprobación era «basta con que aparezca una vez», siempre encontraba ese candidato y siempre bloqueaba.

La solución es quitarlo de la lista, y es segura: la reproducción de música (STREAM_MUSIC) nunca se enruta sola a ese altavoz — el sistema solo lo usa durante una llamada —, así que no hay ningún escenario real en el que el amplificador de UltiMusic esté sonando por él.

Bluetooth · A2DP, SCO y por qué ninguno de los dos sirve aquí

Bluetooth no tiene una sola forma de mandar sonido, sino varias, y el móvil elige según para qué sirva:

  • A2DP (Advanced Audio Distribution Profile) es el de música: estéreo, calidad alta (códecs SBC, AAC, aptX, LDAC) y unidireccional — solo va del móvil al aparato, no lleva micrófono de vuelta.
  • SCO (Synchronous Connection-Oriented) es el enlace que usan los perfiles de llamada (HFP «manos libres», HSP «headset»): mono, muy poco ancho de banda (calidad de teléfono) y bidireccional, porque lleva también el micrófono del auricular. Es la razón de ese efecto conocido: estás escuchando música con los cascos, entra una llamada y de golpe el sonido se vuelve turbio y enlatado — el móvil ha cambiado de A2DP a SCO para poder abrir el micro.

El problema es que ninguno de los dos dice qué forma tiene el aparato: por A2DP se conectan igual unos auriculares que un altavoz portátil, una barra de sonido o la radio del coche. Si se tratara «A2DP conectado» como «hay auriculares», la app diría «desconecta los auriculares» con un altavoz Bluetooth en la otra punta del salón — justo el caso en el que sí quieres quitar el límite.

Bluetooth · la clase de aparato (BluetoothClass)

Todo aparato Bluetooth anuncia una clase: un número que dice qué es (auriculares, altavoz, equipo de coche, teclado, teléfono…). Esa es la única forma de saber si lo que hay al otro lado va en la oreja, porque el perfil de audio no lo dice.

El camino es: AudioDeviceInfo.getAddress() da la dirección MAC de la salida Bluetooth → BluetoothAdapter.getRemoteDevice(mac) da el aparato → .bluetoothClass.deviceClass da la clase.

NOT_IN_EAR_CLASSES es una lista de lo permitido y no de lo prohibido, a propósito: contiene solo las clases que seguro que no van en la oreja, y cualquier otra se trata como auriculares. Está agrupada por la clase mayor del aparato (la parte del número que dice la categoría general):

  • AUDIO_VIDEO — solo los subtipos de equipo de sonido de habitación: altavoz, coche, hifi, decodificador, vídeo, monitor, pantalla con altavoz, videoconferencia. Fuera a propósito los que sí son auriculares en alguna forma (AUDIO_VIDEO_HEADPHONES, _WEARABLE_HEADSET, _HANDSFREE) y los ambiguos (_PORTABLE_AUDIO, _UNCATEGORIZED, que usan tanto altavoces baratos como auriculares).
  • COMPUTER — de sobremesa, portátil, servidor… Un ordenador emparejado como salida de audio Bluetooth no va pegado a la oreja.
  • PHONE — mismo razonamiento: otro teléfono actuando de altavoz Bluetooth no es un auricular.

El bloque COMPUTER es el que faltaba en la primera versión de esta lista, y el motivo de ampliarla: un PC de Windows emparejado como altavoz Bluetooth se anuncia con esa clase mayor, no con AUDIO_VIDEO. Como no estaba en ninguna lista, caía en el «cualquier otra» y la aplicación trataba el propio ordenador del usuario como si fueran auriculares — bloqueando el amplificador precisamente en el caso más inofensivo posible.

Se quedan fuera las clases mayores WEARABLE (salvo COMPUTER_WEARABLE, dejado también fuera por el mismo motivo) y TOY: cosas como WEARABLE_GLASSES o WEARABLE_HELMET sí pueden llevar altavoces junto al oído, y no hay forma de distinguirlas del resto de su clase (relojes, chaquetas…) sin arriesgarse. Ante la duda, se protege el oído, aunque eso signifique que algún aparato inofensivo se quede tratado como auriculares.

Android · el permiso BLUETOOTH_CONNECT

Preguntarle su clase a un aparato Bluetooth necesita permiso, y Android cambió el sistema en la versión 12 (API 31): antes bastaba con BLUETOOTH, un permiso normal que se concede al instalar; a partir de ahí hace falta BLUETOOTH_CONNECT, que es de tiempo de ejecución y hay que pedirle al usuario con un diálogo, como el de almacenamiento.

Por eso el manifest declara los dos, el viejo con maxSdkVersion="30" para no pedirlo donde ya no sirve. Y por eso el nuevo lleva usesPermissionFlags="neverForLocation": sin esa marca, Android trata el Bluetooth como un permiso de ubicación (porque los aparatos cercanos delatan dónde estás), y aquí no se usa para nada de eso.

El permiso no se pide al arrancar, sino solo en el momento en que hace falta de verdad: cuando el usuario intenta quitar el límite y hay un Bluetooth sin identificar. Si lo concede, se reintenta solo.
