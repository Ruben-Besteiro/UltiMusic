UltiMusic por dentro

Cómo está construido el reproductor: cada script explicado uno a uno, su estructura, el flujo de datos que los conecta y los conceptos de Android, Kotlin y Room que necesitas para entenderlos.

Qué es UltiMusic

UltiMusic es «el reproductor de música definitivo, libre de las restricciones de MediaStore». Esa frase resume su decisión de diseño más importante.

Concepto · MediaStore

MediaStore es el índice de medios del sistema Android: una base de datos que el propio Android mantiene con todas las canciones, fotos y vídeos del móvil. La mayoría de reproductores se limitan a preguntarle a MediaStore «dame las canciones». El problema: si MediaStore tiene una etiqueta mal, un artista mal escrito, etc., tú no lo puedes corregir de verdad.

UltiMusic da la vuelta a eso con dos reglas:

  • Descubrir canciones escaneando el sistema de archivos directamente (recorriendo carpetas), no preguntando a MediaStore.
  • Lo que el usuario edita dentro de la app manda. Las ediciones se guardan en una base de datos propia y sobrescriben lo que hubiera. MediaStore solo se usaría como fuente inicial de etiquetas, nunca como verdad definitiva.

El editor de metadatos de canciones ya está implementado, igual que las pestañas de Álbumes, Artistas y Productores con sus fichas de detalle y el color dinámico sacado de la carátula. La pestaña de Listas de reproducción también está implementada (playlists guardadas como archivos de texto, con reordenación por arrastre y navegación desde el iPod). El editor de metadatos de álbum también está implementado, desde el botón de 3 puntos de su ficha (que además ofrece añadir el álbum entero a una playlist o a la cola, y eliminarlo). La pestaña de Géneros también está implementada: lista de solo texto (sin ficha propia) que, al pinchar un género, abre el iPod en modo navegación igual que una playlist, salvo que no se puede reordenar. El autorrelleno de metadatos también está implementado, en los dos editores, buscando en MusicBrainz (ver Fuentes remotas) — cubre ese hueco sin necesidad de Last.fm. Quedan los editores de artista y productor y la integración con YT-DLP y Musixmatch (para la letra). Esta documentación cubre el estado actual del código, centrado en la persistencia (guardar los modelos para que sobrevivan al cierre de la app) y la interfaz.

Flujo 4 — Desinstalar y reinstalar: recuperación automática

Desinstalar la app borra /data/data/<paquete>/databases/ultimusic.db, pero no borra ~/UltiMusic/databases (vive en el almacenamiento del dispositivo, no en el privado de la app). Al volver a instalar y abrir la app, UltiMusicDatabase.get() comprueba si la base de datos interna existe; si no existe y hay una copia en ~/UltiMusic/databases, la restaura ahí antes de que Room llegue a abrirla (ver UltiMusicDatabase.kt). Así las ediciones del usuario —que solo viven en Room, nunca en MediaStore— sobreviven a un desinstalar/reinstalar.

Conceptos base

Ideas de Android, Kotlin y Room que se repiten por todo el código. Si algún término te suena raro más adelante, vuelve aquí.

Kotlin · data class

Una data class es una clase pensada para guardar datos. Kotlin le genera automáticamente cosas útiles (comparación, copia con copy(), texto legible). Casi todos los «modelos» son data classes.

Kotlin · object y companion object

object X { } crea un singleton: una única instancia global para toda la app (útil para utilidades sin estado). Un companion object dentro de una clase es como su «zona estática»: constantes y funciones que pertenecen a la clase, no a cada objeto (p. ej. UltiMusicDatabase.get(...)).

Kotlin · coroutines, suspend y Dispatchers

Una corrutina es una tarea que puede pausarse y reanudarse sin bloquear el hilo. Una función suspend solo se llama desde dentro de una corrutina. withContext(Dispatchers.IO) mueve el trabajo a hilos de entrada/salida (disco, red, base de datos), dejando libre el hilo principal para que la interfaz no se congele.

Kotlin · Flow y StateFlow

Un Flow es un «grifo» de valores que van llegando con el tiempo. Si te suscribes, recibes cada nuevo valor. Room puede devolver un Flow de una consulta: cuando la tabla cambia, el Flow reemite la nueva lista solo. Un StateFlow es un Flow que además recuerda siempre su último valor (ideal para la interfaz).

Android · Activity, Fragment y ViewModel

Una Activity es una pantalla del sistema. Un Fragment es un trozo reutilizable de pantalla dentro de una Activity (aquí, cada pestaña). Un ViewModel guarda los datos de la pantalla y sobrevive a girar el móvil o a recrear la vista; separa «los datos» de «cómo se dibujan».

Android · RecyclerView y Adapter

Un RecyclerView es una lista eficiente: solo crea las filas visibles y las recicla al hacer scroll. El Adapter es el puente entre tus datos y esas filas: dice cuántas hay, crea cada fila (ViewHolder) y rellena su contenido.

Android · Room

Room es la librería oficial para usar una base de datos SQLite con comodidad. Tú describes las tablas con clases anotadas (@Entity), las consultas en una interfaz (@Dao), y Room genera todo el código SQL por ti, comprobando los errores al compilar.

Capa de modelos — model/

Los modelos de dominio: objetos limpios que consume la interfaz. No saben nada de Room ni del disco; son solo «una canción», «un álbum», «un artista». La capa de datos los produce a partir de las tablas.

model/Song.ktdata class · una canción

Representa una canción tal como la ve la interfaz, ya con sus artistas y álbumes incrustados como listas.

Estructura

  • id, filePath (ruta del archivo), title, duration, year, genres.
  • artists: List<Artist>, albums: List<Album> y producers: List<Producer> — una canción puede tener varios de cada uno.
  • imageName, comment, lyrics, language — metadatos editables.
  • videoUrl — enlace de YouTube del videoclip, para el modo vídeo del iPod. Lo pone siempre el usuario (a mano en el editor, o eligiéndolo en el buscador que abre el propio iPod); vale null mientras la canción no tenga vídeo asignado.
  • videoThumbnailName — nombre del archivo de la miniatura de ese vídeo, recortada al cuadrado y cacheada en ~/UltiMusic/images (ver CoverArt). Sirve de carátula de reserva cuando la canción no tiene imagen propia ni arte embebido. Se descarga sola al guardar un enlace nuevo; vale null mientras no haya vídeo o la descarga haya fallado.
  • videoOffsetMs — milisegundos que se adelanta (positivo) o atrasa (negativo) el vídeo respecto al audio local, para corregir videoclips que no van del todo sincronizados. Se ajusta desde los ajustes del reproductor de vídeo del iPod (ver modo vídeo) y nunca toca el audio: solo la posición a la que se pide el vídeo. Por defecto 0.
  • ogTitle / ogArtist / ogAlbum / ogYear — info de la canción original de un remix (el prefijo «og» = original). No son etiquetas del archivo: los rellena el usuario cuando la canción es un remix, y valen null mientras no lo sea.

model/Producer.ktdata class · un productor

Idéntico a Artist: id, name e imageName. Artistas y productores se tratan exactamente igual en todo el proyecto (tabla propia, pestaña propia, ficha propia); lo que se hace con uno se hace con el otro.

¿Por qué dos clases en vez de una sola con un campo «rol»? Porque una misma persona puede aparecer como artista y como productor con nombre o imagen distintos, y porque así cada tabla se poda de forma independiente.

model/MetadataSuggestion.ktdata class · candidato de autorrelleno

Un candidato encontrado en MusicBrainz para el autorrelleno de metadatos. Representa siempre una publicación concreta (un álbum, un single…), nunca «la canción» en abstracto —ver el aside sobre Recording/Release/Release Group en MusicBrainzApi— porque eso es justo lo que permite elegir, por ejemplo, el año y la portada del single en vez de los del álbum.

Es un único modelo compartido por canción y álbum (kind: SuggestionKind dice cuál de los dos es) en vez de dos clases separadas, porque el diálogo de sugerencias, su lista y su ViewModel son los mismos para ambos casos; solo cambia qué campos trae rellenos cada uno (una sugerencia de álbum no tiene trackNumber/discNumber, por ejemplo).

SuggestionKind
model/LyricsSuggestion.ktdata class · candidato del buscador de letras

Un candidato encontrado en lrclib.net para el buscador de letras del editor de metadatos. A diferencia de MetadataSuggestion, aquí la búsqueda ya trae la letra completa (syncedLyrics/plainLyrics) de cada candidato: no hace falta pedir nada más cuando el usuario elige uno.

syncedLyrics es texto con marcas de tiempo [mm:ss.xx] por línea (el formato «LRC», el estándar de facto de las letras sincronizadas); plainLyrics es la misma letra sin esas marcas, de respaldo cuando lrclib.net no tiene una versión sincronizada de esa grabación.

model/Summaries.ktdata class · resúmenes de las pestañas

Los modelos que consumen las pestañas de Álbumes, Artistas, Productores y Géneros y sus fichas de detalle. No son las entidades completas porque lo que se pinta ahí son datos agregados, que la entidad por sí sola no conoce.

  • AlbumSummary — title, artistName, year, songCount, totalDuration y un CoverRef.
  • PersonSummary — name, albumCount, songCount, totalDuration y su CoverRef. El mismo modelo vale para un artista y para un productor, así que sus dos pestañas comparten adaptador y ficha.
  • AlbumTrack — una canción más el trackNumber que ocupa en ese álbum (vive en la tabla de cruce, no en la canción).
  • GenreSummary — name y songCount, nada más: sin id ni CoverRef, porque un género no tiene ficha ni carátula propia (ver GenresFragment). Es el único de estos resúmenes que no sale de una consulta SQL, sino de agrupar en Kotlin la lista de géneros de cada canción (ver LibraryRepository.genres).
CoverRef

Capa de escaneo — data/scan/

La parte de «lectura» de la fonoteca. Recorre el disco y extrae las etiquetas de cada archivo de audio, sin tocar la base de datos.

data/scan/ScannedSong.ktdata class · etiquetas crudas

El resultado de escanear un archivo: solo las etiquetas leídas (título, artista, álbum, artista del álbum, géneros, año, duración, productor, nº de pista y disco). Sin IDs ni relaciones. Es lo que el escáner entrega a la capa de datos.

Los campos de artista/álbum pueden ser null (no todas las canciones traen etiquetas); es la capa de datos quien decide el valor «desconocido».

data/scan/MusicScanner.ktobject (singleton) · escáner de disco

Busca canciones directamente en el sistema de archivos, fiel a la filosofía «libre de MediaStore».

Estructura

  • AUDIO_EXTENSIONS — extensiones reconocidas (mp3, flac, m4a, opus…).
  • Constantes UNKNOWN_ARTIST / UNKNOWN_ALBUM («Artista/Álbum desconocido»).
  • scanRoots() — carpetas donde busca: solo UltiMusic, para que el usuario tenga un único sitio claro donde guardar su música y no se dupliquen canciones con otras apps.
  • libraryFolderReadable() — ¿se puede leer ahora mismo esa carpeta? Lo consulta quien vaya a dar una canción por perdida, para no confundir «la canción ya no está» con «la carpeta no se puede leer».
  • collectAudioFiles(...) — recorre carpetas recursivamente juntando archivos de audio.
  • readSong(file) — abre el archivo y lee sus etiquetas.
  • scan(): List<ScannedSong> — la función pública; junta todo en segundo plano.
  • findByFilename(name): File? — busca un archivo de audio por su nombre (sin carpetas) dentro de las mismas raíces. A diferencia de scan(), solo recorre directorios: no abre ningún archivo ni lee etiquetas, así que es muy rápido. Sirve para relocalizar al vuelo una canción que el usuario ha movido de carpeta (ver LibraryRepository.resolvePlayablePath()).

Flujo / por qué

scan() corre en Dispatchers.IO (leer disco es lento; no debe bloquear la interfaz). Usa un LinkedHashSet para evitar archivos duplicados manteniendo el orden.

Tablas de la base de datos — data/db/entities/

Cada clase aquí es una tabla de la base de datos. La interfaz no las usa directamente; son la forma «normalizada» de guardar los datos.

Room · @Entity, clave primaria e índices

@Entity convierte una clase en una tabla. La clave primaria (@PrimaryKey) identifica cada fila de forma única; autoGenerate deja que Room asigne un número. Un índice (@Index) acelera las búsquedas por una columna y, si es unique, impide filas repetidas en esa columna.

Concepto · normalización y «clave de emparejamiento»

En vez de repetir «DECO*27» en cada canción, se guarda el artista una sola vez en su tabla y las canciones lo referencian. Eso es normalizar: editar el artista una vez lo cambia en todas sus canciones. Para reencontrar al mismo artista en escaneos futuros, cada artista/álbum guarda su valor de etiqueta original (tagName, tagTitle…) como clave estable de emparejamiento, independiente del nombre editable que se muestre.

data/db/entities/SongEntity.kttabla songs

Una fila por canción. filePath tiene índice único: es el ancla estable que identifica la canción entre escaneos (aunque el id autogenerado cambie).

Guarda los campos editables (title, duration, year, genres, lyrics, language, imageName, comment, videoUrl, videoThumbnailName, videoOffsetMs, hiddenByGreylist) y los og* de remix (a null al escanear).

El productor ya no es una columna de aquí: desde la v2 del esquema vive en su propia tabla, enlazada por una tabla de cruce, igual que los artistas. La v3 añadió videoUrl; la v4 añadió videoThumbnailName, el nombre de la miniatura de ese vídeo cacheada como carátula de reserva; la v6 añadió videoOffsetMs, el desplazamiento vídeo/audio de los ajustes del reproductor de vídeo; la v7 añadió hiddenByGreylist, ver el recuadro de abajo. No hay migraciones de verdad: la base de datos se abre con fallbackToDestructiveMigration, así que un cambio de esquema simplemente la recrea vacía (ver UltiMusicDatabase).

Diseño · hiddenByGreylist, ocultar sin borrar

hiddenByGreylist es la columna que hace funcionar la lista gris de los ajustes: cuando el usuario activa el switch de una subcarpeta (la excluye), sus canciones se marcan con true aquí y todas las consultas de lectura (observeSongs, los resúmenes de álbumes/artistas/productores, las fichas de detalle…) las excluyen. Al desactivar el switch, se marcan de vuelta a false y reaparecen exactamente igual.

La alternativa obvia —excluir esas carpetas del escaneo y dejar que reconcile() borre las canciones que «desaparecen»— se descartó a propósito: reconcile() borraría de verdad esas filas (con sus ediciones del editor, carátula propia, enlace de vídeo del iPod y su sitio en las playlists) y, al reactivar la carpeta, las recrearía como canciones nuevas, sin nada de eso. hiddenByGreylist es solo un filtro de lectura: la fila nunca se borra por esto.

Por qué videoUrl lo pone siempre el usuario. Las Developer Policies de YouTube obligan a borrar o refrescar cada 30 días cualquier dato obtenido de su API, así que un identificador de vídeo sacado de search.list no se podría guardar aquí de forma permanente. Un enlace que teclea o elige el usuario no es dato de la API: es dato nuestro, y se puede conservar indefinidamente. videoThumbnailName se acoge a la misma lógica: es una miniatura pública del CDN de YouTube (img.youtube.com), no un dato de la API oficial, así que tampoco caduca. Ver el modo vídeo.

Room · relaciones N:N y claves foráneas

Una canción puede tener varios artistas y un artista varias canciones: es una relación muchos-a-muchos. En SQL eso se resuelve con una tabla de cruce (cross-ref) que empareja los IDs de ambos lados. Una clave foránea (@ForeignKey) con onDelete = CASCADE hace que, al borrar una canción, se borren solas sus filas de cruce (sin dejar «basura»).

data/db/entities/SongArtistCrossRef.kt · SongAlbumCrossRef.kt · AlbumArtistCrossRef.kt · SongProducerCrossRef.kttablas de cruce N:N
  • song_artist — empareja songId ↔ artistId.
  • song_album — songId ↔ albumId, más trackNumber y discNumber propios de esa aparición.
  • album_artist — albumId ↔ artistId.
  • song_producer — songId ↔ producerId. Gemela de song_artist.

Cada una tiene clave primaria compuesta, claves foráneas en cascada e índice en la columna secundaria (Room exige indexar las columnas foráneas).

@ForeignKey CASCADEprimaryKeys
data/db/entities/GreylistFolderEntity.kttabla greylist_folders · v7

Una fila por subcarpeta añadida en ajustes > Lista gris. path (la ruta absoluta que devuelve el explorador de carpetas propio) es la clave primaria: no tiene sentido añadir la misma carpeta dos veces. excluded es el estado del switch de esa fila: encendido significa que la carpeta está fuera de la biblioteca.

A diferencia de las tablas de cruce de arriba, no tiene ninguna clave foránea hacia songs: la relación entre una subcarpeta y sus canciones no se guarda como enlace, se calcula comparando el filePath de cada canción contra el path de la carpeta (ver LibraryDao.setSongsHiddenUnderFolder). Nace con excluded = false: añadir una carpeta no la oculta de golpe, el switch es para excluirla después sin quitarla del todo (eso lo hace la papelera de su fila, que borra solo esta fila, nunca la carpeta real del dispositivo).

data/db/relations/Summaries.ktPOJOs de salida de consultas

Lo que devuelven las consultas de agregación que alimentan las pestañas de Álbumes, Artistas y Productores: AlbumSummaryRow, PersonSummaryRow y TrackPosition.

Room · POJOs de salida

Una @Query no tiene por qué devolver una entidad: puede devolver cualquier clase cuyos campos coincidan con los nombres de las columnas del SELECT. Room hace el emparejamiento por nombre. Se usa aquí porque lo que se pinta son cuentas y sumas («4 canciones», «12:41»), y calcularlas en SQLite es muchísimo más barato que traerse todas las canciones a memoria para contarlas en Kotlin.

El sufijo Row los distingue de los modelos de dominio del mismo nombre (model/Summaries.kt); los mappers convierten unos en otros.

Los campos sampleSongImage / sampleSongPath / sampleSongVideoThumbnail sostienen la cadena de carátulas: un álbum o un artista no son un archivo de audio, así que si no tienen imagen propia se recurre a la de una de sus canciones, en ese mismo orden (ver CoverArt).

Núcleo de Room — data/db/

La base de datos en sí, las consultas y los conversores.

data/db/Converters.ktTypeConverter

SQLite no sabe guardar una List<String>. Este conversor traduce la lista de géneros a texto (unido por un separador especial) al guardar, y la reconstruye al leer.

Room · @TypeConverter

Un TypeConverter enseña a Room a guardar un tipo que SQLite no entiende, convirtiéndolo a uno que sí (aquí, lista ↔ texto). Se registra en la base de datos con @TypeConverters.

La pestaña «Géneros» ya existe y sigue leyendo este texto tal cual, sin tabla propia: un género no tiene ficha, id ni portada, así que no aporta nada que Room tendría que gestionar (relaciones, huérfanos…) — LibraryRepository.genres simplemente agrupa esta lista en Kotlin.

data/db/LibraryDao.kt@Dao · el corazón de la persistencia

Define todas las operaciones sobre la base de datos. Es una clase abstracta (no interfaz) para poder incluir la lógica de reconciliación con @Transaction.

Room · @Dao, @Query/@Insert/@Update y @Transaction

Un DAO (Data Access Object) agrupa las operaciones de una tabla. @Query lleva SQL escrito por ti; @Insert/@Update generan el SQL automáticamente. @Transaction agrupa varias operaciones en un todo-o-nada: si algo falla a mitad, no queda la base de datos a medias.

Qué contiene

  • observeSongs(): Flow<List<SongWithRelations>> — la lectura reactiva que observa la interfaz.
  • Resúmenes de las pestañas: observeAlbumSummaries(id), observeArtistSummaries(id) y observeProducerSummaries(id). Calculan con subconsultas el nº de canciones, la duración total, el artista del álbum y la carátula de reserva. El parámetro id hace doble uso: con null devuelven la lista entera (la rejilla) y con un id concreto, una sola ficha (el detalle) — así no hay que duplicar esos SELECT tan largos.
  • observeAlbumEntity(id) / observeAlbumArtistNames(id) — la fila cruda del álbum y los nombres de sus artistas, sin cifras agregadas. Los usa el editor de metadatos de álbum para rellenar su formulario (mismo papel que observeSongs() para el editor de canciones).
  • Canciones de una ficha: observeSongsOfAlbum(id) (ordenadas por nº de pista), observeTrackPositions(id), observeSongsOfArtist(id) y observeSongsOfProducer(id).
  • Consultas de apoyo del escaneo: allSongPaths(), findArtistByTag(), findAlbumByTag() — buscan por el nombre de la etiqueta del archivo.
  • Consultas de apoyo del editor: findArtistByName() / findAlbumByTitle() / findProducerByName() (buscan por el nombre visible, el editable), observeArtistNames() / observeAlbumTitles() / observeProducerNames() para el autocompletado y trackNumberOf() / discNumberOf().
  • Inserciones, updateSong/Artist/Album/Producer, desenlazado (clearSongArtists/Albums/Producers), borrado por ruta y poda de huérfanos (pruneOrphanArtists/Albums/Producers).
  • deleteSong(songId) — borra una única fila por su id (a diferencia de deleteSongsByPath, que es para lotes) y poda huérfanos, en una @Transaction. La usa la opción «Eliminar» del menú de 3 puntos de la canción.
  • reconcile(scanned) — dentro de una transacción: inserta lo nuevo, crea/enlaza artistas, álbumes y productores, reapunta lo que se haya movido de carpeta y borra lo que ya no está en disco.
  • updateSongPath(oldPath, newPath) — reapunta una canción a su nueva ruta cuando el archivo se ha movido.
  • saveSongEdits(...) — el guardado del editor, también en una transacción (ver abajo).
  • saveAlbumEdits(album, artistNames) — su gemela para el álbum: actualiza la fila entera y rehace album_artist desde cero con clearAlbumArtists() + resolveArtist() (el mismo método privado que usa saveSongEdits), también en una @Transaction. No toca song_album ni ninguna canción.
  • Lista gris (v7): observeGreylistFolders(), insertGreylistFolder(), deleteGreylistFolder(), updateGreylistFolderExcluded() y excludedGreylistFolderPaths() son el CRUD de la tabla greylist_folders. Por encima de ellas, tres métodos en @Transaction: setSongsHiddenUnderFolder(folderPath, hidden) marca en bloque hiddenByGreylist de toda canción cuyo filePath empiece por esa carpeta (comparando texto, no una @ForeignKey: ver GreylistFolderEntity); setGreylistFolderExcluded(path, excluded) cambia el switch y oculta/muestra sus canciones en el mismo paso; removeGreylistFolder(path) quita la fila de la lista y devuelve visibles sus canciones. Ninguno de los tres reescanea: son UPDATE/DELETE directos, instantáneos.

Cómo guarda el editor: saveSongEdits()

Actualiza la fila de la canción y rehace desde cero sus enlaces con artistas y álbumes. Va todo en una sola @Transaction porque, si no, existiría un instante en el que la canción se ha quedado sin artistas — y como la interfaz observa la base de datos, lo pintaría.

Los nombres que escribe el usuario reenlazan: se busca la entidad con ese nombre y, si no existe, se crea. Nunca se renombra un artista o álbum existente, porque eso afectaría a todas las demás canciones que cuelgan de él (renombrar será cosa de sus propios editores). Por eso resolveArtist() busca primero por nombre visible y solo después por etiqueta: así un artista ya renombrado se reutiliza en vez de duplicarse.

Lo mismo vale para los productores, con una diferencia: si el usuario vacía el campo, la canción se queda sin ninguno. Al contrario que artista y álbum, aquí no se inventa un «Productor desconocido», porque llenaría la pestaña de ruido; por eso el escáner tampoco crea uno cuando la etiqueta no trae compositor.

Detalle fácil de olvidar: la pista y el disco viven en la tabla de cruce song_album, así que hay que volver a escribirlos al recrear los enlaces o se perderían. Al final se podan los artistas y álbumes de los que ya no cuelga nada.

La regla de oro de reconcile()

Una canción cuya ruta ya está guardada no se toca (appeared solo recoge las rutas que no estaban): así ningún reescaneo puede pisar lo que editaste, y las ediciones sobreviven a reabrir la app.

Las tres fases de reconcile(), y por qué mover un archivo no rompe nada

La reconciliación no compara canción a canción, sino conjuntos de rutas, en tres fases:

  1. Se separan las rutas que han desaparecido del disco (gone) de las que han aparecido (appeared).
  2. Se emparejan por nombre de archivo: una ruta que desaparece y otra que aparece con el mismo nombre son, casi con total seguridad, el mismo archivo movido de carpeta. En ese caso no se borra ni se inserta nada: solo se reapunta la fila con updateSongPath().
  3. Lo que queda sin emparejar sí son altas y bajas de verdad: se insertan (creando/enlazando artistas, álbumes y productores) y se borran (podando después los huérfanos).
Diseño · por qué detectar movimientos y no borrar+insertar

La fila de una canción guarda mucho más que su ruta: su id, todo lo que hayas escrito en el editor de metadatos, la carátula que hayas importado y sus enlaces con artistas, álbumes y productores. Si mover un archivo se tratara como «se ha borrado uno y ha aparecido otro», todo eso se perdería en cada movimiento y la canción volvería a nacer con las etiquetas crudas del archivo. Emparejar por nombre lo evita.

El emparejamiento asume que no hay dos archivos con el mismo nombre en carpetas distintas — exactamente la misma suposición que ya hacen las playlists, que guardan solo el nombre del archivo.

reconcile() nunca reescanea a propósito de la lista gris (eso lo resuelven directamente setGreylistFolderExcluded/removeGreylistFolder, ver arriba), pero sí tiene en cuenta qué carpetas están excluidas en dos sitios puntuales: al insertar una canción que aparece por primera vez dentro de una carpeta ya excluida, entra directamente con hiddenByGreylist = true (si no, se colaría visible hasta el próximo toque del switch); y si un archivo se mueve hacia dentro o hacia fuera de una carpeta excluida, su visibilidad se recalcula con la ruta nueva en el mismo paso que updateSongPath().

SQLite · WAL y checkpoint

Room usa el modo WAL (Write-Ahead Log): los cambios se escriben primero en un archivo aparte (.db-wal) y más tarde se «consolidan» en el .db principal. Por eso, para hacer una copia consistente, primero se ejecuta un checkpoint (PRAGMA wal_checkpoint) que vuelca el WAL al archivo principal.

La copia es unidireccional (solo para inspección; la base interna sigue mandando) y best-effort (si algo falla, se ignora con runCatching). Se hace porque en algunos móviles no se puede entrar en /data/data.

Diseño · la ventana en la que una ruta guardada miente

La reconciliación no es instantánea: MusicScanner.scan() abre y lee las etiquetas de todos los archivos (tarda segundos) y el DAO no escribe nada hasta el final, en una sola transacción. Durante todo ese rato la base de datos sigue apuntando a la carpeta antigua de cualquier archivo que hayas movido. Y como la reconciliación solo se dispara una vez por ejecución (SongsViewModel.loadIfNeeded()), la ventana puede durar bastante más.

Antes, esa ruta obsoleta se le pasaba tal cual a ExoPlayer: el archivo no existía, el reproductor fallaba sin decir nada y se quedaba clavado en 0:00. Se notaba sobre todo al abrir una playlist recién movido un archivo, porque las playlists casan por nombre y la canción seguía apareciendo en la lista.

resolvePlayablePath() cierra esa ventana: si el archivo no está donde decía la base de datos, lo busca por nombre con MusicScanner.findByFilename() (recorrido de carpetas, sin leer etiquetas: barato) y, si aparece, corrige la fila de paso para no tener que volver a buscarlo nunca más.

Concepto · archivos no reactivos vs. Room

Room reemite un Flow solo cuando cambia una tabla; un File no avisa a nadie cuando se modifica. Por eso, quien observa las playlists (el PlaylistsViewModel) debe volver a leer tras cada cambio: mantiene un contador («tick») que incrementa al mutar y que fuerza el recálculo.

Limitación asumida por diseño: como el modelo pide guardar «los nombres de los archivos», se casa por basename. Si dos archivos en carpetas distintas se llaman igual, gana el que esté en el índice.

data/remote/MusicBrainzApi.ktobject · cliente de MusicBrainz

MusicBrainz es una base de datos musical libre y colaborativa (la «Wikipedia de la música»): cualquiera puede editarla, y su contenido es de acceso libre a través de una API pública. Este archivo le pregunta por candidatos con los que rellenar el editor, a partir de título+artista (canción) o álbum+artista (álbum).

Es un object —no una clase con constructor— porque no necesita ningún Context de Android ni guarda nada entre peticiones: cada función pregunta y devuelve, sin recordar la anterior.

Android · HttpURLConnection

Es la clase de red que trae el propio Android, sin ninguna librería aparte (a diferencia de OkHttp o Retrofit, muy habituales en otros proyectos). Como la app entera solo hace dos tipos de llamada de red —esta y la miniatura de YouTube, ver LibraryRepository.downloadVideoThumbnail— no compensa añadir una dependencia solo para eso: se abre la conexión, se ponen las cabeceras, se lee la respuesta como texto y se cierra.

JSON · org.json

JSON es el formato de texto con el que casi todas las APIs web devuelven sus datos: llaves { } para objetos, corchetes [ ] para listas, y pares "clave": valor. org.json (JSONObject/JSONArray) es el lector de JSON que trae el propio Android; se usa aquí en vez de una librería como Gson o Moshi (que convierten el JSON directamente en objetos Kotlin) porque son muy pocos campos de muy pocos tipos de respuesta — no compensa generar clases para ello, y así tampoco hace falta ninguna dependencia nueva.

MusicBrainz · Recording, Release y Release Group

MusicBrainz distingue tres cosas que a simple vista parecen la misma canción: un Recording es la grabación en abstracto («esta canción, suene donde suene»); un Release es una publicación concreta de esa grabación (el álbum tal cual se vendió en un país y año, o el single); un Release Group agrupa todas las ediciones (distintos países, remasterizaciones…) de la misma publicación bajo un único id, para no tratarlas como cosas distintas. Cada Release tiene su propio año y su propia carátula. Es justo lo que hace falta para poder elegir, por ejemplo, el año y la portada del single en vez de los del álbum en el que la canción acabó apareciendo — el caso que motivó todo este autorrelleno.

Qué ofrece

  • searchSongs(title, artist) — busca en /recording. Cada recording de la respuesta trae su lista de releases[]; como la misma publicación puede aparecer repetida (una vez por país en que se vendió, o bajo grabaciones distintas que comparten álbum), se deduplica por el id de su release-group, quedándose con la de fecha más temprana de cada uno. Las publicaciones «ruidosas» (entrevistas, audiolibros…) se descartan por su secondary-types.
  • searchAlbums(album, artist) — busca en /release-group. Más simple que la anterior: cada resultado ya es la unidad correcta (un álbum, sin duplicados por país), así que no hace falta deduplicar nada.
  • fetchGenres(kind, mbId) — los géneros de MusicBrainz son folksonomía (etiquetas que cualquiera vota), no un campo fijo: no vienen en la búsqueda, hay que pedirlos aparte. Por eso esta función es independiente, y MetadataSuggestionsViewModel solo la llama para el candidato que el usuario elige, nunca para los diez de la lista.

MusicBrainz exige, para usar su API pública, un User-Agent con el nombre de la app y un contacto real ("UltiMusic/1.0 ( rbesteiro@proton.me )") — si no, empiezan a limitar o bloquear las peticiones. También limita a 1 petición por segundo sin registrarse; como la búsqueda es manual (botón del editor) y los géneros solo se piden al elegir un candidato, nunca se dispara más de una petición seguida, así que no hace falta ningún control de ritmo aparte.

Las portadas no las da MusicBrainz, sino su servicio hermano Cover Art Archive (coverartarchive.org): la URL se construye directamente a partir del id de la publicación (/release/{id}/front-250 o /release-group/{id}/front-250), sin comprobar antes si existe — no todas las publicaciones tienen carátula archivada, y si no la hay, Coil cae solo al recuadro de siempre (error(R.drawable.cover_placeholder)), igual que en el resto de la app.

lrclib.net es una base de datos libre y colaborativa de letras sincronizadas: cada línea de la letra lleva pegada la marca de tiempo en la que se canta (formato «LRC», [mm:ss.xx]texto), lo que permite ir resaltando la línea que toca mientras suena la canción — algo que servicios de pago como Musixmatch o Spotify Premium cobran aparte. Diseño · por qué sigue existiendo esta clase

Podría pensarse que, con toda la lógica en PlaybackService, los fragmentos podrían hablar con él directamente. No lo hacen por dos motivos: primero, un Service no es observable como lifecycle owner de forma cómoda desde XML/fragmentos igual que un ViewModel obtenido con activityViewModels(); segundo, y sobre todo, así ningún fragmento ni adaptador de la aplicación ha tenido que cambiar una sola línea al introducir el Service — todos siguen escribiendo playerViewModel.currentSong, playerViewModel.play(song), etc., exactamente como antes.

El único hueco real es la ventana, normalmente de una fracción de segundo, entre que se crea este ViewModel (arranca MainActivity) y que el sistema termina de llamar a PlaybackService.onCreate(): mientras tanto los StateFlow valen su valor por defecto y las llamadas se ignoran en silencio. No hay forma de evitar esa ventana del todo —arrancar un Service es asíncrono por diseño de Android—, pero en la práctica no da tiempo a que el usuario llegue a tocar nada antes de que se cierre.

Las clases de datos y constantes de nivel superior de este fichero (PlaybackProgress, CollectionKind, EqBand, EqPreset, BOOST_MIN_PERCENT/BOOST_LIMIT_PERCENT/BOOST_MAX_PERCENT) se han quedado aquí y no se han movido a PlaybackService.kt: son tipos que usa media aplicación (fragmentos, adaptadores, la pantalla de ajustes) para hablar de reproducción sin necesitar saber nada del Service, así que mudarlas habría obligado a cambiar el import en todos esos sitios sin ganar nada a cambio. PlaybackService las importa desde aquí, no al revés.

El motor de reproducción de verdad: dueño del ExoPlayer, de los seis efectos de audio (amplificador + ecualizador), de la cola en memoria y de su persistencia entre procesos — todo lo que antes estaba en PlayerViewModel (ver ahí arriba), trasladado aquí prácticamente sin cambios de fondo, más lo nuevo: la sesión y la notificación.

Por qué un Service y no un ViewModel

Un AndroidViewModel como el de antes vive mientras vive la Activity: en cuanto Android decide recuperar memoria quitando la aplicación de «recientes», su ViewModelStore se destruye (onCleared()) y con él el ExoPlayer, aunque el proceso siguiera vivo un instante más. Un Service en primer plano (con notificación activa) es la pieza que el sistema operativo respeta y no mata por presión de memoria; y android:stopWithTask="false" (ver AndroidManifest.xml) evita que cerrar la aplicación desde «recientes» se lleve el Service por delante si en ese momento está sonando algo.

Diseño · QueueAwarePlayer, por qué hace falta envolver el ExoPlayer

El diseño de toda la vida de UltiMusic es cargar una canción cada vez (player.setMediaItem, no setMediaItems) y decidir la siguiente con lógica propia — importante para la «cola suelta», que sigue con una canción al azar al agotarse, y para que next/skipToNext/skipToPrevious entiendan playlists, géneros, álbumes… Como el ExoPlayer de dentro por tanto nunca tiene más de un elemento en su propia lista, no sabe avanzar/retroceder por sí solo — y sin embargo, el botón «siguiente» de la notificación (y de la pantalla de bloqueo, y de unos auriculares Bluetooth) los maneja Media3 directamente sobre el Player de la sesión, sin pasar por ningún método de este fichero.

QueueAwarePlayer, una inner class privada que extiende ForwardingPlayer (la clase de Media3 pensada justo para esto: reenviar todo a un Player de dentro salvo lo que se pise), es el arreglo: sobreescribe seekToNext()/seekToNextMediaItem()/seekToPrevious()/seekToPreviousMediaItem() para llamar a skipToNext()/skipToPrevious() de este mismo Service en vez de al ExoPlayer de dentro, y hasNextMediaItem()/hasPreviousMediaItem() para que sepan responder según la cola real (una colección en su última canción no tiene «siguiente»; una cola suelta, al poder continuar al azar, siempre lo tiene). getAvailableCommands() e isCommandAvailable() hay que sobreescribirlos los dos —no basta con uno— porque ForwardingPlayer.isCommandAvailable() no se calcula a partir de getAvailableCommands(): reenvía sin más al ExoPlayer de dentro (así lo pide el propio javadoc de la clase). Es esta QueueAwarePlayer, y no el ExoPlayer desnudo, la que se le pasa a MediaSession.Builder en onCreate().

Al pulsar el mini-reproductor (en cualquier punto, no solo la flecha) sube desde abajo, de un tirón, una ventana a pantalla completa con forma de iPod Nano que cubre la app. Arrastrando el mini-reproductor hacia arriba en vez de pulsarlo, esta misma ventana sube en vivo con el dedo (ver MainActivity.setupMiniPlayerDrag): a mitad de arrastre se ve la mitad del iPod. Aparte de esos dos modos, el botón de la derecha de la cabecera activa el modo vídeo: la pantalla del iPod pasa a mostrar el videoclip (mudo) de la canción, sincronizado con el audio local, que sigue siendo la única fuente de sonido en todo momento. Diseño · refreshQueueHint(), el aviso bajo la carátula

queueHintBox (dentro de topBox, debajo de la última fila de la cola) lleva dos TextView: tvQueueCount («Quedan N canciones…») y tvQueueDuration (su duración conjunta, o el aviso que corresponda). La actual nunca se cuenta ni suma en la duración: solo lo que va detrás de currentIndex.

Vale para los dos adaptadores posibles de queueList: con queueAdapter (modo normal, la cola real) cuenta de verdad; con PlaylistQueueAdapter (modo navegación, ver más abajo) no hay nada que sonara todavía de esa colección, así que se limita a mostrar fijo R.string.ipod_choose_song («Elige una canción») con tvQueueCount oculto.

En modo normal, la palabra para el tipo de colección sale de PlayerViewModel.isLooseQueue/currentCollectionKind: «cola» (cola suelta), «playlist», «género», «álbum», «de este artista» o «de este productor» (un plurals distinto para cada una, más un genérico sin palabra para una colección sin tipo conocido). Igual que el antiguo aviso que sustituye, no se muestra u oculta en bloque: ocupa el hueco que quede libre en pantalla bajo la última fila (o toda la lista, si está vacía), midiendo su alto real con View.measure() y comparándolo con ese hueco; si no cabe, se oculta del todo. Por eso va en un post{} encadenado después del scroll que centra la fila actual, igual que refreshEndDivider. En modo navegación se llama desde renderSelected() (cursor y carga inicial) y desde el propio botón de 3 rayas cuando alterna carátula/lista; en modo normal, desde el collect de queue + currentIndex y desde ese mismo botón.

Modo navegación (playlist o género)

Se entra con newInstance(nombrePlaylist) (lo abre la pestaña de Listas) o con newInstanceForGenre(nombreGénero) (lo abre la pestaña de Géneros), salvo que esa misma colección ya sea la que suena ahora mismo (PlayerViewModel.currentPlaylistName coincide): en ese caso se abre directamente en modo normal, porque no tiene sentido "elegir" algo que ya está sonando.

Diseño · enterBrowseMode generalizada

Ambas entradas confluyen en la misma función privada, enterBrowseMode(collectionKey, reorderable, loadSongs, onReordered, ...): collectionKey es lo que se guarda en currentPlaylistName (para un género lleva un prefijo interno, "genre:", que evita que se confunda con una playlist del mismo nombre), loadSongs resuelve las canciones (la playlist en disco, o la biblioteca filtrada por género vía LibraryRepository.songsOfGenre) y reorderable/onReordered solo están activos para una playlist — ver «Reordenar» más abajo.

  • Un flag browsing solo afecta al colector de la cola real: se salta mientras se navega, porque el recuadro superior lo ocupa la lista de la colección en vez de la cola real. El resto de colectores (currentSong, isPlaying, progress, accentColor) no se gobiernan por este flag: siguen pintando lo que suena de verdad aunque la ventana esté en modo navegación, para no fingir nunca que «no hay nada sonando» si en realidad sí suena algo (de esta colección, de otra, o de una canción suelta reproducida desde Canciones/Álbumes/etc.).
  • El recuadro superior muestra la lista de la colección (con PlaylistQueueAdapter) en lugar de la carátula, para poder hacer scroll y pinchar.
  • Las 3 rayas, las flechas y el cursor dependen de si la canción que suena de verdad está en esta colección (PlaylistQueueAdapter.containsNowPlaying(), revisado en la función local refreshBrowseControls() cada vez que cambia la canción real):
    • No está → selección pura: 3 rayas es el icono de aleatorio (ic_shuffle, reproduce una canción al azar de la colección) y las flechas mueven el cursor (selectedIndex) por la lista sin reproducir nada (solo resalta la fila).
    • Sí está → no tiene sentido "elegir" nada, ya se está reflejando lo que realmente suena: 3 rayas alterna el recuadro superior entre carátula y lista (como en modo normal), y las flechas van a la canción anterior/siguiente de esta colección (calculado con nowPlayingIndex() ± 1) — no a skipToPrevious()/skipToNext() del PlayerViewModel, porque esos operan sobre la cola real genérica, que puede ser una colección totalmente distinta (p.ej. si sonaba una canción suelta desde Canciones, su "siguiente" real sería cualquier canción al azar de la biblioteca, no la de esta lista). Para ir a la fila de al lado se hace lo mismo que al pincharla: playCollection(currentSongs(), índice, collectionKey), saliendo de la navegación. El cursor pasa a seguir siempre a la fila que suena.
  • Al cargar la colección, si la canción que suena de verdad está en ella, el cursor arranca en su fila (no siempre en la primera). El recuadro de info, la carátula, el play/pausa y la barra de progreso siempre son los de la reproducción real, nunca los de la fila del cursor.
  • Elegir una fila o pulsar play normalmente llama a playCollection/shuffleCollection del PlayerViewModel pasándole collectionKey (una playlist o un género pasa a ocupar la cola al completo, como colección: se para al acabar en vez de seguir con algo al azar; la clave se guarda en currentPlaylistName), interrumpiendo lo que sonara antes. Pone browsing = false, cancela la corrutina que mantenía el altavoz/menú al día (browseJob), restaura los controles normales y la ventana pasa a ser el reproductor de siempre. Excepción: si la fila pinchada (o la del cursor, al pulsar play) es justo la que ya suena de verdad (isRowNowPlaying/isSelectedNowPlaying), reiniciarla no tendría sentido, así que en su lugar solo se alterna pausa/reproducción (togglePlayPause) sin salir de la navegación.
  • La barra de progreso (arrastrar/soltar) también funciona en modo navegación: siempre controla la reproducción real, esté o no la ventana navegando una colección.
  • Reordenar — solo playlists: cada fila lleva un manejador de arrastre; un ItemTouchHelper (solo vertical, iniciado desde el manejador) reordena en memoria y, al soltar, persiste el nuevo orden en el archivo con playlistsViewModel.reorder(nombre, ...). Un género no tiene ItemTouchHelper enganchado ni manejador visible (PlaylistQueueAdapter(reorderable = false)): no hay ningún orden propio que guardar, es sencillamente lo que traen las canciones.

Modo vídeo

El botón de la derecha de la cabecera cambia la pantalla del iPod por el videoclip (mudo) de la canción. Pulsándolo otra vez se vuelve exactamente a como estaba. El icono alterna entre una claqueta (ic_video) y una nota musical (ic_music_note) para indicar a qué se va a cambiar.

  • El audio de verdad nunca se pausa. A diferencia de una primera versión de este modo, el sonido lo sigue poniendo siempre el archivo local (ExoPlayer, en PlayerViewModel); el videoclip de YouTube es una capa puramente visual y muda (YouTubePlayer.mute()) que se limita a seguir la posición y el play/pausa del audio (ver VideoScreenController.sync()). Así no hay ningún hueco de silencio al entrar o salir del modo vídeo, ni nada que reconciliar al volver de segundo plano: el audio nunca dejó de sonar.
  • Al entrar (startVideo), se lee PlayerViewModel.currentPositionMs() y el estado de reproducción real, y se le pide al controlador que cargue el vídeo justo ahí (controller.load(videoId, posición, sonando, offsetMs)). Al salir (exitVideo) solo se pausa el vídeo (controller.pause()); el audio no se toca en ningún momento de la transición.
  • Sincronización continua, no un único traspaso. Mientras el modo vídeo está activo, los colectores de isPlaying y progress del PlayerViewModel siguen activos como siempre (no se saltan) y, además de pintar sus controles de costumbre, llaman a videoController.sync(...): al instante en cada cambio de play/pausa, y en cada tick de progreso del audio (unos 500 ms) para el vídeo. Ese segundo camino es el que autocorrige cualquier deriva acumulada (por ejemplo, al volver de segundo plano) sin que el usuario tenga que hacer nada. El play/pausa y la barra de progreso siguen gobernando solo el audio real; el vídeo los sigue por detrás.
  • Si cambia la canción, se sale solo del modo vídeo (comparando song.id con videoSongId en el colector de currentSong). El vídeo pertenece a una canción concreta: la siguiente puede no tener ninguno asignado todavía, y es el audio local el que sabe seguir la cola.
  • Al cerrar la ventana (onDestroyView) se libera el reproductor de YouTube (VideoScreenController.release()); el audio, que nunca dependió de él, sigue sonando sin más.
  • Los vídeos elegidos en el buscador se recuerdan también en un mapa en memoria (pickedVideoIds), además de guardarse en Room. Hace falta porque PlayerViewModel guarda una copia en memoria de las canciones de la cola y no observa la base de datos: el videoUrl recién escrito no aparece en currentSong hasta que la cola se reconstruye. Sin ese mapa, apagar y volver a encender el modo vídeo en la misma sesión abriría otra vez el buscador para una canción a la que ya se le había elegido vídeo.
  • El enlace sale de Song.videoUrl. Si está vacío, se abre el buscador para que el usuario elija el vídeo; al volver, se guarda en la canción con LibraryRepository.setVideoUrl y ya no se vuelve a preguntar. Esa misma llamada descarga también la miniatura del vídeo como carátula de reserva (ver CoverArt), igual que si el enlace se hubiera puesto desde el editor de metadatos. Si el enlace guardado no se puede interpretar, se avisa con un toast que remite al editor de metadatos.
  • Esquinas redondeadas. topBox (el recuadro superior) se recorta con clipToOutline + un ViewOutlineProvider propio que dibuja un rectángulo con las mismas esquinas redondeadas que ipod_display, para que el vídeo no asome esquinas rectas por fuera del marco: antes se intentó recortar directamente el YouTubePlayerView (ver VideoScreenController), pero su wrap_content no siempre coincidía con el tamaño real del recuadro y dejaba el redondeado descuadrado (esquinas de arriba bien, las de abajo no); recortar el contenedor entero vale igual en modo carátula (cuadrado) que en modo vídeo (16:9, ver animateAspectRatio) sin recalcular nada al cambiar de forma.
  • Ese recorte de topBox no basta para redondear cualquier cosa dentro. cover se ve bien porque una ShapeableImageView recorta su propio contenido con shapeAppearanceOverlay, sin depender del padre. queueList, en cambio, es un RecyclerView sin ese mecanismo propio: mientras no llevó fondo (antes del velo semitransparente que ahora se ve tras las 3 rayas), no se notaba que no estaba realmente recortado, porque no había nada sólido que asomara por las esquinas; en cuanto llevó un fondo visible, sus esquinas rectas se salían del marco redondeado. Por eso queueList lleva su propio clipToOutline + ViewOutlineProvider, con el mismo radio que topBox, en vez de fiarse del recorte del contenedor.

Ajustes del reproductor de vídeo

Mientras el modo vídeo está activo, el botón de las 3 rayas de la cabecera se sustituye por un engranaje (ver applyMenuButton): lo pulsa para abrir un AlertDialog corriente (con setView sobre dialog_video_settings.xml) con dos ajustes de la canción que suena, ambos ligados a esa canción y no globales:

  • URL del vídeo — el mismo campo que el editor de metadatos (no se escribe a mano: al tocarlo, estos ajustes se cierran y se abre el mismo buscador de YouTube que usa el botón de vídeo principal). El resultado lo recoge el mismo setFragmentResultListener ya registrado en onViewCreated para el buscador: guarda el enlace, actualiza pickedVideoIds y reinicia el vídeo con el id nuevo, sin necesidad de un listener aparte.
  • Desplazamiento — milisegundos que se adelanta o atrasa el vídeo respecto al audio (Song.videoOffsetMs), para videoclips que no van del todo sincronizados. Usa el mismo componente ValueRuler (regla arrastrable) que el amplificador de volumen sin límite, más una caja de texto para escribir el número a mano; los dos se mantienen sincronizados con la misma bandera «lo estoy cambiando yo» que usa SettingsDialogFragment. La regla se mueve en muescas de 100 ms (cada unidad suya vale VIDEO_OFFSET_STEP_MS, no 1 ms): con 1 ms por unidad, la separación fija entre marcas de ValueRuler obligaría a arrastrar metros para los cambios de unos pocos cientos de milisegundos que es el caso normal. La caja de texto, en cambio, admite cualquier milisegundo exacto; al escribir un valor que no sea múltiplo de 100, la regla se cuadra a la muesca más cercana. El rango va de −30.000 a +30.000 ms: como en el amplificador, el tope no es de diseño sino técnico (ValueRuler necesita un máximo), puesto lejísimos para no toparse con él sin querer.

Cada cambio de desplazamiento (arrastrando o escribiendo) se aplica y guarda al instante, sin botón de guardar: VideoScreenController.setOffset(...) reposiciona el vídeo en caliente para que el ajuste se note en tiempo real mientras suena la canción, y en paralelo se escribe en Room con LibraryRepository.setVideoOffsetMs. Igual que con pickedVideoIds, el valor elegido se recuerda también en un mapa en memoria (pickedVideoOffsets) por el mismo motivo: PlayerViewModel no observa Room, así que sin ese mapa reabrir los ajustes tras cambiar el desplazamiento (sin recargar la cola) mostraría el valor viejo.

Por qué no hay búsqueda automática del vídeo

La idea inicial era buscar el vídeo solo, por título y artista, y quedarse con el primer resultado. No se ha hecho, y el motivo no es técnico sino de la propia API de YouTube:

  • La cuota es por proyecto, no por usuario: 10.000 unidades diarias, y cada search.list cuesta 100. Son unas 100 búsquedas al día repartidas entre todos los que instalen la app. Ampliarla exige pasar una auditoría de conformidad de Google.
  • Los datos obtenidos de la API hay que borrarlos o refrescarlos cada 30 días, así que el identificador ni siquiera se podría guardar de forma permanente: habría que volver a gastar 100 unidades por canción cada mes.
  • Un enlace elegido por el usuario no tiene ninguna de las dos limitaciones (no es dato de la API) y además acierta más: el primer resultado de una búsqueda es muchas veces un lyric video, un directo o una versión que no es la buena.

De paso, esto encaja con la filosofía del proyecto: el usuario controla el dato, igual que con el resto de metadatos.

Estructura / flujo

  • Inicialización perezosa. En el XML el reproductor lleva enableAutomaticInitialization="false", que desactiva el arranque automático de la librería. Sin eso, el WebView interno se prepararía y descargaría el reproductor de YouTube nada más abrir el iPod, aunque el usuario nunca pulsara el botón de vídeo: gastaría datos para nada. Así solo se inicializa la primera vez que hace falta de verdad (ver load()).
  • Todo pasa por onReady. La librería no acepta órdenes hasta que su WebView ha cargado el reproductor, y eso tarda. Por eso load() guarda el vídeo en un campo pending si aún no ha llegado ese momento, y lo lanza en cuanto llega.
  • Sin los mandos de YouTube. El reproductor se arranca con IFramePlayerOptions.Builder(contexto).controls(0), que oculta la barra de controles propia de YouTube (play, progreso, título, compartir…). Sin eso, cada toque sobre el vídeo la hacía aparecer encima, y estorba: el iPod ya tiene sus propios mandos y son esos los que gobiernan el vídeo. Ojo con construir estas opciones: el Builder pide el contexto porque él solo rellena el origin con el paquete de la app, y si se pierde vuelve el error 152.
  • load(videoId, startMs, isPlaying, offsetMs) carga el vídeo desde startMs (la posición del audio local, más el desplazamiento — ver más abajo) y lo deja mudo. Si el audio local estaba en pausa, no se pausa en el mismo instante de pedir la carga (la pantalla se quedaría en negro: YouTube todavía no tiene ni un fotograma que enseñar), sino en cuanto llega el primer estado PLAYING de verdad (bandera pauseOnceStarted): así, al pausar, el WebView ya enseña su miniatura habitual con el HUD propio en vez de negro.
  • sync(targetPositionMs, targetIsPlaying) es lo que mantiene el vídeo pegado al audio: lo llama el iPod tanto al alternar play/pausa como en cada tick de progreso del audio local (unos 500 ms), así que también es lo que autocorrige cualquier deriva acumulada al volver de segundo plano, sin que el usuario tenga que hacer nada. Solo manda una orden nueva si el estado de play/pausa no coincide o si la posición se ha desviado más de driftThresholdMs (500 ms por defecto): pedir seekTo en cada tick, aunque no haga falta, dejaría el vídeo dando saltitos.
  • seekTo(positionMs) salta al instante, sin esperar al siguiente tick de sync: lo usa el iPod al soltar la barra de progreso tras arrastrarla.
  • Desplazamiento vídeo/audio (offsetMs). Todas las posiciones que load, sync y seekTo reciben son «posición del audio local»; internamente se les suma offsetMs (recortado a 0 como mínimo: YouTube no admite pedir un vídeo desde antes de su inicio) para obtener la posición real del vídeo. setOffset(newOffsetMs, currentAudioPositionMs) cambia ese desplazamiento en caliente y reposiciona el vídeo al instante, para que ajustarlo desde los ajustes del reproductor de vídeo se vea en tiempo real sin esperar al siguiente tick.
  • Ruedecilla de carga propia. El callback onLoadingChanged(true/false) avisa de si hay que tapar el WebView con una ruedecilla mientras se espera el primer aviso de estado de un vídeo recién pedido (bandera awaitingFirstState): en cuanto llega, YouTube ya pinta algo por su cuenta (su propia ruedecilla o el vídeo) y tener las dos a la vez sobraría.
  • hideCaptions() fuerza los subtítulos apagados llamando a player.unloadModule('captions') por JavaScript sobre el WebView interno (localizado a mano recorriendo el árbol de vistas, porque la librería no expone ninguna forma pública de llegar a él). Hace falta porque, sin mandos visibles, no hay botón «CC» con el que el usuario pueda quitarlos si el dispositivo tiene activados los subtítulos de accesibilidad de Android: ese ajuste del sistema hace que YouTube los pinte igual, ignorando el cc_load_policy por defecto de la librería. Un vídeo nuevo puede recargar su propio módulo de subtítulos, así que se repite en cada cambio de estado, no solo en onReady.
  • La librería trabaja en segundos con decimales y el resto de la app en milisegundos, así que aquí se hacen todas las conversiones (/ 1000f y * 1000).
  • release() es obligatorio y lo llama el iPod en onDestroyView: al desactivar la inicialización automática, la librería tampoco libera sola su WebView, que seguiría vivo consumiendo batería y datos.
  • Este archivo no recorta esquinas. El redondeado del vídeo lo hace topBox desde IPodDialogFragment (ver la lista de «Modo vídeo» más arriba), no aquí: aplicar clipToOutline sobre el propio YouTubePlayerView se probó y no servía en cuanto el vídeo se reproducía de verdad, porque su fotograma se pinta en una capa acelerada por hardware que ese recorte no alcanza (mismo motivo de fondo que el aviso de setLayerType de abajo).
Por qué el WebView no lleva setLayerType(LAYER_TYPE_SOFTWARE)

Un WebView reproduciendo vídeo suele promocionar el fotograma a una capa compuesta directamente por Android fuera del árbol de vistas (como una SurfaceView), así que queda siempre por encima de todo lo demás en la ventana sin importar el orden del XML. Forzarlo a capa de software (setLayerType(LAYER_TYPE_SOFTWARE, null)) lo devuelve al árbol normal y respeta el Z-order — pero deja el vídeo completamente en negro: Chromium no puede presentar un fotograma decodificado por hardware a través de una capa de software. Se probó, se confirmó el motivo por comparación directa (comentar la línea hace que el vídeo vuelva a verse) y se dejó comentada en el código como recordatorio.

Lo que YouTube deja y no deja hacer con su reproductor

Las condiciones de la API (Required Minimum Functionality) marcan dos límites que condicionan este archivo: «no debes mostrar superposiciones, marcos u otros elementos visuales delante de ninguna parte de un reproductor incrustado de YouTube, incluidos sus controles» y «no debes hacer cambios en el reproductor de YouTube que no estén descritos explícitamente en la documentación de la API».

De ahí salen las dos decisiones sobre la interfaz del reproductor. Los mandos se quitan con el parámetro controls=0, que sí está en la documentación y por tanto es un cambio permitido. Y los toques se bloquean con un contenedor que no los reparte a sus hijos (TouchBlockerFrameLayout), no tapando el vídeo con una vista transparente: eso último sería «un elemento visual delante del reproductor» y está prohibido aunque no se vea.

Nada en esas condiciones obliga a que el reproductor sea interactivo, así que dejarlo inerte y controlarlo desde los botones del iPod es correcto. La única regla sobre toques va en sentido contrario: prohíbe aprovecharlos para hacer algo en nombre del usuario (abrir ventanas, suscribirle a un canal…), que no es el caso.

Lo que no se puede quitar. Además de los mandos, el reproductor pinta una capa de marca con el avatar del canal, el título, el botón de compartir y el logo de YouTube. No hay ningún parámetro que la oculte: la documentación dice que «el avatar del canal y el título del vídeo siempre se mostrarán antes de que empiece la reproducción, cuando esté en pausa y cuando termine», y el antiguo modestbranding está obsoleto y no hace nada. Por eso esa capa se ve al entrar en el modo vídeo, hasta que arranca la reproducción, y se asume: se probó a retrasar la aparición del reproductor hasta que el vídeo estuviera rodando, pero eso dejaba la pantalla congelada varios segundos sin explicación, que se percibe como que la app se ha colgado. Ver la capa un momento es el mal menor. Lo que sí se evita es que reaparezca a mitad del vídeo, porque bloquear los toques impide pausarlo sin querer.

Los errores del reproductor: dos familias distintas

Cuando un vídeo no se reproduce, el motivo puede llegar por dos caminos que no hay que confundir:

  • Errores de la API, que llegan al callback onError y por tanto a nuestro onPlaybackError. Son solo seis, y la librería los traduce a la enumeración PlayerConstants.PlayerError: INVALID_PARAMETER_IN_REQUEST (código 2, identificador mal formado), HTML_5_PLAYER (5), VIDEO_NOT_FOUND (100, borrado o privado), VIDEO_NOT_PLAYABLE_IN_EMBEDDED_PLAYER (101 y 150 — el autor ha desactivado la reproducción embebida, habitual en videoclips de discográficas) y REQUEST_MISSING_HTTP_REFERER (153).
  • Errores internos del propio reproductor, que se pintan dentro del WebView como «Este vídeo no está disponible» con un código de dos partes tipo 152-4 o 152-15. Estos no pasan por onError: la app no se entera, el usuario solo ve el mensaje. La familia 152 significa que el reproductor no ha conseguido arrancar.

La causa típica del 152 es la identidad del incrustador: desde julio de 2025 YouTube exige que el reproductor embebido diga desde dónde se le está usando (origin / cabecera Referer), y un WebView de Android no lo manda por su cuenta. Por eso la app fija como mínimo la versión 13.0.0 de la librería, cuyo cambio principal es precisamente usar el paquete de la app como origin. Las versiones 12.x son anteriores a ese requisito y fallan con 152. Aun así el 152 puede seguir apareciendo en vídeos con restricciones de región, y contra eso lo único que se puede hacer es elegir otro vídeo.

YouTube no permite reproducir sus vídeos con un reproductor propio: hay que usar el suyo. La forma oficial en Android es cargar su reproductor web (el mismo que ves incrustado en cualquier página) dentro de un WebView, y hablarle por JavaScript. La librería android-youtube-player hace justo eso y nos lo presenta como una View de Android normal con callbacks en Kotlin, para no tener que escribir ese puente a mano.

Diseño · por qué forgetSong mira si la carpeta se puede leer

Antes de tocar nada, forgetSong comprueba library.libraryFolderReadable(). Si la carpeta de música no fuera accesible (permiso revocado, almacenamiento no montado…), todas las canciones parecerían perdidas y, pasando canciones, se irían vaciando las playlists una a una. Y una playlist es un archivo del usuario: al contrario que la base de datos, no se puede reconstruir volviendo a escanear. Por eso la comprobación va justo al lado de la acción destructiva.

Como los archivos no reemiten solos, se usa un MutableStateFlow<Int> (el «tick») como disparador: cada cambio lo incrementa y los flujos que dependen de él (con combine + mapLatest) vuelven a leer disco. mapLatest cancela el cálculo anterior si llega otro antes de acabar.

Buscador — ui/search/

La barra de la toolbar principal (donde antes iba el texto «UltiMusic») es el campo de búsqueda: no hace falta abrir nada aparte para escribir. Al tocarla se escribe un texto y aparecen, en este orden, las canciones, los álbumes, los artistas y los productores cuyo nombre lo contiene, cada grupo bajo su propia cabecera de sección. Un grupo sin resultados no enseña ni su cabecera.

Los resultados se recalculan letra a letra, sin botón de «buscar». La comparación ignora mayúsculas y tildes (ver TextSearch.kt), así que cancion encuentra «Canción» y bjork encuentra «Björk».

Se busca por el nombre visible de cada cosa: el título de la canción, el del álbum, el nombre del artista o del productor. Una canción no sale por el nombre de su artista, porque para eso está la sección de artistas: su ficha ya lista todas sus canciones. Así cada resultado significa una única cosa y la lista no se llena de repeticiones.

ui/search/SearchViewModel.ktAndroidViewModel · consulta y resultados

El cerebro del buscador. Vive en el ámbito de MainActivity (by viewModels()), no en el de un diálogo: como la búsqueda ya no abre una ventana aparte (ver SearchBarController más abajo), el ViewModel tiene que sobrevivir a que el usuario colapse el buscador y vuelva a abrirlo sin perder la consulta.

Kotlin · sealed interface (jerarquía cerrada)

SearchResult es una sealed interface: una familia de tipos cerrada, de la que solo pueden existir los cuatro que se declaran ahí mismo (Header, SongRow, AlbumRow, PersonRow). Eso permite meter cosas de naturaleza distinta en una sola lista y que el adaptador decida qué pintar con un when que el compilador comprueba que está completo: si mañana se añade una quinta sección, el código que la olvide no compila. La alternativa —cuatro listas y cuatro RecyclerView— rompería el scroll continuo de la pantalla.

¿Por qué filtrar en Kotlin y no con SQL?

Por dos razones. La primera es que el LIKE de SQLite solo ignora mayúsculas en el alfabeto inglés (no sabe que «Á» y «á» son la misma letra) y no tiene ninguna noción de tildes. La segunda es que la biblioteca ya está entera en memoria para pintar las pestañas, así que recorrerla es cuestión de milisegundos y no hace falta ir al disco. Aun así, el filtrado se manda a un hilo de cómputo con flowOn(Dispatchers.Default), para que teclear deprisa no atasque la interfaz.

Como los cuatro flujos son reactivos, los resultados se corrigen solos: si con el buscador abierto se edita el título de una canción o termina una reconciliación, la lista se repinta sin volver a escribir nada.

¿Se puede saltar el límite de volumen de Android?

No del todo, y conviene tener claro qué se puede y qué no:

  • El 100 % del volumen del sistema es el máximo de la escala de Android. Una aplicación normal no puede subirlo por encima: ese tope lo fija el sistema y el driver de audio.
  • El aviso de «volumen alto» que sale con auriculares en los móviles europeos (normativa EN 50332) también es del sistema. Ninguna aplicación puede quitarlo.
  • Lo que sí puede hacer una aplicación es amplificar su propio sonido antes de que salga, para que dentro de ese 100 % suene más fuerte de lo que sonaría sin tocarlo. Eso es exactamente lo que hace el amplificador de UltiMusic.

La herramienta es LoudnessEnhancer, un efecto de audio de Android que se engancha a la sesión de audio de un reproductor y le añade ganancia con compresión de rango dinámico (comprime los picos, para que subir el volumen no lo rompa en distorsión). No hace falta root ni ningún permiso peligroso: solo MODIFY_AUDIO_SETTINGS, que es un permiso normal y el sistema concede al instalar.

El problema de los tres controles que muestran lo mismo

Slider, regla y caja de texto enseñan el mismo número, así que al mover uno hay que actualizar los otros dos. Hecho sin cuidado, eso es un bucle infinito: el slider avisa de que ha cambiado → se escribe en la caja → la caja avisa de que ha cambiado → se mueve el slider → …

La solución es una bandera, updatingUi. Mientras vale true, los avisos de los controles se ignoran: significa «este cambio lo he provocado yo al repintar, no el usuario». Es el mismo truco que usa el editor de metadatos y una pieza clásica de cualquier interfaz con controles espejados.

El slider tiene además su propio mecanismo para lo mismo, el parámetro fromUser de addOnChangeListener, que distingue moverlo con el dedo de moverlo por código.

Detalle de la caja de texto: mientras se teclea «120» se pasa por «1» y por «12». Corregir eso al vuelo al mínimo sería pelearse con el usuario, así que solo se aplica lo escrito cuando ya es un número válido (≥ 100), y lo que quede fuera de rango se cuadra al terminar — al pulsar «hecho» en el teclado o al perder el foco.

Los mandos se tiñen con el color de la canción que suena, igual que las pestañas y el mini-reproductor (ver DynamicColor). Lo mismo hacen los tres títulos de sección («Amplificador de volumen», «Lista gris», «Ecualizador», antes amarillo fijo del XML) y el interruptor maestro del ecualizador (eqSwitch): todos se repintan en el mismo accentColor.collect. Los switches de cada fila de la lista gris los tiñe GreylistAdapter por su cuenta, ver ahí.

Las dos casillas (noLimitCheck, additionalOptionsCheck) llevan app:rippleColor="@color/um_ripple_white" fijo en el XML (MaterialCheckBox.setRippleColor existe pero es private, así que no se puede pisar desde código), y eqSwitch lleva android:theme="@style/ThemeOverlay.UltiMusic.SwitchRippleWhite", también en el XML. El amplificador por dentro

La lógica de audio no está en el fragmento sino en PlayerViewModel, que es donde vive el ExoPlayer. Lo que hay allí:

  • loudnessEnhancer — el efecto, enganchado a player.audioSessionId. Es nullable y se crea dentro de un try/catch porque hay móviles y emuladores sin este efecto: si falla, la aplicación sigue funcionando exactamente igual, solo que sin amplificar. Además solo existe mientras hace falta: applyBoost() lo crea la primera vez que el amplificador sube de 100 % y lo suelta (release()) en cuanto vuelve a 100 %, en vez de crearlo una vez en init y dejarlo enganchado (apagado) para siempre — ver el recuadro «Por qué los efectos se crean bajo demanda» más abajo.
  • volumeBoost y limitDisabled — el estado, en StateFlow, persistido en unas SharedPreferences propias (audio_settings), aparte de las de la reproducción porque son cosas distintas.
  • setVolumeBoost(percent) — recorta el valor siempre, venga de donde venga: nunca por debajo de 100 y, con el límite puesto, nunca por encima de 150. Así el tope no depende de que la interfaz se acuerde de respetarlo.
  • setLimitDisabled(disabled) — devuelve por qué no se ha podido quitar el límite: Check.NONE significa que sí se ha aplicado, y cualquier otro valor que se ha rechazado. Devolver el motivo y no un simple false es lo que permite a la pantalla de ajustes reaccionar distinto ante «hay auriculares» y ante «hay un Bluetooth que no puedo identificar». Al volver a poner el límite, recorta la amplificación si se había pasado.
  • applyBoost() — traduce el porcentaje y se lo da al efecto.
De porcentaje a milibelios: amplitud contra percepción

LoudnessEnhancer no trabaja en porcentajes sino en milibelios (mB), o sea décimas de decibelio. La conversión merece explicación porque la respuesta «obvia» está mal, y de hecho la primera versión de esto la tenía mal.

Un decibelio mide amplitud, y multiplicar la amplitud de la onda por un factor son 20 · log10(factor) decibelios. Con esa cuenta, el 150 % serían 3,5 dB. Es la fórmula correcta… para la física de la onda.

El problema es que el oído no percibe la amplitud, sino algo mucho más comprimido. La regla estándar de psicoacústica (la escala de sonios) dice que hacen falta +10 dB para que algo suene el doble de fuerte, no los ~6 dB que doblan la amplitud. Así que aquellos 3,5 dB, que sobre el papel eran «una vez y media», el oído los registraba como un 10 % largo: técnicamente impecable y prácticamente inútil.

Como el número que ve el usuario tiene que significar lo que oye, se usa la escala de la percepción, que es la inversa de la regla de los sonios (percepción = 2^(dB/10)):

dB = 10 · log2(factor)

Aun así es el estándar de la industria y se acerca muchísimo más a lo que uno oye que la fórmula de la amplitud.

Diseño · por qué los decibelios no se le enseñan al usuario

Hubo una versión que escribía «+5,9 dB sobre el volumen normal» debajo del mando. Se quitó, y el motivo merece quedar escrito porque es fácil querer volver a ponerlo.

Ese número son los decibelios añadidos, no el volumen que llega al oído. El absoluto la app no puede saberlo: depende del volumen del sistema, de la sensibilidad de los auriculares y hasta del contenido de la canción. Y un usuario sin ningún punto de referencia no puede hacer nada con «+5,9 dB»: no le dice si está en terreno seguro ni cuánto le queda por subir. Como dato aislado no informa, solo decora — y peor aún, se puede confundir con el nivel absoluto y dar una falsa sensación de seguridad.

Con el amplificador al 100 % el efecto se suelta del todo (ver el recuadro de abajo) en vez de dejarlo creado con ganancia 0: quien no lo use no tiene ningún procesado de audio de por medio, y tampoco ocupa sitio en el procesador de efectos del sistema.

Por qué los efectos se crean bajo demanda (y no una vez en init)

La primera versión de esto creaba los seis efectos (LoudnessEnhancer y los cinco del ecualizador) una vez en init y los dejaba enganchados a la sesión de audio toda la vida de la aplicación, apagándolos con enabled = false cuando el usuario no los usaba. El fallo: un AudioEffect enganchado ocupa un hueco del procesador de efectos del sistema aunque esté apagado, y ese procesador es un recurso compartido con el resto de aplicaciones del móvil, no algo privado de UltiMusic. Con los seis siempre enganchados —los usara el usuario o no— UltiMusic ocupaba de más ese recurso compartido; en algunos dispositivos, tener otra aplicación de audio abierta a la vez (YouTube, Instagram…) agotaba el hueco compartido y dejaba **sin sonido a las dos aplicaciones**, no solo a UltiMusic, hasta que se cerraba una de las dos.

La solución es crear cada efecto solo mientras está activo y soltarlo (release()) en cuanto se apaga, en vez de crearlo una vez y limitarse a alternar enabled:

  • applyBoost() crea loudnessEnhancer la primera vez que el amplificador sube de 100 % y lo suelta al volver a 100 %.
  • ensureEqEffects() crea los cinco efectos del ecualizador cuando se enciende eqEnabled; releaseEqEffects() los suelta al apagarlo. Las llama applyEq(), que es quien decide si tocan crearse o soltarse.
  • Lo único que se sigue calculando una vez, en init, es probeEqCapabilities(): crea cada efecto un instante para preguntarle sus límites (número de bandas, rangos, si soporta fuerza variable…) y lo suelta enseguida, antes de que la pantalla de ajustes exista siquiera. No hace falta dejarlo enganchado solo para saber sus límites — esos no cambian.

Esto no cambia nada para quien no usa el amplificador ni el ecualizador: por defecto (100 %, ecualizador apagado) UltiMusic no tiene ningún efecto de audio enganchado a su sesión.

La protección de los auriculares

Quitar el límite solo se permite cuando el sonido sale al aire, porque directo al oído puede dañarlo de verdad. Ojo al matiz: lo que descalifica no es «tener algo conectado» sino que ese algo vaya en la oreja. Con un altavoz Bluetooth o el coche sí se puede quitar; distinguirlos es trabajo de Headphones.kt, que devuelve tres respuestas en vez de un sí/no.

Comprobarlo una vez, al marcar la casilla, no basta: alguien podría subir al 400 % por altavoz y enchufar los cascos después, con la música ya sonando. Por eso el ViewModel registra un AudioDeviceCallback en el AudioManager, que avisa cada vez que aparece una salida de audio nueva. Si aparece un auricular con el límite quitado, el límite se repone solo y se emite limitForcedByHeadphones para que la pantalla de ajustes lo cuente, si está abierta. La vigilancia vive en el ViewModel y no en el fragmento justamente para que funcione esté esa pantalla abierta o cerrada.

En esa vigilancia, un Bluetooth sin identificar cuenta como auriculares: puede saltar con la app en segundo plano, donde no hay a quién pedirle ningún permiso, así que se protege el oído. En la pantalla de ajustes, en cambio, sí se le ofrece al usuario conceder el permiso y se reintenta.

El callback se da de baja en onCleared(), junto con el release() del efecto: los efectos de audio son un recurso escaso del sistema y, si no se sueltan, se acaban agotando.

El ecualizador por dentro

Tampoco está en el fragmento sino en PlayerViewModel, junto al amplificador y enganchado a la misma sesión de audio del ExoPlayer — solo mientras está activado, ver «Por qué los efectos se crean bajo demanda» arriba. Son cinco efectos más de android.media.audiofx, todos nullable y creados dentro de un try/catch por el mismo motivo que LoudnessEnhancer: hay móviles y emuladores sin ellos.

  • Equalizer — sube o baja el volumen de bandas de frecuencia concretas, en milibelios. numberOfBands, bandLevelRange y getCenterFreq(banda) los decide el propio dispositivo, no son un número fijo de la aplicación: por eso eqBands (una lista de EqBand(centerFreqHz, minLevelMb, maxLevelMb)) se calcula una única vez en probeEqCapabilities() (llamada desde init) leyendo esas propiedades de un Equalizer temporal, y es lo que usa la pantalla de ajustes para construir sus sliders verticales en código.
  • BassBoost («refuerzo de graves») y Virtualizer («sonido envolvente», ensancha el estéreo simulando altavoces separados) no tienen bandas: cada uno tiene una única fuerza de 0 a 1000 (setStrength()). PlayerViewModel la expone como porcentaje (0-100), igual que el resto de la aplicación, y multiplica por 10 al aplicarla. Si el dispositivo no admite variar esa fuerza (getStrengthSupported() == false), bassBoostSupported/virtualizerSupported quedan en false y la pantalla de ajustes deshabilita ese slider en concreto.
  • PresetReverb («reverberación») simula el eco de un espacio (habitación, sala, auditorio…). A diferencia de los dos anteriores no tiene una fuerza continua: solo admite elegir una sala entre sus siete constantes (PRESET_NONE..PRESET_PLATE), así que reverbPreset guarda un índice (0 = «Ninguno», apaga el efecto) sobre reverbPresetNames, una lista de nombres escrita a mano en PlayerViewModel.kt (son nombres de una API de Android, no texto traducible de la interfaz — igual criterio que predefinedPresetNames).
  • DynamicsProcessing («compresor de rango dinámico») sube el sonido flojo y baja el fuerte en tiempo real, algo que ningún ajuste estático (bandas, refuerzos, ganancia maestra) puede hacer. Es el más complejo de los cinco: solo existe desde Android 9 (API 28), así que se comprueba Build.VERSION.SDK_INT antes de crearlo, y no viene con una configuración por defecto útil — hay que construirlo con un DynamicsProcessing.Config que le dice de antemano cuántos canales tiene (2, a capón: el audio de ExoPlayer es casi siempre estéreo y no merece la pena leer el formato real) y qué «etapas» quiere usar (aquí solo el compresor multibanda, con una única banda que cubre todo el espectro, más un limitador de seguridad para que la compresión no sature). dynamicsStrength (0-100 %) se traduce a los parámetros de esa banda en buildCompressorBand(): a más fuerza, el umbral baja (de −10 a −30 dB) y la razón sube (de 1:1, sin comprimir, a 4:1), con una ganancia de compensación de hasta +6 dB.
  • eqEnabled — un único interruptor para los cinco efectos: no tiene sentido tener el ecualizador «a medias». setEqEnabled(enabled) cambia eqEnabled y llama a applyEq(), que crea los cinco efectos (ensureEqEffects()) o los suelta (releaseEqEffects()) según toque.
  • eqBandLevels, bassBoostStrength, virtualizerStrength, reverbPreset, dynamicsStrength, eqPreGain — el estado, en StateFlow, persistido en las mismas SharedPreferences del amplificador (audio_settings): una banda por clave (eq_band_0, eq_band_1...) más eq_enabled, bass_boost, virtualizer, reverb_preset, dynamics_strength y eq_pre_gain.
  • setEqBandLevel(banda, mB), setBassBoostStrength(%), setVirtualizerStrength(%), setReverbPreset(índice), setDynamicsStrength(%), setEqPreGain(%) — tocan solo el control que ha cambiado (y llaman a markEqAsModified(), ver abajo). applyEq(), en cambio, aplica todo de golpe a los cinco efectos: la usan el arranque de la aplicación, el interruptor maestro y resetEqualizer() (todas las bandas y los cuatro refuerzos a cero, la ganancia maestra a su punto neutro del 50 %).

EqPreset (ver abajo) sigue empaquetando solo bandas, refuerzo de graves y envolvente, no reverberación ni compresor: aplicar un preset (de fábrica o guardado) no toca esos dos, se quedan como estuvieran. Es una limitación consciente para no rehacer los ocho presets de fábrica al añadirlos; si se quiere que formen parte del preset, hay que extender EqPreset, createPredefinedPresets() y la persistencia de userPresets.

La ganancia maestra: un desplazamiento que no se guarda por banda

eqPreGain (0-100 %) no es una banda más: es un desplazamiento en milibelios que se suma a las eqBandLevels guardadas al mandarlas de verdad al hardware, en vez de guardarse banda por banda. Es bipolar: preGainMb() = (eqPreGain − 50) × 20, así que el 50 % (su valor por defecto) es el punto neutro (0 mB, sin efecto), 0 % son −1000 mB (−10 dB) y 100 % son +1000 mB (+10 dB) — el control sirve tanto para subir como para bajar el conjunto, no solo para subirlo. effectiveBandLevel(índice, nivel) es quien hace esa suma y recorta el resultado al rango de esa banda concreta (eqBands[índice]), y la usan tanto applyEq() como setEqBandLevel() para que las dos vías de aplicar una banda den siempre el mismo resultado. Así, mover la ganancia maestra desplaza toda la curva del ecualizador sin tocar lo que marca cada slider de banda — y no hace falta que esos sliders se muevan para reflejarlo, porque su posición ya es solo un indicador relativo dentro del rango de su propia banda (no muestran ningún número). Útil para compensar cuando se han subido muchas bandas a la vez y el conjunto empieza a saturar, o para bajar el ecualizador entero sin tocar banda por banda.

Presets: predefinidos, guardados por el usuario y el aviso «Usuario»

EqPreset(nombre, bandLevels, bassBoostStrength, virtualizerStrength) es la clase de nivel superior (fuera de PlayerViewModel, en PlayerViewModel.kt) que empaqueta un preset entero. Hay dos fuentes:

  • predefinedPresets — ocho de fábrica (Plano, Rock, Pop, Jazz, Clásica, Heavy Metal, Hip-Hop, Dance), calculados en createPredefinedPresets() después de conocer eqBands: sus valores son proporciones fijas sobre bandas concretas (graves, agudos…) que se adaptan al número de bandas real del dispositivo. predefinedPresetNames expone solo los nombres, en orden, para que la pantalla de ajustes construya el desplegable sin conocer la clase EqPreset.
  • userPresets — los que el usuario ha guardado él mismo con saveUserPreset(nombre), persistidos en audio_settings con un contador (user_preset_count) y cuatro claves por preset (nombre, niveles de banda unidos por comas, refuerzo de graves y envolvente). restoreUserPresets() los recompone en init, descartando cualquiera cuyo número de bandas ya no cuadre con eqBands (por ejemplo, tras reinstalar en un dispositivo distinto).

applyPreset(nombre) busca primero en los predefinidos y luego en los del usuario, y recorta sus valores al rango real de este dispositivo antes de aplicarlos — un preset guardado en otro móvil, con otro rango de bandas, no debería poder mandar milibelios fuera de lo que este ecualizador admite. markEqAsModified() es la otra mitad del mecanismo: cualquier set* tocado a mano pone currentPresetName en «Usuario» (una constante de fichero, USER_MODIFIED_PRESET_NAME) si no lo estaba ya, para que el desplegable refleje que hay cambios sin guardar. Elegir «Usuario» a mano en el desplegable no hace nada: applyPreset() no encuentra ningún preset con ese nombre y no toca nada.

Los tres efectos de audio se liberan en onCleared() junto con loudnessEnhancer y el propio player: son el mismo tipo de recurso escaso del sistema.

Un toque no llega directamente a la vista tocada: baja desde la de más arriba hacia sus hijos, y cada contenedor puede quedárselo por el camino. ui/common/ScrollbarDrag.ktfunción de extensión · barra de scroll propia (estilo Phonograph)

Función de extensión para RecyclerView: recycler.attachScrollbarDrag { posición -> letra }, o recycler.attachScrollbarDrag() a secas si no se quiere la burbuja de la letra. La barra de scroll nativa de Android tiene dos problemas para lo que se quería aquí: solo se deja agarrar con el dedo si la lista ya estaba en movimiento, y su grosor es proporcional a cuánto ocupa lo visible sobre el total (en una lista larga se vuelve un hilo). Por eso esta función no usa la barra nativa en absoluto — los XML de las listas afectadas llevan android:scrollbars="none" — y la sustituye por una vista propia, calcada del comportamiento de ~/Phonograph (que a su vez usa una librería de terceros para esto; aquí se reimplementó a mano para no añadir esa dependencia).

  • El "pulgar" (thumb) y la burbuja de letra (bubble) son dos View/TextView que la función crea por código y añade como hermanas del RecyclerView dentro de su ViewGroup padre (por eso los seis layouts que la usan meten el RecyclerView en un FrameLayout propio: hace falta un padre donde colgar estas dos vistas). Se posicionan con translationY, no con layout, porque se mueven en cada evento de scroll o de arrastre y recolocar con layout a esa frecuencia sería mucho más caro.
  • Tamaño fijo: el pulgar mide siempre 8dp de ancho por 48dp de alto (THUMB_WIDTH_DP / THUMB_HEIGHT_DP), sea cual sea la longitud de la lista — al contrario que la barra nativa, aquí no depende de la proporción visible/total. Los 8dp son a propósito los mismos que la pista del SeekBar de las canciones (res/drawable/seekbar_line.xml), para que las dos barras de la app tengan el mismo grosor.
  • La burbuja es un cuadrado fijo de 80dp (BUBBLE_SIZE_DP) con radio de esquina de media anchura, que es lo que la convierte en círculo perfecto; la letra va a 32sp. No es WRAP_CONTENT justamente para que su altura no cambie según la letra que toque, porque de esa altura depende la alineación con el pulgar.
  • Pulgar y burbuja comparten centro. Miden distinto (48dp y 80dp), así que si cada uno se colocara por su borde superior acabarían descuadrados en los extremos — que era el fallo que se veía: al llegar abajo del todo el círculo quedaba por debajo del pulgar, y arriba por encima. Ahora moveThumbTo(fracción) calcula un solo centro y de él cuelga a los dos (centro − altura/2 cada uno). El recorrido de ese centro deja de margen arriba y abajo media altura del más alto de los dos (halfTallestPx), así que ninguno se sale de la lista jamás.
  • No siempre visible: el pulgar nace con alpha = 0f y solo se enseña (showThumb()) al hacer scroll o al empezar a arrastrar; al cabo de un segundo sin actividad (AUTO_HIDE_DELAY_MS) se vuelve a ocultar solo, con un Handler que se reprograma (scheduleHide()) cada vez que hay actividad nueva.
  • Hitbox siempre activo: en el ACTION_DOWN se comprueba si el toque cae en la franja de la derecha (event.x >= width - hitboxWidthPx) sin mirar si el pulgar está visible en ese instante — por eso se puede empezar a arrastrar aunque la barra esté oculta. Sí se comprueba isScrollable() (que haya algo que desplazar): si la lista es tan corta que no hace falta scroll, el toque no se intercepta y llega normal a los elementos de debajo.
  • Se escucha con addOnItemTouchListener, no con setOnTouchListener (ver el recuadro de abajo): con lo segundo la barra solo agarraba si la lista ya venía moviéndose, que era exactamente el fallo que se arrastraba. Al quedarse el gesto también se llama a parent.requestDisallowInterceptTouchEvent(true), para que un temblor horizontal del dedo no le haga cambiar de pestaña al ViewPager2 que hay por encima.
  • Un toque suelto en la franja (sin arrastrar) no mueve la lista: el salto solo se calcula en los ACTION_MOVE. Lo que sí hace el DOWN es quedarse el gesto, así que ese toque tampoco reproduce la canción que hubiera debajo.
  • hitboxWidthDp (24dp por defecto) es deliberadamente más ancho que el pulgar visible (6dp): la zona donde "se nota" que hay barra para agarrar es mayor que lo que se ve, para no obligar a apuntar con precisión de píxel.
  • En ACTION_MOVE, la fracción vertical del toque (event.y / height) se traduce a una posición del adaptador (itemCount * fracción) y se llama a layoutManager.scrollToPositionWithOffset(posición, 0). Sirve igual para una lista (LinearLayoutManager) que para una rejilla (GridLayoutManager, que es subclase de aquel), porque el cálculo es por fracción de altura, no por filas.
  • Letra al arrastrar: en cada ACTION_MOVE se rellena la burbuja con sectionFor(posición) — la lambda que pasa cada pantalla — y se coloca pegada al pulgar (no a la altura exacta del dedo). sectionFor vive en cada fragment porque solo él sabe qué campo mostrar (el título de la canción/álbum, el nombre de la persona o de la playlist); la función sectionLetter(texto) de este mismo archivo hace el trabajo común (primera letra, en mayúscula, o "#" si no hay texto).
  • La burbuja es opcional. sectionFor tiene valor por defecto null, y si no se pasa, el TextView del círculo ni se crea ni se añade al layout: queda solo el pulgar arrastrable. Es lo que hace el buscador, donde los resultados no están en orden alfabético sino agrupados por secciones y una letra no significaría nada. Como efecto secundario, sin burbuja el margen que la barra deja arriba y abajo (halfTallestPx, media altura del más alto de los dos) se reduce de 40dp a 24dp, así que el pulgar recorre algo más de pantalla.
  • Devuelve un ScrollbarController con setAccentColor(color) para que el pulgar y la burbuja (si la hay) sigan el color dinámico (ver DynamicColor).   • Se usa el acento a plena intensidad, como las pestañas o la barra de progreso, y no la versión apagada DynamicColor.asBackground(...): esa es solo para fondos que llevan texto encima (la cabecera de la ficha), no para un elemento de primer plano.

Android · quién se queda el toque

Un ViewGroup (y un RecyclerView lo es) reparte cada toque en este orden: primero se pregunta a sí mismo si quiere quedárselo (onInterceptTouchEvent), y si dice que no, se lo pasa a sus hijos. El OnTouchListener del contenedor solo entra en juego al final, cuando ningún hijo se lo quedó.

Ahí estaba el fallo original de esta barra: escuchaba con setOnTouchListener, y como las filas son clicables (tocar una canción la reproduce), la fila se quedaba el ACTION_DOWN y la barra nunca se enteraba de que empezaba un arrastre. Solo funcionaba si la lista ya venía moviéndose, porque en ese caso el RecyclerView intercepta el toque de entrada (para frenar el scroll) y entonces sí llegaba al listener.

La solución es addOnItemTouchListener: es el mecanismo que ofrece el propio RecyclerView para mirar el toque antes que los hijos (se consulta dentro de su onInterceptTouchEvent). Si el listener devuelve true en el DOWN, el RecyclerView le adjudica el gesto entero — manda un ACTION_CANCEL a la fila que lo estuviera recibiendo, para que no se quede «pulsada» ni dispare su click — y el resto del gesto llega por su onTouchEvent.

Este comportamiento está cubierto por un test instrumentado (ScrollbarDragTest), que arrastra la barra con la lista parada y comprueba que la lista salta a donde toca.

ui/common/ValueRuler.ktView personalizada · regla de arrastre

Una cinta métrica horizontal: marcas y números que se mueven con el dedo bajo un indicador fijo en el centro. Lo que quede bajo el indicador es el valor elegido.

La usa la pantalla de ajustes como sustituto del slider cuando se desactiva el límite del amplificador, y también el desplazamiento vídeo/audio del reproductor de vídeo del iPod (que no usa slider en ningún momento: el rango con sentido ahí ya es demasiado grande para uno). El motivo de fondo es que un slider dibuja su recorrido, así que necesita un máximo cercano para que el dedo tenga un rango cómodo; cuando el rango se dispara, un píxel pasaría a valer decenas de unidades y el slider se vuelve inservible. Una cinta que se arrastra no tiene ese problema: el recorrido es tan largo como haga falta.

Por qué una View propia y no un RecyclerView

La idea de «lista horizontal larguísima» en Android sería un RecyclerView horizontal, con su adaptador y su snap helper. Pero aquí no hay elementos que reciclar — solo rayas y números —, así que sale bastante más simple dibujarlo a mano: se guarda cuánto se ha arrastrado y se pintan solo las marcas que caen dentro de la pantalla. Da igual lo lejos que se llegue: siempre se pintan las mismas ~30 rayas.

Lección aprendida · «infinito» no puede ser literal

La primera versión de esta clase se llamaba InfiniteValueRuler y no tenía máximo, porque la idea era «que se pueda arrastrar indefinidamente». Estaba rota: bastaba arrastrar con un poco de impulso para que el ajuste saltara a números como 148.888.880 % y se quedara pillado ahí.

Fallaban dos cosas a la vez, y las dos son trampas clásicas al escribir una View:

  • Precisión de la coma flotante. Un Float guarda unos 7 dígitos significativos. Pasados unos 16 millones, sumarle el arrastre del dedo no cambia nada: el número es tan grande que el incremento se pierde al redondear. El ajuste se queda congelado en un valor absurdo.
  • Desbordamiento al pasar a Int. El cálculo de la inercia trabaja en enteros, y se le pasaba Int.MAX_VALUE como tope. Al convertir un desplazamiento gigantesco a Int, el número se satura en ese máximo en vez de dar error, así que el fallo pasaba desapercibido en vez de reventar.

La conclusión: «arrastre sin tope» es una idea de interfaz, no de aritmética. El tope tiene que existir; lo que tiene que hacer es estar lo bastante lejos como para que no se note. Ahora la clase tiene maxValue, el amplificador lo pone en BOOST_MAX_PERCENT (1000 %, unos 33 dB — muy por encima de cualquier uso real), y llegar hasta ahí arrastrando son varios metros de dedo.

Estructura / flujo

  • Todo el estado es un único número, scrollPx: cuántos píxeles se ha desplazado la cinta desde minValue. De ahí sale el valor (minValue + scrollPx / pxPerUnit) y de ahí sale dónde va cada marca al dibujar. Se mantiene siempre dentro de 0..maxScrollPx.
  • onDraw calcula qué unidades caben en el ancho de la vista y pinta una raya por cada una: pequeña y gris las normales, grande y del color de acento las múltiplos de 10, que además llevan su número debajo. El indicador central se dibuja al final, encima.
  • onMeasure le da un alto por defecto de 64 dp, lo justo para las marcas y sus números, si nadie dice otra cosa desde el XML.
  • Al soltar, la cinta se cuadra con la marca entera más cercana (snapToNearest) para no quedarse a medio camino entre dos números.
Android · GestureDetector y OverScroller

GestureDetector traduce la lluvia de MotionEvent a gestos con sentido: aquí interesan onScroll (el dedo arrastra: da cuántos píxeles se ha movido) y onFling (el dedo se suelta con impulso: da la velocidad). Sin él habría que medir distancias y velocidades a mano dentro de onTouchEvent.

Cuidado con los signos, que no coinciden entre los dos: distanceX es positivo cuando el dedo va hacia la izquierda, mientras que velocityX es positivo cuando va hacia la derecha. Por eso en onFling la velocidad lleva un menos delante y en onScroll la distancia no.

OverScroller calcula la inercia: se le dice la posición y la velocidad iniciales y él va diciendo, fotograma a fotograma, dónde debería estar la cinta mientras frena sola. Es la misma pieza que usan las listas de Android, así que el tacto es idéntico al del resto del sistema.

La trampa de computeScroll()

computeScroll() es el bucle de animación: Android lo llama en cada fotograma que se dibuja, se lee la posición del scroller, se redibuja y se pide el siguiente fotograma con postInvalidateOnAnimation hasta que la inercia se agota.

Lo que es fácil pasar por alto —y aquí también estaba mal al principio— es que se llama siempre, no solo mientras hay animación. La primera versión aprovechaba la rama del «ya no hay inercia» para encajar la cinta con la marca más cercana, y eso significaba intentar el encaje en cada dibujado, sin que nadie lo hubiera pedido. Como con la coma flotante el desfase nunca llega a ser exactamente cero, el encaje se reprogramaba a sí mismo indefinidamente.

La solución es la bandera pendingSnap: se levanta al soltar el dedo y se baja en cuanto se hace el encaje, así que solo ocurre cuando de verdad ha terminado un gesto.

Dos detalles de convivencia: tocar la cinta corta la inercia en seco (scroller.forceFinished(true) en onDown), como en cualquier lista; y mientras se arrastra se llama a requestDisallowInterceptTouchEvent(true) para que el ScrollView que la contiene no le robe el gesto y convierta el ajuste en un scroll de la pantalla.

  • DEFAULT — el amarillo de siempre, para cuando no hay carátula que analizar. Tiene que valer lo mismo que @color/um_yellow; está repetido como constante en Kotlin porque hace falta como valor inicial en sitios sin Context a mano (los campos accent de los adaptadores).
  • fromCover(context, data) — carga la imagen con el mismo ImageLoader de Coil que usa toda la app (así también funciona con el arte embebido de un MP3), la analiza y devuelve el color. Es suspend porque decodificar y recorrer píxeles es trabajo pesado que no puede ir en el hilo principal.

  • asBackground(color) — versión apagada y oscura, para usarla de fondo (la cabecera de una ficha). El acento a plena intensidad detrás de un texto sería ilegible.

  • switchTrackTint(accent, defaultTrackTint) — ColorStateList para la pista de un MaterialSwitch: el acento cuando está encendido, el gris de fábrica (defaultTrackTint, capturado por quien llama antes de pisarlo la primera vez, porque una vez sustituido ya no se puede recuperar) cuando está apagado. Esto es el relleno sólido de la pista, no su ripple — ese es un caso aparte, ver el «Qué queda fuera» de AccentTint.
Ojo · dim no es asBackground

Las dos oscurecen, pero no sirven para lo mismo. dim solo baja la luz y conserva el tono y la viveza: es la regla de los dos amarillos de la app. asBackground además desatura y fija una luminosidad concreta, para que el resultado sea un fondo neutro sobre el que se lea el texto, venga de donde venga el acento. Solo la usa la cabecera de las fichas.

Gráficos · HSL y hardware bitmaps

Los ajustes se hacen en HSL (tono, saturación, luminosidad) y no en RGB, porque en HSL «más vivo» y «más claro» son literalmente subir un número, mientras que en RGB habría que tocar los tres canales a la vez sin cambiar el tono.

Y hay un detalle imprescindible: allowHardware(false) al pedirle la imagen a Coil. Por defecto Coil devuelve hardware bitmaps, que viven en la memoria de la GPU y cuyos píxeles no se pueden leer desde la CPU; Palette necesita leerlos uno a uno, así que hay que pedir un bitmap normal.

util/AccentTint.ktobject · aplicar el acento a las vistas

DynamicColor calcula el color; este objeto es el que lo pinta. Recoge los tres gestos que se repiten en todas las pantallas al repintar con el acento, y sobre todo deja escrita en un solo sitio la regla de los dos amarillos de UltiMusic:

Los dos amarillos fijos cumplen esa misma relación, así que mientras no suena nada la app se ve exactamente igual que siempre: la regla no cambia el diseño, solo lo formaliza.

Estructura

  • icons(root, accent, vararg ids) — tiñe iconos buscándolos por id dentro de root. Usa ImageViewCompat.setImageTintList y no setColorFilter, porque un tinte respeta el estado de la vista (pulsada, deshabilitada) y un filtro de color no.

  • stroke(root, id, color, widthDimen) — cambia su contorno (el <stroke>). Hay que volver a pasarle el ancho porque setStroke lo reescribe entero y no hay forma de preguntarle a un GradientDrawable cuál tenía; por eso los anchos viven en res/values/dimens.xml (ipod_stroke_*) y los comparten el XML del drawable y esta llamada.
  • buttons(dialog, accent) — tiñe el texto de los botones («Aceptar», «Cancelar»…) de un AlertDialog ya mostrado, y de paso fija su ripple (el destello al tocarlos) en blanco fijo, no en accent: por defecto Material lo pinta con colorPrimary (el amarillo fijo del tema), así que sin esto los botones de todos los diálogos de la app pulsarían en amarillo aunque su texto ya siguiera el acento. Se hace con un cast a MaterialButton, seguro en esta app porque el tema es Material3 (la MaterialComponentsViewInflater convierte cualquier <Button> de un AlertDialog.Builder normal en un MaterialButton por su cuenta, sin que haga falta MaterialAlertDialogBuilder).
Android · mutate() y drawables compartidos

Tanto fill como stroke llaman a mutate() antes de tocar nada, y es imprescindible. Android cachea los drawables por recurso: dos vistas que usen el mismo @drawable/… comparten el mismo objeto en memoria. Sin mutar, repintar una repintaría también la otra (y cualquier otra que se infle después). mutate() le da a esa vista una copia propia sobre la que escribir.

Por qué no se detecta solo

Aquí no hay ninguna magia que recorra el árbol de vistas buscando lo que sea amarillo: cada pantalla enumera las suyas en su collect de accentColor. Es a propósito. Android deja escribir colores sin problema pero casi no deja leerlos: el color de un <stroke> de un shape no se puede consultar desde código a ningún nivel de API, y los cinco contornos del iPod son justo eso. Detectarlos automáticamente obligaría a re-parsear los XML de los drawables y a llevar un registro de qué era cada superficie antes del primer repintado. Enumerarlas es más tonto, pero se entiende de un vistazo y no se rompe.

Consecuencia práctica: quien añada una vista amarilla nueva tiene que acordarse de darla de alta en su pantalla.

Qué queda fuera

colorPrimary y colorSecondary del tema siguen siendo el amarillo fijo, así que lo que Material pinta por su cuenta desde ahí no sigue al acento automáticamente. Cambiar un color del tema de verdad exige recrear la Activity, que con un color que cambia en cada canción daría un parpadeo constante. Donde molestaba se ha compensado a mano: el tabRippleColor de las pestañas en MainActivity, los contornos y el cursor del editor de metadatos, y las casillas y botones del diálogo «Añadir a playlist».

Hay un caso más sutil, porque no es el relleno de una vista el que se queda en amarillo fijo, sino su ripple — el destello al tocarla, un gesto que Material calcula aparte y que en varios sitios sale de colorPrimary por defecto en vez del android:colorControlHighlight blanco de siempre. Compensado a mano: buttons() (arriba) para los botones de todos los AlertDialog de la app, y en ajustes las casillas «Desactivar límite» / «Opciones adicionales».

El blanco de estos dos usa @color/um_ripple_white (#33FFFFFF, un 20% de opacidad) y no blanco a secas: es el mismo porcentaje que ripple_material_dark, el valor de fábrica de android:colorControlHighlight con el que ya pulsa el resto de la app (mini-reproductor, filas de listas…). Un blanco opaco pulsaba mucho más fuerte que todo lo demás.

MaterialSwitch tuvo un caso propio, más largo de rastrear porque parecía ya arreglado sin estarlo: su ripple no sale de colorPrimary como el resto, sino de colorControlActivated —que en un tema Material3/MDC como este resuelve a colorAccent y de ahí a colorSecondary, el mismo amarillo— cuando está encendido, y de colorControlHighlight (blanco translúcido, sin relación con el acento) cuando está apagado. Ese atributo no lo toca ni trackTint ni thumbTint: el ripple de un MaterialSwitch lo pinta el android:background que hereda de Widget.AppCompat.CompoundButton.Switch (?attr/controlBackground), un selector de fábrica ajeno del todo a esos dos atributos. DynamicColor.switchTrackTint (ver abajo) solo arregla el relleno sólido de la pista, y deja este ripple tal cual: por eso eqSwitch tocaba en blanco al activarlo (rama «apagado» de ese selector) y en amarillo al desactivarlo (rama «encendido»: sigue marcado como encendido mientras se mantiene pulsado, hasta soltar el dedo), aunque la pista ya estuviera corregida. (Un primer intento fue añadir un tercer estado «pulsado» a switchTrackTint y a thumbTint, forzándolos también a blanco; se descartó al dar con el problema de verdad, porque no arreglaba el ripple —la causa real— y encima pintaba la pista de un blanco sólido redundante encima del cual el ripple seguía en amarillo.) Se corta con ThemeOverlay.UltiMusic.SwitchRippleWhite (styles.xml), que redefine colorControlActivated a blanco solo para esa vista vía android:theme — la única vía pública, porque MaterialSwitch no expone ningún rippleColor propio. Aplicado tanto en eqSwitch (dialog_settings.xml) como en el switch de cada carpeta de la lista gris (item_greylist_folder.xml), el mismo problema de fondo en los dos.

MaterialCheckBox.setRippleColor existe pero es private — no se puede llamar desde fuera de la librería, así que las dos casillas fijan app:rippleColor="@color/um_ripple_white" directamente en dialog_settings.xml en vez de por código. MaterialButton.rippleColor (el que usa buttons()) y trackTintList de MaterialSwitch sí son públicos, por eso esos dos se tocan en Kotlin; su ripple, en cambio, no tiene ningún atributo público propio (de ahí el ThemeOverlay de arriba).

util/YouTubeUrl.ktobject · enlaces de YouTube

Traduce cualquier enlace de YouTube al identificador de 11 caracteres que necesita el reproductor. Existe porque loadVideo() no acepta una URL, quiere solo el ID, y porque el mismo vídeo se escribe de muchas maneras según de dónde se copie el enlace.

Formatos que reconoce

  • youtube.com/watch?v=ID (con cualquier parámetro extra detrás: &t=42s, &list=…).
  • youtu.be/ID — lo que da el botón de compartir, normalmente con un ?si=… detrás.
  • /embed/ID, /shorts/ID, /live/ID y /v/ID.
  • El ID pelado, por si el usuario pega solo eso.
  • Da igual el protocolo y el subdominio: se quitan https://, www., m. y music. antes de mirar nada, así que también funciona con lo que el usuario escriba a medias.

Comprobar que el resultado son exactamente 11 caracteres de A-Z a-z 0-9 - _ hace de validación: si lo que se pegó no encaja, devuelve null y quien llama avisa en vez de intentar reproducir algo que no existe. Ofrece además searchUrl(consulta) (la página de resultados con la búsqueda ya escrita) y watchUrl(id) (el enlace canónico, que es lo que se guarda en Song.videoUrl).

Se analiza a mano en vez de con Uri.parse a propósito: así la función no depende de Android y se puede probar sin emulador.

util/Headphones.ktobject · ¿el sonido va a un oído?

Una única función, check(context), que la usa el amplificador de volumen: quitar el tope del 150 % solo se permite cuando el sonido sale al aire, porque un volumen así directo al oído puede dañarlo de verdad.

La pregunta no es «¿hay algo conectado?» sino «¿ese algo va en la oreja?». Un altavoz Bluetooth en la otra punta del salón está tan conectado como unos auriculares, pero amplificarlo no tiene ningún riesgo, así que ahí sí se deja quitar el tope. Distinguirlos es la parte interesante de este archivo.

Las tres respuestas

  • Check.NONE — nada pegado al oído: altavoz del móvil, altavoz Bluetooth, coche… Se puede amplificar sin tope.
  • Check.CONNECTED — auriculares, cascos o audífonos. El tope se mantiene.
  • Check.UNKNOWN_BLUETOOTH — hay un aparato Bluetooth pero no se sabe cuál, porque falta el permiso para preguntárselo. Se trata como si fueran auriculares, pero se distingue del anterior para que la pantalla de ajustes pueda ofrecer conceder el permiso en vez de dar un «no» sin explicación.
Android · AudioManager.getDevices

getDevices(GET_DEVICES_OUTPUTS) devuelve todas las salidas de audio disponibles ahora mismo, cada una con su type (una constante de AudioDeviceInfo: altavoz, HDMI, jack, Bluetooth…).

Se usa esto y no el isWiredHeadsetOn() de toda la vida por dos motivos: aquel está obsoleto y, sobre todo, no se entera de los auriculares Bluetooth, que hoy son la mayoría.

Las salidas por cable (jack con y sin micrófono, USB-C y audífonos) no tienen ninguna ambigüedad: si están, hay auriculares y se acabó. El problema es el Bluetooth.

Bug de verdad · el altavoz de llamadas siempre estaba «conectado»

La primera versión de WIRED_IN_EAR_TYPES incluía TYPE_BUILTIN_EARPIECE, el altavocito de llamadas que se pega a la oreja. Parecía razonable: es, literalmente, un auricular. El resultado fue que check() devolvía CONNECTED en cualquier móvil real, siempre, sin nada conectado — desinstalar y reinstalar la aplicación no cambiaba nada, porque el fallo no vivía en ningún estado guardado.

El motivo: getDevices(GET_DEVICES_OUTPUTS) devuelve las salidas disponibles, no las que están sonando ahora mismo. Cualquier móvil con radio de telefonía tiene ese altavoz de fábrica, así que aparece en la lista esté en uso o no — no hace falta estar llamando para que salga. Y como la comprobación era «basta con que aparezca una vez», siempre encontraba ese candidato y siempre bloqueaba.

La solución es quitarlo de la lista, y es segura: la reproducción de música (STREAM_MUSIC) nunca se enruta sola a ese altavoz — el sistema solo lo usa durante una llamada —, así que no hay ningún escenario real en el que el amplificador de UltiMusic esté sonando por él.

Bluetooth · A2DP, SCO y por qué ninguno de los dos sirve aquí

Bluetooth no tiene una sola forma de mandar sonido, sino varias, y el móvil elige según para qué sirva:

  • A2DP (Advanced Audio Distribution Profile) es el de música: estéreo, calidad alta (códecs SBC, AAC, aptX, LDAC) y unidireccional — solo va del móvil al aparato, no lleva micrófono de vuelta.
  • SCO (Synchronous Connection-Oriented) es el enlace que usan los perfiles de llamada (HFP «manos libres», HSP «headset»): mono, muy poco ancho de banda (calidad de teléfono) y bidireccional, porque lleva también el micrófono del auricular. Es la razón de ese efecto conocido: estás escuchando música con los cascos, entra una llamada y de golpe el sonido se vuelve turbio y enlatado — el móvil ha cambiado de A2DP a SCO para poder abrir el micro.

El problema es que ninguno de los dos dice qué forma tiene el aparato: por A2DP se conectan igual unos auriculares que un altavoz portátil, una barra de sonido o la radio del coche. Si se tratara «A2DP conectado» como «hay auriculares», la app diría «desconecta los auriculares» con un altavoz Bluetooth en la otra punta del salón — justo el caso en el que sí quieres quitar el límite.

Bluetooth · la clase de aparato (BluetoothClass)

Todo aparato Bluetooth anuncia una clase: un número que dice qué es (auriculares, altavoz, equipo de coche, teclado, teléfono…). Esa es la única forma de saber si lo que hay al otro lado va en la oreja, porque el perfil de audio no lo dice.

El camino es: AudioDeviceInfo.getAddress() da la dirección MAC de la salida Bluetooth → BluetoothAdapter.getRemoteDevice(mac) da el aparato → .bluetoothClass.deviceClass da la clase.

NOT_IN_EAR_CLASSES es una lista de lo permitido y no de lo prohibido, a propósito: contiene solo las clases que seguro que no van en la oreja, y cualquier otra se trata como auriculares. Está agrupada por la clase mayor del aparato (la parte del número que dice la categoría general):

  • AUDIO_VIDEO — solo los subtipos de equipo de sonido de habitación: altavoz, coche, hifi, decodificador, vídeo, monitor, pantalla con altavoz, videoconferencia. Fuera a propósito los que sí son auriculares en alguna forma (AUDIO_VIDEO_HEADPHONES, _WEARABLE_HEADSET, _HANDSFREE) y los ambiguos (_PORTABLE_AUDIO, _UNCATEGORIZED, que usan tanto altavoces baratos como auriculares).
  • COMPUTER — de sobremesa, portátil, servidor… Un ordenador emparejado como salida de audio Bluetooth no va pegado a la oreja.
  • PHONE — mismo razonamiento: otro teléfono actuando de altavoz Bluetooth no es un auricular.

El bloque COMPUTER es el que faltaba en la primera versión de esta lista, y el motivo de ampliarla: un PC de Windows emparejado como altavoz Bluetooth se anuncia con esa clase mayor, no con AUDIO_VIDEO. Como no estaba en ninguna lista, caía en el «cualquier otra» y la aplicación trataba el propio ordenador del usuario como si fueran auriculares — bloqueando el amplificador precisamente en el caso más inofensivo posible.

Se quedan fuera las clases mayores WEARABLE (salvo COMPUTER_WEARABLE, dejado también fuera por el mismo motivo) y TOY: cosas como WEARABLE_GLASSES o WEARABLE_HELMET sí pueden llevar altavoces junto al oído, y no hay forma de distinguirlas del resto de su clase (relojes, chaquetas…) sin arriesgarse. Ante la duda, se protege el oído, aunque eso signifique que algún aparato inofensivo se quede tratado como auriculares.

Android · el permiso BLUETOOTH_CONNECT

Preguntarle su clase a un aparato Bluetooth necesita permiso, y Android cambió el sistema en la versión 12 (API 31): antes bastaba con BLUETOOTH, un permiso normal que se concede al instalar; a partir de ahí hace falta BLUETOOTH_CONNECT, que es de tiempo de ejecución y hay que pedirle al usuario con un diálogo, como el de almacenamiento.

Por eso el manifest declara los dos, el viejo con maxSdkVersion="30" para no pedirlo donde ya no sirve. Y por eso el nuevo lleva usesPermissionFlags="neverForLocation": sin esa marca, Android trata el Bluetooth como un permiso de ubicación (porque los aparatos cercanos delatan dónde estás), y aquí no se usa para nada de eso.

El permiso no se pide al arrancar, sino solo en el momento en que hace falta de verdad: cuando el usuario intenta quitar el límite y hay un Bluetooth sin identificar. Si lo concede, se reintenta solo.

Las listas de tipos son arrays de constantes y no rangos porque los valores no son consecutivos: cada tipo de salida tiene su propio número, asignado sin ningún orden particular.

Android · dos APKs

Un test instrumentado no se ejecuta «sobre» la app: se instalan dos APKs (el de la app y el de pruebas, com.untar.ultimusic.test) y el runner (AndroidJUnitRunner, declarado en build.gradle.kts) corre el código de pruebas dentro del proceso de la app. Por eso el test puede tocar clases internas de la app… pero no puede abrir Activities declaradas en el APK de pruebas.

ActivityScenario es el ayudante de AndroidX que abre esa Activity, la lleva a un estado del ciclo de vida y la cierra al terminar; scenario.onActivity { } ejecuta un bloque en el hilo principal, que es el único desde el que se pueden tocar vistas.

Cómo inspeccionar la base de datos

Los tres archivos (ultimusic.db, .db-wal, .db-shm) son SQLite estándar. Cópialos los tres juntos o haz checkpoint antes, porque con la app abierta gran parte de los datos vive en el .db-wal.

  • Android Studio · Database Inspector (View ▸ Tool Windows ▸ App Inspection): con la app en modo debug, ves y editas la BD en vivo. Cero instalación.
  • DB Browser for SQLite (PC, gratis): abre el .db con sus sidecars en la misma carpeta.
  • La copia externa de ~/UltiMusic/databases: ya viene con checkpoint hecho, así que es un archivo consistente y autónomo.
  • Línea de comandos: sqlite3 ultimusic.db "SELECT * FROM songs;".
