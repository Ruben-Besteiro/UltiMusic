Cómo está construido el reproductor: cada script explicado uno a uno, su estructura, el flujo de datos que los conecta y los conceptos de Android, Kotlin y Room que necesitas para entenderlos.

Qué es UltiMusic

UltiMusic es «el reproductor de música definitivo, libre de las restricciones de MediaStore». Esa frase resume su decisión de diseño más importante.

Concepto · MediaStore

MediaStore es el índice de medios del sistema Android: una base de datos que el propio Android mantiene con todas las canciones, fotos y vídeos del móvil. La mayoría de reproductores se limitan a preguntarle a MediaStore «dame las canciones». El problema: si MediaStore tiene una etiqueta mal, un artista mal escrito, etc., tú no lo puedes corregir de verdad.

UltiMusic da la vuelta a eso con dos reglas:

  • Descubrir canciones escaneando el sistema de archivos directamente (recorriendo carpetas), no preguntando a MediaStore.
  • Lo que el usuario edita dentro de la app manda. Las ediciones se guardan en una base de datos propia y sobrescriben lo que hubiera. MediaStore solo se usaría como fuente inicial de etiquetas, nunca como verdad definitiva.

El editor de metadatos de canciones ya está implementado, igual que las pestañas de Álbumes, Artistas y Productores con sus fichas de detalle y el color dinámico sacado de la carátula. La pestaña de Listas de reproducción también está implementada (playlists guardadas como archivos de texto, con reordenación por arrastre y navegación desde el iPod). Quedan los editores de álbum, artista y productor, la pestaña de Géneros y las integraciones con YT-DLP, Last.fm y Musixmatch. Esta documentación cubre el estado actual del código, centrado en la persistencia (guardar los modelos para que sobrevivan al cierre de la app) y la interfaz.

Conceptos base

Ideas de Android, Kotlin y Room que se repiten por todo el código. Si algún término te suena raro más adelante, vuelve aquí.

Kotlin · data class

Una data class es una clase pensada para guardar datos. Kotlin le genera automáticamente cosas útiles (comparación, copia con copy(), texto legible). Casi todos los «modelos» son data classes.

Kotlin · object y companion object

object X { } crea un singleton: una única instancia global para toda la app (útil para utilidades sin estado). Un companion object dentro de una clase es como su «zona estática»: constantes y funciones que pertenecen a la clase, no a cada objeto (p. ej. UltiMusicDatabase.get(...)).

Kotlin · coroutines, suspend y Dispatchers

Una corrutina es una tarea que puede pausarse y reanudarse sin bloquear el hilo. Una función suspend solo se llama desde dentro de una corrutina. withContext(Dispatchers.IO) mueve el trabajo a hilos de entrada/salida (disco, red, base de datos), dejando libre el hilo principal para que la interfaz no se congele.

Kotlin · Flow y StateFlow

Un Flow es un «grifo» de valores que van llegando con el tiempo. Si te suscribes, recibes cada nuevo valor. Room puede devolver un Flow de una consulta: cuando la tabla cambia, el Flow reemite la nueva lista solo. Un StateFlow es un Flow que además recuerda siempre su último valor (ideal para la interfaz).

Android · Activity, Fragment y ViewModel

Una Activity es una pantalla del sistema. Un Fragment es un trozo reutilizable de pantalla dentro de una Activity (aquí, cada pestaña). Un ViewModel guarda los datos de la pantalla y sobrevive a girar el móvil o a recrear la vista; separa «los datos» de «cómo se dibujan».

Android · RecyclerView y Adapter

Un RecyclerView es una lista eficiente: solo crea las filas visibles y las recicla al hacer scroll. El Adapter es el puente entre tus datos y esas filas: dice cuántas hay, crea cada fila (ViewHolder) y rellena su contenido.

Android · Room

Room es la librería oficial para usar una base de datos SQLite con comodidad. Tú describes las tablas con clases anotadas (@Entity), las consultas en una interfaz (@Dao), y Room genera todo el código SQL por ti, comprobando los errores al compilar.

Los modelos de dominio: objetos limpios que consume la interfaz. No saben nada de Room ni del disco; son solo «una canción», «un álbum», «un artista». La capa de datos los produce a partir de las tablas.

Capa de escaneo — data/scan/

La parte de «lectura» de la fonoteca. Recorre el disco y extrae las etiquetas de cada archivo de audio, sin tocar la base de datos.

data/scan/ScannedSong.ktdata class · etiquetas crudas

El resultado de escanear un archivo: solo las etiquetas leídas (título, artista, álbum, artista del álbum, géneros, año, duración, productor, nº de pista y disco). Sin IDs ni relaciones. Es lo que el escáner entrega a la capa de datos.

Los campos de artista/álbum pueden ser null (no todas las canciones traen etiquetas); es la capa de datos quien decide el valor «desconocido».

data/scan/MusicScanner.ktobject (singleton) · escáner de disco

Busca canciones directamente en el sistema de archivos, fiel a la filosofía «libre de MediaStore».

Estructura

  • AUDIO_EXTENSIONS — extensiones reconocidas (mp3, flac, m4a, opus…).
  • Constantes UNKNOWN_ARTIST / UNKNOWN_ALBUM («Artista/Álbum desconocido»).
  • scanRoots() — carpetas donde busca: Descargas, Music y UltiMusic.
  • collectAudioFiles(...) — recorre carpetas recursivamente juntando archivos de audio.
  • readSong(file) — abre el archivo y lee sus etiquetas.
  • scan(): List<ScannedSong> — la función pública; junta todo en segundo plano.

Flujo / por qué

Tablas de la base de datos — data/db/entities/

Cada clase aquí es una tabla de la base de datos. La interfaz no las usa directamente; son la forma «normalizada» de guardar los datos.

Room · @Entity, clave primaria e índices

@Entity convierte una clase en una tabla. La clave primaria (@PrimaryKey) identifica cada fila de forma única; autoGenerate deja que Room asigne un número. Un índice (@Index) acelera las búsquedas por una columna y, si es unique, impide filas repetidas en esa columna.

Concepto · normalización y «clave de emparejamiento»

En vez de repetir «DECO*27» en cada canción, se guarda el artista una sola vez en su tabla y las canciones lo referencian. Eso es normalizar: editar el artista una vez lo cambia en todas sus canciones. Para reencontrar al mismo artista en escaneos futuros, cada artista/álbum guarda su valor de etiqueta original (tagName, tagTitle…) como clave estable de emparejamiento, independiente del nombre editable que se muestre.

data/db/entities/SongEntity.kttabla songs

Una fila por canción. filePath tiene índice único: es el ancla estable que identifica la canción entre escaneos (aunque el id autogenerado cambie).

Guarda los campos editables (title, duration, year, genres, lyrics, language, imageName, comment) y los og* de remix (a null al escanear).

El productor ya no es una columna de aquí: desde la v2 del esquema vive en su propia tabla, enlazada por una tabla de cruce, igual que los artistas.

data/db/entities/ProducerEntity.kttabla producers

title editable + la pareja tagTitle/tagAlbumArtist como índice único compuesto (desambigua álbumes con el mismo título de artistas distintos) + year, genres, imageName.

Room · relaciones N:N y claves foráneas

Una canción puede tener varios artistas y un artista varias canciones: es una relación muchos-a-muchos. En SQL eso se resuelve con una tabla de cruce (cross-ref) que empareja los IDs de ambos lados. Una clave foránea (@ForeignKey) con onDelete = CASCADE hace que, al borrar una canción, se borren solas sus filas de cruce (sin dejar «basura»).

data/db/entities/SongArtistCrossRef.kt · SongAlbumCrossRef.kt · AlbumArtistCrossRef.kt · SongProducerCrossRef.kttablas de cruce N:N
  • song_artist — empareja songId ↔ artistId.
  • song_album — songId ↔ albumId, más trackNumber y discNumber propios de esa aparición.
  • album_artist — albumId ↔ artistId.
  • song_producer — songId ↔ producerId. Gemela de song_artist.

Cada una tiene clave primaria compuesta, claves foráneas en cascada e índice en la columna secundaria (Room exige indexar las columnas foráneas).

Relaciones de lectura — data/db/relations/

data/db/relations/SongWithRelations.ktPOJO de relación

Junta en un solo objeto una SongEntity con sus listas de ArtistEntity, AlbumEntity y ProducerEntity, resueltas a través de las tablas de cruce. Es lo que Room devuelve al leer, y luego se convierte al modelo de dominio Song.

Room · @Embedded, @Relation y @Junction

@Embedded mete las columnas de la canción «en plano» dentro del objeto. @Relation le dice a Room que rellene una lista con las entidades relacionadas, y @Junction indica la tabla de cruce por la que pasar. Room hace las consultas y el emparejamiento por ti.

@Embedded@Relation@Junction
data/db/relations/Summaries.ktPOJOs de salida de consultas

Lo que devuelven las consultas de agregación que alimentan las pestañas de Álbumes, Artistas y Productores: AlbumSummaryRow, PersonSummaryRow y TrackPosition.

Room · POJOs de salida

Una @Query no tiene por qué devolver una entidad: puede devolver cualquier clase cuyos campos coincidan con los nombres de las columnas del SELECT. Room hace el emparejamiento por nombre. Se usa aquí porque lo que se pinta son cuentas y sumas («4 canciones», «12:41»), y calcularlas en SQLite es muchísimo más barato que traerse todas las canciones a memoria para contarlas en Kotlin.

El sufijo Row los distingue de los modelos de dominio del mismo nombre (model/Summaries.kt); los mappers convierten unos en otros.

Los campos sampleSongImage / sampleSongPath sostienen la cadena de carátulas: un álbum o un artista no son un archivo de audio, así que si no tienen imagen propia se recurre a la de una de sus canciones (ver CoverArt).

Núcleo de Room — data/db/

La base de datos en sí, las consultas y los conversores.

data/db/Converters.ktTypeConverter

SQLite no sabe guardar una List<String>. Este conversor traduce la lista de géneros a texto (unido por un separador especial) al guardar, y la reconstruye al leer.

Room · @TypeConverter

Un TypeConverter enseña a Room a guardar un tipo que SQLite no entiende, convirtiéndolo a uno que sí (aquí, lista ↔ texto). Se registra en la base de datos con @TypeConverters.

Nota de mantenimiento: los géneros son provisionales como texto; cuando exista la pestaña «Géneros» convendría normalizarlos en su propia tabla.

data/db/LibraryDao.kt@Dao · el corazón de la persistencia

Define todas las operaciones sobre la base de datos. Es una clase abstracta (no interfaz) para poder incluir la lógica de reconciliación con @Transaction.

Room · @Dao, @Query/@Insert/@Update y @Transaction

Un DAO (Data Access Object) agrupa las operaciones de una tabla. @Query lleva SQL escrito por ti; @Insert/@Update generan el SQL automáticamente. @Transaction agrupa varias operaciones en un todo-o-nada: si algo falla a mitad, no queda la base de datos a medias.

Qué contiene

  • observeSongs(): Flow<List<SongWithRelations>> — la lectura reactiva que observa la interfaz.
  • Resúmenes de las pestañas: observeAlbumSummaries(id), observeArtistSummaries(id) y observeProducerSummaries(id). Calculan con subconsultas el nº de canciones, la duración total, el artista del álbum y la carátula de reserva. El parámetro id hace doble uso: con null devuelven la lista entera (la rejilla) y con un id concreto, una sola ficha (el detalle) — así no hay que duplicar esos SELECT tan largos.
  • Canciones de una ficha: observeSongsOfAlbum(id) (ordenadas por nº de pista), observeTrackPositions(id), observeSongsOfArtist(id) y observeSongsOfProducer(id).
  • Consultas de apoyo del escaneo: allSongPaths(), findArtistByTag(), findAlbumByTag() — buscan por el nombre de la etiqueta del archivo.
  • Consultas de apoyo del editor: findArtistByName() / findAlbumByTitle() / findProducerByName() (buscan por el nombre visible, el editable), observeArtistNames() / observeAlbumTitles() / observeProducerNames() para el autocompletado y trackNumberOf() / discNumberOf().
  • Inserciones, updateSong/Artist/Album/Producer, desenlazado (clearSongArtists/Albums/Producers), borrado por ruta y poda de huérfanos (pruneOrphanArtists/Albums/Producers).
  • reconcile(scanned) — dentro de una transacción: inserta lo nuevo, crea/enlaza artistas, álbumes y productores, y borra lo que ya no está en disco.
  • saveSongEdits(...) — el guardado del editor, también en una transacción (ver abajo).

Cómo guarda el editor: saveSongEdits()

Actualiza la fila de la canción y rehace desde cero sus enlaces con artistas y álbumes. Va todo en una sola @Transaction porque, si no, existiría un instante en el que la canción se ha quedado sin artistas — y como la interfaz observa la base de datos, lo pintaría.

Los nombres que escribe el usuario reenlazan: se busca la entidad con ese nombre y, si no existe, se crea. Nunca se renombra un artista o álbum existente, porque eso afectaría a todas las demás canciones que cuelgan de él (renombrar será cosa de sus propios editores). Por eso resolveArtist() busca primero por nombre visible y solo después por etiqueta: así un artista ya renombrado se reutiliza en vez de duplicarse.

Lo mismo vale para los productores, con una diferencia: si el usuario vacía el campo, la canción se queda sin ninguno. Al contrario que artista y álbum, aquí no se inventa un «Productor desconocido», porque llenaría la pestaña de ruido; por eso el escáner tampoco crea uno cuando la etiqueta no trae compositor.

Detalle fácil de olvidar: la pista y el disco viven en la tabla de cruce song_album, así que hay que volver a escribirlos al recrear los enlaces o se perderían. Al final se podan los artistas y álbumes de los que ya no cuelga nada.

La regla de oro de reconcile()

// Si la canción ya existe, NO se toca: las ediciones del usuario mandan.
if (s.filePath in existing) continue

Esa línea es la que garantiza que las ediciones sobrevivan a reabrir la app: una canción ya guardada se salta por completo, así que ningún reescaneo puede pisar lo que editaste.

Cuando cambias la estructura de las tablas, subes la version y das una «migración» que transforma los datos viejos. Durante el desarrollo se usa fallbackToDestructiveMigration: si el esquema cambió, recrea la base de datos desde cero (se pierden los datos de prueba). El único punto por el que el resto de la app accede a la biblioteca. Orquesta el escáner y la base de datos, y esconde los detalles.

Qué ofrece

SQLite · WAL y checkpoint

Room usa el modo WAL (Write-Ahead Log): los cambios se escriben primero en un archivo aparte (.db-wal) y más tarde se «consolidan» en el .db principal. Por eso, para hacer una copia consistente, primero se ejecuta un checkpoint (PRAGMA wal_checkpoint) que vuelca el WAL al archivo principal.

La copia es unidireccional (solo para inspección; la base interna sigue mandando) y best-effort (si algo falla, se ignora con runCatching). Se hace porque en algunos móviles no se puede entrar en /data/data.

Playlists en disco — data/playlist/

Las listas de reproducción son la única parte de la biblioteca que no vive en Room, sino en archivos de texto. Se decidió así porque una playlist es, conceptualmente, un documento del usuario: debe poder verse y editarse desde fuera de la app y sobrevivir a reinstalaciones sin tocar la base de datos.

data/playlist/PlaylistRepository.ktobject · almacén de playlists

Guarda y lee las playlists de ~/UltiMusic/Playlists. Cada playlist es un archivo <nombre>.txt: el nombre del archivo (sin la extensión) es el nombre de la lista, y su contenido es un nombre de archivo de canción por línea, en orden de reproducción (solo el «basename»: cancion.mp3, no la ruta entera).

Qué ofrece

  • listPlaylistNames() — los nombres de todas las playlists (archivos .txt), ordenados.
  • readFilenames(name) / setFilenames(name, list) — leer y reescribir el archivo entero. Se reescribe completo (en vez de parchear líneas) porque es más simple y seguro; es lo que usa la reordenación por arrastre.
  • createPlaylist / deletePlaylist / renamePlaylist — crear (archivo vacío), borrar y renombrar (renombra el archivo). Rechazan nombres con / o \, que romperían el mapeo nombre↔archivo.
  • addSong / removeSong — añaden al final (si no estaba) o quitan una canción.

Concepto · archivos no reactivos vs. Room

Room reemite un Flow solo cuando cambia una tabla; un File no avisa a nadie cuando se modifica. Por eso, quien observa las playlists (el PlaylistsViewModel) debe volver a leer tras cada cambio: mantiene un contador («tick») que incrementa al mutar y que fuerza el recálculo.

Limitación asumida por diseño: como el modelo pide guardar «los nombres de los archivos», se casa por basename. Si dos archivos en carpetas distintas se llaman igual, gana el que esté en el índice.

Concepto · cola 1, cola 2 y la invariante

Cola 1 = lo que suena y su contexto: el historial ya reproducido, la canción actual (posición currentIndex) y lo que el usuario ha encolado a mano. Cola 2 = todas las demás canciones, mezcladas. Nunca se reproduce directamente de la cola 2: cuando la cola 1 se agota, su elemento 0 pasa al final de la cola 1 y se reproduce. Invariante que se mantiene siempre: cola2 = (todas) − (las de cola1), disjuntas.

  • play(song, allSongs) — destruye y recrea las colas: cola 1 = solo esa canción; cola 2 = las demás .shuffled().
  • addToQueue(song) — mueve la canción al final de la cola 1 (la parte que suena + lo encolado): la quita de donde estuviera (cola 1 o cola 2) para no duplicarla, ajustando el índice si hacía falta. No corta la reproducción.
  • next() — avanza en la cola 1; si se agota, mueve cola2[0] al final de la cola 1 y lo reproduce. previous() retrocede en la cola 1.
  • jumpTo(d) — salto desde la vista de cola del iPod, que muestra la lista combinada cola 1 + cola 2 (d es el índice combinado). Equivale a pulsar siguiente/anterior las veces necesarias: si la pinchada ya está en la cola 1 solo mueve el índice; si está en la cola 2, arrastra a la cola 1 todo lo que hay hasta ella (que pasa a ser historial), igual que ir pulsando «siguiente».
  • seekToFraction(f) — salta a un punto de la canción actual (fracción 0..1 de su duración); lo usan las barras deslizables del mini-reproductor y del iPod.
  • accentColor: StateFlow<Int> — el color de acento de toda la app, sacado de la carátula de lo que suena (ver DynamicColor). Se recalcula en playCurrent(); el cálculo anterior se cancela (accentJob) para que, si el usuario pasa canciones rápido, el análisis de una portada vieja no termine después que el de la actual y deje el color equivocado.
  • Colecciones (fichas de álbum/artista/productor, y playlists): playCollection(collection, startIndex, playlistName = null) y shuffleCollection(collection, playlistName = null). Usan una lógica distinta a la de la pestaña de Canciones: allí se pincha un tema suelto y el resto de la biblioteca pasa a la cola 2 mezclada, porque no hay un «después» natural; aquí sí lo hay —el álbum entero, en orden—, así que la colección ocupa la cola 1 completa y la cola 2 se queda vacía. Al acabar el último tema, se para. Es lo que uno espera al poner un disco.
  • currentPlaylistName: StateFlow<String?> — el nombre de la playlist cuya colección ocupa ahora la cola 1, o null si lo que suena no viene de una playlist (canción suelta, álbum, artista, productor…). Se fija al llamar a playCollection/shuffleCollection con el parámetro playlistName (solo lo pasa el iPod en modo navegación) y se limpia a null en play(song, allSongs) (la reproducción de la pestaña Canciones). Sirve para que, al reabrir una playlist que ya es la que suena, el iPod entre directamente en modo normal en vez de en modo navegación.
  • playRandom(songs) (pasa por play), togglePlayPause(), seekToFraction(f) (mueve la reproducción a la fracción 0..1 de la duración; lo usan las barras deslizables), y playCurrent() privada: único sitio que carga ExoPlayer.
  • Contrato: el sistema de dos colas es la lógica de reproducción exclusiva de «Canciones» (SongsFragment). Solo desde ahí se construye la cola (play/playRandom/addToQueue); los demás fragmentos usarán otra lógica y no deben llamar a esos métodos.
  • Un bucle actualiza el progreso cada 500 ms; onCleared() libera el reproductor.
Diseño · el sistema de colas es solo de «Canciones»

Los métodos que crean o amplían las colas (play, playRandom, addToQueue) son exclusivos del fragmento de Canciones: solo los llama SongsFragment. Los demás fragmentos (Álbumes, Artistas…) usarán en el futuro otra lógica de reproducción distinta, aún por definir. En cambio, los controles sobre la cola ya existente (next/previous/jumpTo/seekToFraction/togglePlayPause) sí los usa el reproductor global —mini-reproductor e iPod— porque operan sobre lo que ya suena.

Modo navegación de playlist

Se entra con newInstance(nombrePlaylist) (lo abre la pestaña de Listas), salvo que esa playlist ya sea la que suena ahora mismo (PlayerViewModel.currentPlaylistName coincide con el nombre): en ese caso se abre directamente en modo normal, porque no tiene sentido "elegir" algo que ya está sonando.

  • Un flag browsing solo afecta al colector de la cola combinada (cola 1 + cola 2): se salta mientras se navega, porque el recuadro superior lo ocupa la lista de la playlist en vez de la cola real. El resto de colectores (currentSong, isPlaying, progress, accentColor) no se gobiernan por este flag: siguen pintando lo que suena de verdad aunque la ventana esté en modo navegación, para no fingir nunca que «no hay nada sonando» si en realidad sí suena algo (de esta playlist, de otra, o de una canción suelta reproducida desde Canciones/Álbumes/etc.).
  • El recuadro superior muestra la lista de la playlist (con PlaylistQueueAdapter) en lugar de la carátula, para poder hacer scroll y pinchar.
  • Las 3 rayas, las flechas y el cursor dependen de si la canción que suena de verdad está en esta playlist (PlaylistQueueAdapter.containsNowPlaying(), revisado en la función local refreshBrowseControls() cada vez que cambia la canción real):
    • No está → selección pura: 3 rayas es el icono de aleatorio (ic_shuffle, reproduce una canción al azar de la playlist) y las flechas mueven el cursor (selectedIndex) por la lista sin reproducir nada (solo resalta la fila).
    • Sí está → no tiene sentido "elegir" nada, ya se está reflejando lo que realmente suena: 3 rayas alterna el recuadro superior entre carátula y lista (como en modo normal), y las flechas van a la canción anterior/siguiente de esta playlist (calculado con nowPlayingIndex() ± 1) — no a previous()/next() del PlayerViewModel, porque esos operan sobre la cola real genérica, que puede ser una colección totalmente distinta (p.ej. si sonaba una canción suelta desde Canciones, su "siguiente" real sería cualquier canción al azar de la biblioteca, no la de esta lista). Para ir a la fila de al lado se hace lo mismo que al pincharla: playCollection(currentSongs(), índice, name), saliendo de la navegación. El cursor pasa a seguir siempre a la fila que suena.
  • Al cargar la playlist, si la canción que suena de verdad está en ella, el cursor arranca en su fila (no siempre en la primera). El recuadro de info, la carátula, el play/pausa y la barra de progreso siempre son los de la reproducción real, nunca los de la fila del cursor.
  • Elegir una fila o pulsar play normalmente llama a playCollection/shuffleCollection del PlayerViewModel pasándole el nombre de la playlist (una playlist es una cola única: ocupa la cola 1 y la cola 2 queda vacía; el nombre se guarda en currentPlaylistName), interrumpiendo lo que sonara antes. Pone browsing = false, cancela la corrutina que mantenía el altavoz/menú al día (browseJob), restaura los controles normales y la ventana pasa a ser el reproductor de siempre. Excepción: si la fila pinchada (o la del cursor, al pulsar play) es justo la que ya suena de verdad (isRowNowPlaying/isSelectedNowPlaying), reiniciarla no tendría sentido, así que en su lugar solo se alterna pausa/reproducción (togglePlayPause) sin salir de la navegación.
  • La barra de progreso (arrastrar/soltar) también funciona en modo navegación: siempre controla la reproducción real, esté o no la ventana navegando una playlist.
  • Reordenar: cada fila lleva un manejador de arrastre; un ItemTouchHelper (solo vertical, iniciado desde el manejador) reordena en memoria y, al soltar, persiste el nuevo orden en el archivo con playlistsViewModel.reorder(name, ...).

ui/editor/MetadataEditorDialogFragment.ktDialogFragment · la pantalla del editor

La pantalla. Es un DialogFragment a pantalla completa por el mismo motivo que la ventana del iPod: se abre y se cierra sin salir de la principal. Usa el tema Theme.UltiMusic.FullScreenDialog, que reutiliza la animación de deslizamiento del iPod pero con fondo opaco.

Estructura / flujo

  • newInstance(songId) guarda el id en los argumentos del fragmento (un Bundle). Nunca se pasan datos por el constructor: Android puede recrear un fragmento al girar la pantalla y solo restaura los argumentos.
  • El formulario se rellena en fillForm(song) desde el collect del ViewModel, pero solo la primera vez (bandera formLoaded). Si no, cada emisión de Room borraría lo que el usuario está escribiendo.
  • Los campos multivalor se leen con splitValues() (parte por comas, recorta espacios, descarta vacíos) y los de texto con textOrNull(), que convierte «vacío» en null para que la columna quede a NULL en la base de datos en vez de guardar una cadena vacía.
  • Guardar valida que el título no esté vacío y llama a viewModel.save(EditorForm(...), pickedImage). El diálogo se cierra al ver saved = true, no justo al pulsar: así solo desaparece cuando la escritura ha terminado de verdad.
  • Álbum(es) y Artista(s) usan MaterialAutoCompleteTextView con setSimpleItems(...): la flechita «▾» despliega los nombres que ya existen en la biblioteca, para no crear «Rosalia» y «Rosalía» por una tilde. Al elegir uno, el widget sustituiría toda la línea, así que setSuggestions lo reescribe cambiando solo el valor posterior a la última coma.
  • La portada llega hasta detrás de la barra de estado con WindowCompat.setDecorFitsSystemWindows(window, false) (le dice al sistema que deje de reservar ese hueco solo) más android:statusBarColor transparente en el tema; el ViewCompat.OnApplyWindowInsetsListener reparte el hueco resultante: el margen izquierdo/derecho/inferior va a la pantalla entera y el superior solo a la toolbar (que crece con layout_height="wrap_content" para no tapar la hora ni la batería).
Android · Photo Picker (PickVisualMedia)

Para elegir la portada se usa ActivityResultContracts.PickVisualMedia, el selector de fotos moderno de Android. No hace falta pedir ningún permiso: el usuario escoge la imagen en una pantalla del propio sistema y la app solo recibe esa. Lo que devuelve es una URI, no un archivo: una especie de dirección con permiso temporal de lectura. Por eso, al guardar, el archivo se copia a la carpeta privada de la app; si guardásemos la URI, la portada se rompería en cuanto el usuario moviese o borrase la foto.

La apertura está protegida contra doble-toque en SongsFragment: onEditMetadata solo llama a .show(...) si parentFragmentManager.findFragmentByTag("metadataEditor") es null. Sin esta guarda, un segundo toque (o un PopupMenu que dispara el clic dos veces) abre dos diálogos superpuestos a pantalla completa: se ven como un contenido «fantasma» duplicado, porque ambos comparten el mismo Window del sistema.

Antes de dibujarse, cada vista pasa por onMeasure, donde el padre le dice cuánto puede medir de ancho y de alto (dos MeasureSpec). Aquí reutilizamos la medida del ancho también como alto (super.onMeasure(widthSpec, widthSpec)), de modo que ambos lados acaban valiendo lo mismo y el recuadro sale cuadrado. Sin esto, el recuadro tomaba «todo el alto sobrante» (con layout_weight) y quedaba rectangular.

Android · ValueAnimator y por qué hay que medir

No se puede animar «de 0 a wrap_content» porque wrap_content no es un número: hay que medir antes cuánto ocuparía el bloque. Eso hace content.measure(...) con MeasureSpec.UNSPECIFIED, que significa «mídete como si tuvieras todo el alto del mundo». Con esa altura real ya se puede usar un ValueAnimator, que no es más que un contador que va de A a B durante unos milisegundos y en cada paso nos avisa para que apliquemos el valor (aquí, el alto del bloque). Al terminar de abrir se devuelve la altura a WRAP_CONTENT, para que la sección pueda crecer sola si un campo ocupa dos líneas.

Utilidades — util/

util/CoverArt.ktcarátulas con Coil

Resuelve la carátula de cada canción con una cadena de reserva: imagen personalizada → arte embebido en el archivo → recuadro negro. Incluye un Fetcher propio para que Coil sepa extraer la imagen embebida de un archivo de audio, y un ImageLoader compartido (CoverLoader).

El primer eslabón lo rellena el editor de metadatos: si song.imageName apunta a un archivo que existe dentro de coversDir(context) (filesDir/covers/), cover(context, song) devuelve ese archivo; si no, cae en el arte embebido. Por eso la función necesita un Context: sin él no se sabe dónde está la carpeta privada de la app.

Para un álbum, artista o productor la cadena tiene un eslabón más, porque ellos no son un archivo de audio: imagen propia → imagen personalizada de una de sus canciones → arte embebido de una de sus canciones → recuadro negro. Eso es lo que describe un CoverRef(ownImage, songImage, songPath), que rellenan las consultas de resumen del DAO y resuelve la sobrecarga cover(context, ref).

Coil es una librería para cargar imágenes de forma asíncrona en un ImageView (descarga/decodifica en segundo plano y cachea). Un Fetcher personalizado le enseña a obtener imágenes de una fuente no estándar — aquí, el arte embebido dentro del MP3.

util/DynamicColor.ktobject · color a partir de la carátula

Saca un color de acento de una carátula para teñir con él la interfaz: las pestañas, las barras de progreso, la rueda del iPod y la cabecera de las fichas. Es lo que sustituye al amarillo fijo de UltiMusic cuando hay algo sonando o una ficha abierta.

AndroidX · Palette

Palette es una librería de AndroidX que analiza un Bitmap y devuelve un puñado de colores representativos («swatches») ya clasificados: vibrante, apagado, oscuro, claro… Aquí se prefieren los vivos, porque un gris sacado de una portada oscura no se distinguiría del fondo negro de la app.

Estructura

  • DEFAULT — el amarillo de siempre, para cuando no hay carátula que analizar.
  • fromCover(context, data) — carga la imagen con el mismo ImageLoader de Coil que usa toda la app (así también funciona con el arte embebido de un MP3), la analiza y devuelve el color. Es suspend porque decodificar y recorrer píxeles es trabajo pesado que no puede ir en el hilo principal.
  • readable(color) (privada) — normaliza el color: le fuerza un mínimo de saturación y mete su luminosidad en una franja media-alta. Sin eso, una portada casi blanca daría un acento invisible y una casi negra, uno indistinguible del fondo.
  • asBackground(color) — versión apagada y oscura, para usarla de fondo (la cabecera de una ficha). El acento a plena intensidad detrás de un texto sería ilegible.
  • onColor(fondo) — el color de texto que se lee sobre ese fondo: blanco sobre fondos oscuros, negro sobre claros.
Gráficos · HSL y hardware bitmaps

Los ajustes se hacen en HSL (tono, saturación, luminosidad) y no en RGB, porque en HSL «más vivo» y «más claro» son literalmente subir un número, mientras que en RGB habría que tocar los tres canales a la vez sin cambiar el tono.

Y hay un detalle imprescindible: allowHardware(false) al pedirle la imagen a Coil. Por defecto Coil devuelve hardware bitmaps, que viven en la memoria de la GPU y cuyos píxeles no se pueden leer desde la CPU; Palette necesita leerlos uno a uno, así que hay que pedir un bitmap normal.

Cómo inspeccionar la base de datos

Los tres archivos (ultimusic.db, .db-wal, .db-shm) son SQLite estándar. Cópialos los tres juntos o haz checkpoint antes, porque con la app abierta gran parte de los datos vive en el .db-wal.

  • Android Studio · Database Inspector (View ▸ Tool Windows ▸ App Inspection): con la app en modo debug, ves y editas la BD en vivo. Cero instalación.
  • DB Browser for SQLite (PC, gratis): abre el .db con sus sidecars en la misma carpeta.
  • La copia externa de ~/UltiMusic/databases: ya viene con checkpoint hecho, así que es un archivo consistente y autónomo.
  • Línea de comandos: sqlite3 ultimusic.db "SELECT * FROM songs;".
